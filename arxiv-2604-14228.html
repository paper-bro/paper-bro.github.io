001Lesson 1 — The Hook~6 min

When autocomplete isn't enough

For years your coding assistant could only finish your sentence. You'd type function login( and it would guess the rest. Helpful — but it never left the editor. It couldn't open another file, run your tests, or tell you "that didn't work, let me try again."

This paper asks: what does it really take to go from finishing a line to fixing a bug for you? The authors reverse-engineered 1,884 files of TypeScript — about 512,000 lines — from Claude Code v2.1.88 to map the answer.

⌨️

Autocomplete

Inline suggestions inside the editor. Example: GitHub Copilot. No conversation, no tools.

💬

Chat in IDE

You ask, it answers and can make multi-file edits. Example: Cursor. Still lives in the editor.

🤖

Agentic CLI

It runs shell commands, reads and writes files, calls external services, and iterates until tests pass. Examples: Claude Code, Codex CLI, Aider.

Beyond those is a fourth level — fully autonomous systems like Devin or SWE-Agent that aim to work with almost no human check-ins — but Claude Code sits deliberately in that middle "agentic CLI" level: autonomous enough to be useful, supervised enough to stay safe.

Every coding agent, no matter which level, has to answer the same recurring design questions: Where does reasoning live — in the model or in hand-written rules? How does the loop keep going? What is allowed by default? What is the scarcest resource? How do you add new capabilities? How do you split work across helpers? How do you remember across sessions?

The paper's core finding: At the center is a tiny while-loop — call the model, run tools, repeat. One striking estimate highlighted by the paper (from community analysis of the codebase, not the authors' own measurement) is that only about 1.6% of the code is that decision logic — the other ~98% is the "harness" around it that makes the loop trustworthy.

That harness reflects five human values the authors traced from Anthropic's own design documents:

  • Human Decision Authority — you stay in charge, can interrupt, and approve what matters.
  • Safety, Security & Privacy — it should protect you even when you're not paying attention.
  • Reliable Execution — it does what you actually meant, and you can verify it.
  • Capability Amplification — you get done work you wouldn't have attempted before (about 27% of tasks in Anthropic's own survey).
  • Contextual Adaptability — it learns your project, tools, and style over time.

To serve those values, the system is split into seven functional components that all feed one place.

Think of it like a kitchen: you (the user) can walk in through several doors — an interactive terminal, a one-shot claude -p command, an IDE plugin, or a developer SDK. Every door leads to the same chef: the agent loop. Before the chef can touch anything, every requested action passes the permission system. Approved actions go to tools (read a file, run bash, search the web) that act on the execution environment (your filesystem, shell, network). And the state & persistence layer writes everything down so you can resume later.

The paper threads one concrete job through all seven components to make this real: "Fix the failing test in auth.test.ts." You'll follow that same bug through the whole course.

Try the lab below: give the same bug to three generations of assistant and watch what changes. Notice how only the agent actually closes the loop by running tests and checking the result — and ask yourself: what extra machinery must exist to make that loop safe to leave running?

002Lesson 2 — The Loop~8 min

One while-loop to rule them all

Imagine your kitchen has one rule: you can think whatever you want, but you are not allowed to touch the stove. You write a note saying "please turn on burner 2," a kitchen manager reads it, checks the safety rules, and only then does the work. That split is the heart of Claude Code.

At its center is a tiny program called queryLoop() in query.ts. It is an async generator — just a function that can pause, hand an update to the screen, and resume. The paper finds the whole loop is surprisingly small. The model does the thinking, the loop does the doing, and most of the other 98% of the codebase exists to move data safely around that loop.

A single turn — one time through for your prompt "Fix the failing test in auth.test.ts" — follows the same 9 steps every time:

  1. Resolve settings — load the system prompt and permission callback. These do not change mid-turn.
  2. Set up State — create one mutable State object for messages, tool context, and counters. At 7 different "continue points" the loop replaces this whole object at once, instead of tweaking fields piecemeal.
  3. Compact boundary — call getMessagesAfterCompactBoundary() so compacted old history stays as a summary, not the original messages.
  4. Five pre-model shapers — budget, snip, microcompact, collapse, auto-compact — run cheapest-first to shrink context before the model is called. You will meet them properly in Lesson 4.
  5. Call the model — deps.callModel() streams back text and any tool_use blocks.
  6. Dispatch tools — if tools were requested, StreamingToolExecutor starts them as they stream in, or the fallback runTools() groups them. Reads can run in parallel; writes (like shell commands) are serialized.
  7. Permission gate — every request is checked (Lesson 3). Any layer can block it.
  8. Collect results — turn each tool's output into a tool_result message for the next iteration.
  9. Loop or stop? — if there was no tool_use, you are done. Otherwise continue.
The key separation: the model never touches files, runs shell commands, or hits the network directly. It only emits structured tool_use blocks. The harness parses them, checks permissions, runs the real tool, and feeds the result back. Reasoning and enforcement live in different code paths — so even a tricked model cannot bypass sandboxing or deny-rules.

Two safety nets make the loop resilient. Inside tool dispatch, a sibling abort controller kills other in-flight Bash work the instant one Bash tool errors, instead of letting broken commands finish. Outside the loop, recovery logic handles overload: hit the output-token cap? Retry up to 3 times with a higher limit. Get a prompt_too_long error? Try reactive compaction and retry once. There is also a streaming fallback and an optional fallback model.

Stopping is equally explicit. The loop ends when the model answers with text only (the normal success), when maxTurns is reached, when a prompt_too_long survives recovery, when a PostToolUse hook sets hook_stopped_continuation, or when you hit abort.

In short: one tiny while-loop, surrounded by a lot of careful plumbing to keep it honest and recoverable.

Try it: step through one full turn below. Toggle whether the model still wants tools, drag the pressure slider to fire shapers, inject a prompt_too_long error, and watch when the loop continues versus when it stops — and how those 7 whole-object State updates and model calls add up.

For the curious — generator detail: queryLoop() yields StreamEvent | RequestStartEvent | Message | TombstoneMessage | ToolUseSummaryMessage so the UI can render in real time while the loop keeps a single synchronous control flow inside. normalizeMessagesForAPI() filters to user-type messages before the next call.

003Lesson 3 — Saying No~8 min

Who decides what's allowed?

An AI that can run shell commands for you is powerful — and a little scary. What stops it from deleting files, leaking secrets, or running something dangerous because you accidentally approved it while half-reading a pop-up?

In Claude Code, the answer is not one big lock. It is a gauntlet of seven independent checkpoints. Every tool request — like npm test via BashTool to reproduce your failing test — must pass through all of them. Any single checkpoint can say no.

Key idea: deny-first with human escalation. The rules are checked in strict order: deny beats ask beats allow. If anything is unknown, the system does not silently allow it — it escalates to you. A broad rule like deny rm -rf always wins, even against a narrow allow rm -rf /tmp/cache.

Those checkpoints are:

  1. Tool pre-filtering — blanket-denied tools are removed before the model even sees them.
  2. Deny-first rule evaluation in permissions.ts — your allow/deny lists applied with deny on top.
  3. Permission mode — the baseline when no rule matches.
  4. Auto-mode classifier — an extra ML check (when enabled) that does a fast filter plus a short chain-of-thought about safety.
  5. Shell sandbox in shouldUseSandbox.ts — filesystem and network isolation, independent of rules.
  6. Non-restoration on resume — restarting with --resume in a new process does not carry old grants with it.
  7. Hook interception — PreToolUse and other hooks (5 of 27 hook events are safety-related) can block or rewrite the request.

The permission modes form a slider from most careful to most automatic: plan (approve a plan first), default (ask for most writes), acceptEdits (auto-approve safe edits in the repo), auto (the ML classifier decides, gated by a feature flag), dontAsk (if it would ask, auto-deny instead), bypassPermissions (skip most prompts — but safety checks still apply), plus internal bubble for subagents that escalate to the parent. More autonomy does not mean fewer safety layers — it means fewer pop-ups, with automation filling the gap.

Why not just ask the human every time? Because humans stop checking. The paper cites internal data that users approve about 93% of prompts — classic approval fatigue — and that auto-approve rates climb from roughly 20% to over 40% as people use the tool more. Sandboxing alone cut prompt volume by about 84% by handling safe cases silently, instead of adding more warnings that get ignored.

Even with seven layers, they are not magic. The paper shows they can share a weakness: for example, commands with more than 50 subcommands once fell back to a single generic prompt instead of per-command deny checks, because per-command parsing made the UI freeze. When layers share performance or cost limits, they can fail together — a real trade-off engineers must watch.

One more human touch: a denial is not a dead end. The model gets the reason and tries a safer alternative next loop turn — a blocked rm -rf might become a targeted rm build/cache.json.

Try it below: sneak a dangerous command past the gauntlet, then add rules and flip modes to see what actually stops it — and what stays blocked even in the most permissive mode.

004Lesson 4 — The Backpack~8 min

The 200K-token backpack problem

Imagine your backpack can hold exactly 200 pages. A chat model from a few years ago could read one textbook at a time — that's all. Now picture an AI teammate that has to carry your project instructions, a pile of file reads, test outputs, tool results, and an entire conversation history — all in that same backpack, all at once. That backpack is the context window, and in Claude Code it is the boss.

For older models the backpack holds about 200,000 tokens (think: pieces of words). For the newer Claude 4.6 family it stretches to 1,000,000. The paper's big finding is that this size — not how fast the computer is, not how many tools exist — is the binding constraint. Everything competes for the same space. One giant test log can eat a fifth of the backpack by itself.

So before every call to the model, Claude Code packs the backpack in a careful order. First the system prompt (the model's base instructions), then environment info like git status — loaded once and remembered with a cache via getSystemContext() so it doesn't cost again. Next comes the CLAUDE.md hierarchy: plain Markdown files with your preferences and project rules, loaded via getUserContext(). There are four levels, from broadest to most specific: managed (set by your organization), user (your personal ~/.claude/CLAUDE.md), project (checked into the repo), and local (a git-ignored CLAUDE.local.md just for you). Files closer to where you're working win. If the agent wanders into a new folder, extra rules for that folder load lazily — only when needed — and @include lets one file pull in another with cycle prevention. This content is delivered as a user message, so the model tries to follow it, but hard safety still comes from permission rules.

After the instructions come the heavy stuff: auto-memory snippets, tool metadata (often hidden until the agent actually asks via ToolSearch), conversation history, file reads, command outputs, and subagent summaries. Each one costs tokens — which is why lazy loading and deferred schemas matter.

When the backpack overflows, Claude Code doesn't just throw out the oldest pages. It runs a graduated pipeline of five shapers, cheapest first, before every model call:

  1. Budget reduction — per-tool size caps on huge outputs, replacing the rest with a reference. You keep the full file on disk, just not in the backpack.
  2. Snip — a light trim of older history (gated by HISTORY_SNIP).
  3. Microcompact — a cache-aware squeeze that knows which parts are already cached (gated by CACHED_MICROCOMPACT).
  4. Context collapse — a virtual, read-time projection (gated by CONTEXT_COLLAPSE). The full history stays on disk; the model only sees a collapsed view with no user-visible output.
  5. Auto-compact — as a last resort, the model writes a compressed summary of old conversation via compactConversation(), firing PreCompact hooks first. Powerful, but costs a whole extra model call.

The same backpack logic shapes two other savings tricks. Tool schemas for 35 of the up-to-54 tools are deferred — the model sees only names until it needs details. And when a subagent finishes exploring that auth module for you, only its short summary hops into your backpack; the subagent's full trace stays in its own sidechain file. That keeps the parent lean, even though the team as a whole used about 7× more tokens in plan mode.

No single shaper is enough — that's the point. Cheap trims handle everyday overflow; heavy summarization is saved for emergencies, preserving recent context longest.

Try it yourself in the lab below: pile in file reads and chat history until you overflow, then flip the five shapers on one by one and see which layer saves you cheapest. Watch how a shaper that's enabled but not needed shows "not needed" and saves 0 — just like the real pipeline in query.ts.

Going deeper. How does summarization not lose your old messages forever? The boundary marker saved to disk carries three IDs — headUuid, anchorUuid, tailUuid — so the loader can patch the chain back together at read time. Compaction appends; it never deletes transcript lines. The five shapers live in query.ts lines 365–453 and are traced in Sections 4.3 and 7.3; the CLAUDE.md loader is in claudemd.ts and compaction building in compact.ts.

005Lesson 5 — Extensions~8 min

Four ways to give the agent superpowers

An agent loop alone isn't very useful — it can call a model and run a tool, but which tools does it have? Claude Code's answer isn't "one plugins folder." It's four different ways to plug in, each with a different price in context.

Think of the context window like a backpack that only holds about 200,000 tokens (1M in the newest models). Everything you add — instructions, file contents, tool descriptions — takes up space. So Claude Code organizes extensions by how much backpack space they cost, cheapest first:

🪝

Hooks — 0 cost

Lifecycle interceptors that run before or after a tool. 27 events like PreToolUse can block, rewrite, or annotate an action. Zero context by default.

📘

Skills — low until used

A SKILL.md file with 15+ frontmatter fields (description, allowed tools, model override…). Only a short description sits in the prompt; full instructions inject only when you invoke the skill via SkillTool.

📦

Plugins — medium

A distributable bundle defined by PluginManifestSchema. One plugin can contribute 10 kinds of components — commands, skills, hooks, MCP servers, agents, output styles and more — across all insertion points.

🔌

MCP servers — high once schemas load

Model Context Protocol — the open standard for external services. Each server adds real callable tools over stdio, SSE, HTTP and other transports. Tool schemas are large, so they cost the most backpack space.

This is the five-layer view in Figure 3: the surface (CLI, SDK, IDE) feeds the core loop, which is guarded by the safety/action layer (permissions, hooks, tools, subagents), fed by the state layer (context, memory, transcripts), sitting on the backend (shell, MCP, remote). Extensions plug into different layers at different costs.

Where the price matters most is tool assembly. Before each turn, assembleToolPool() in tools.ts runs five steps:

  1. Base enumeration: 19 tools are always there — Bash, Read, Edit, Agent, Skill and more. 35 more are conditional on flags and user type. Up to 54 total.
  2. Mode filtering: In CLAUDE_CODE_SIMPLE mode the model sees just 3 tools: Bash, Read, Edit.
  3. Deny pre-filtering: filterToolsByDenyRules() strips blanket-denied tools from the model's view — so the model can't even try them.
  4. MCP merge: Tools from connected MCP servers are filtered and merged in.
  5. Dedup: If a name clashes, built-in wins over MCP.
Why four, not one? Because they plug in at different spots in the loop (Figure 5 in the paper): assemble() controls what the model sees (skills), model() controls what it can reach (MCP tool pool), execute() controls whether an action runs (hooks). Plugins can touch all three. A single mechanism would force every extension to pay the highest context cost.

The trick that makes expensive extensions affordable is deferral: with ToolSearch on, the model sees only MCP tool names at first; full schemas load on demand. Cheap extensions scale widely for free; expensive ones are reserved for when you truly need a new tool surface.

006Lesson 6 — Divide & Conquer~7 min

Hiring AI helpers (carefully)

Fixing that failing test in auth.test.ts might need two jobs at once: one helper to explore how auth.ts works, another to draft a plan. Claude Code can hire AI helpers called subagents for that. The trick is hiring them carefully — so they don't rummage through your desk and overwrite each other's work.

Every helper runs in its own isolated bubble. It does not see the parent's conversation history and it does not automatically inherit the parent's permissions. It gets a fresh context window, its own assembled tool set, and a self-contained prompt. That's the paper's isolated subagent boundaries principle: share nothing by default, share only what you explicitly allow.

You create a helper with the Agent tool — AgentTool.tsx and runAgent.ts under the hood. You give it a prompt ("explore the auth module"), pick a type, and choose how isolated it should be:

🔍

Explore / Plan / Verify

Read-only helpers. Explore searches code, Plan writes a plan, Verification runs checks. Safe to run in parallel — they can't edit files.

🛠️

General-purpose

Can read and write. Powerful for real fixes, but needs isolation so it doesn't collide with you or another helper editing the same file.

🎛️

Custom

Your own .claude/agents/*.md file becomes a helper's instructions, model, tool list, and hooks. Plugins can ship them too.

Isolation has three levels. In-process is the default: own conversation, but same folder on disk — fastest, but two writers can clash. Worktree gives the helper a temporary Git copy of the repo to edit safely; changes don't touch your working files until you merge them. Remote (internal-only) runs on a remote machine in the background.

Permissions are also isolated. If you start Claude Code with --allowedTools from the SDK, those SDK-level allows are kept for all helpers. But session-level rules you added during the chat are replaced by each helper's own allowedTools list. And a safety override always wins: if the parent is in bypassPermissions, acceptEdits, or auto mode, the helper can't escalate beyond that — the human's top-level choice travels down.

Why only summaries come back: Each helper writes its full chat to its own sidechain file (.jsonl + .meta.json), not into the parent's transcript. The parent receives only a short summary text. That's how Claude Code keeps the parent's 200K-token backpack from overflowing. The trade-off is real: agent teams in plan mode use about 7× the tokens of a normal session in the paper, and summaries can hide detail you might want.

Teams of helpers coordinate through a surprisingly simple trick: file locking. Each teammate has an inbox JSON file on disk, and messages are pushed under a lockfile — no message broker needed. It's slower, but you can debug it by opening a file.

Try it below: hire helpers for the auth bug, switch their jobs and isolation modes, and watch three numbers move — how much the parent must carry, how much token cost multiplies, and whether edits collide. See why the paper picks worktree when edits are risky and in-process when read-only speed matters.

Go deeper: the override cascade — When a helper defines its own permissionMode, the parent's bypassPermissions / acceptEdits / auto still wins because those represent an explicit human decision about autonomy. Async helpers also decide whether to show permission prompts: explicit canShowPermissionPrompts > internal bubble mode (always show) > sync shows, async hides by default, with classifier+hooks resolving first.

007Lesson 7 — Memory~7 min

Remembering without oversharing

Your laptop crashes in the middle of fixing that auth test. When you reopen Claude Code, should it remember everything — your prompts, test output, the compact summaries — and also automatically re-allow every tool you approved before?

Keeping the first part is helpful. Automatically keeping the second part is risky. Lesson 7 is about how Claude Code remembers reliably without oversharing trust.

Claude Code actually keeps three separate diaries. The session transcript is the main one: one append-only JSONL file per session, project-scoped, with a line for every prompt, tool result, and compact boundary. The global prompt history is just your past prompts in history.jsonl for up-arrow navigation. And sidechain transcripts are separate .jsonl + .meta.json files for each subagent, so subagent chatter never inflates the parent file. They run independently.

The key rule for the session transcript is append-only. Compaction never deletes old lines. Instead buildPostCompactMessages() appends something like [boundaryMarker, ...summaries, ...messagesToKeep, ...attachments]. The boundary marker carries three IDs — headUuid, anchorUuid, and tailUuid — via annotateBoundaryWithPreservedSegment(). Think of them like paper-clips linking old pages.

On resume, the loader doesn't erase history; it applies a read-time projection. It uses those UUIDs to patch the parent chain, so the model sees the short summary view while the disk still holds the full history for audit and reconstruction. In plain words: what the model sees is compressed, what is stored is complete.

Why trust doesn't survive a restart: Session-scoped permissions live only in memory — they are never written into the JSONL. Running --resume in a new process replays messages and boundaries but starts with zero grants. Forking to a new session does the same. This is deliberate safety: don't carry stale trust into a changed context; re-grant it.

One common mix-up: "checkpoints" in Claude Code are not general workflow save-points. They are file-history snapshots for --rewind-files, stored at ~/.claude/file-history/<sessionId>/, letting you revert file edits. The conversation transcript and the file snapshots are separate systems.

008Lesson 8 — So What?~8 min

Same questions, different answers — and what's left to solve

The paper's big move is to treat design questions as the constant and answers as the variable. Every serious coding agent must decide: where does reasoning live, what safety posture to use, how to manage a fixed context window, how to extend the system, how to delegate work, and how to remember it. Claude Code, OpenClaw, and Hermes Agent all face the same six questions (Section 10) — they just answer from different worlds.

Take trust. Claude Code assumes an untrusted model on a trusted developer machine, so it uses deny-first per-action rules: deny beats allow every time, with 7 permission modes from plan through default and acceptEdits to auto (an ML classifier in yoloClassifier.ts), dontAsk, bypassPermissions, and internal bubble. Seven layers must all pass — pre-filtering, deny-first rules, mode constraints, the auto classifier, shell sandboxing, non-restoration on resume, and hooks. OpenClaw is a persistent gateway daemon on port 18789: one trusted operator, many untrusted channels. Its answer is perimeter-level — DM pairing codes, sender allowlists, and opt-in sandboxing per-agent or per-session. Hermes sits in between: one file (tools/approval.py) with three modes (manual, smart with an extra LLM check, off) plus an unconditional HARDLINE_PATTERNS floor that always blocks rm -rf /, mkfs, raw dd to block devices, fork bombs and shutdown — and the same approval rendered in four places: CLI prompt, Telegram/Discord keyboards, IDE permission pop-up, and a cron-only unattended mode.

The other dimensions rhyme the same way. Runtime: Claude Code's center is the single queryLoop() async generator (Section 4); OpenClaw's center is the gateway control plane that embeds a pi-coding-agent runner inside RPC dispatch; Hermes is a synchronous while inside AIAgent.run_conversation that by default runs up to 90 iterations and then makes one tool-free summary call. Extensions: Claude Code offers 4 mechanisms at graduated context cost (hooks = 0, skills = low until invoked, plugins = medium, MCP servers = high once schemas load); OpenClaw offers 12 capability types plus a ClawHub registry; Hermes offers 5 surfaces — the same 3 plus pluggable memory and model-provider backends you can swap wholesale. Memory: Claude Code compresses with 5 layers before every model call (budget reduction → snip → microcompact → context collapse → auto-compact); OpenClaw promotes with dreaming, daily notes and hybrid vector+keyword search when embeddings are on; Hermes does one summarizer with tail-budget protection plus a scan that replaces prompt-injected context files with [BLOCKED]. Multi-agent: Claude Code delegates tasks to Explore/Plan children that return only summaries via sidechain files; OpenClaw routes to fully isolated agents with bindings and nesting depth up to 5; Hermes delegates via delegate_task with at most 3 children and depth 1 by default, plus a separate SQLite Kanban board where multiple workers claim and heartbeat tasks.

No one best design — deployment context picks the winner. A CLI bound to one repo wants per-action safety and a single loop. A multi-channel gateway wants perimeter control and gateway-wide plugins. A single-process, multi-surface assistant wants one approval file rendered everywhere and swappable backends. And they stack: OpenClaw can host Claude Code via ACP, and Hermes can be both host and guest.

Telling which answer is better means looking at evidence, not just architecture. The paper shows per-action approval alone is shaky: users approve about 93% of prompts (Hughes 2026), so Claude Code cut prompts by an estimated 84% with sandboxing instead of adding warnings. The cost of bounded context is measurable: after Cursor adoption across 807 repos, complexity rose 40.7% (He et al. 2025); across 304,000 AI-authored commits, about one-quarter of AI-introduced issues persisted, with security issues persisting even more (Liu et al. 2026). A randomized trial of 16 developers found AI made them 19% slower despite feeling 20% faster (Becker et al. 2025), and cleaner inputs saved 7–8% tokens and 34% file revisits even when pass rates didn't change (Trivedi & Schmitt 2026). The paper's bet — minimal scaffolding, maximal operational harness, with about 1.6% decision logic and 98.4% harness — matters most as models converge: one harness-only change can shift long-horizon scores by up to 18 points (Ding et al. 2026).

That leaves Section 13's six open directions, which apply to all three systems. How do we catch silent failures when 78% are invisible and evaluation lags observability? What belongs between a static CLAUDE.md hierarchy and a single session's transcript — durable memory that survives restarts without reintroducing stale permissions? Where should the harness run, when should it act proactively, what non-text actions should it own, and with whom should it coordinate? How do we scale from one session to weeks-long programs with verifiable done-ness? What logging and oversight will governance require? And the cross-cutting question from Section 2.4: how do we amplify capability without hollowing out understanding — when studies already show 17% lower comprehension (Shen & Tamkin 2026), persistent neural effects (Kosmyna et al. 2025), and a 25% drop in entry-level hiring (Rak 2025)? The paper's closing takeaway is that future systems must treat that sustainability gap as a first-class design problem, not a downstream metric.

ABCWord bank

Word bank.

AI agent

An AI system that can decide what steps to take, run tools like reading files or shell commands, see the results, and keep going until a task is done.

Agent loop

The simple while-loop that drives the agent: call the model, get tool requests, check permissions, run tools, add results, repeat. In Claude Code it is called queryLoop().

Harness

All the deterministic code around the model — permission checks, tool routing, context building, recovery — that lets the model act safely. The paper estimates only ~1.6% of Claude Code is decision logic; ~98.4% is harness.

ReAct

Think → Act → Observe pattern. The model reasons, calls a tool, the harness runs it and returns the result for the next turn.

Permission mode

One of seven modes that sets baseline safety: plan, default, acceptEdits, auto (ML classifier), dontAsk, bypassPermissions, plus internal bubble for subagents.

Deny-first

Rule-evaluation order: deny rules always beat allow rules, even if the allow is more specific. Unrecognized actions are escalated, not silently allowed.

MCP server

Model Context Protocol — an open standard for connecting the agent to external services (databases, web tools). Each server contributes tools the model can call.

Plugin

A distributable bundle that can contribute commands, skills, hooks, MCP servers, agents, and more in one package.

Skill

A Markdown file (SKILL.md) with instructions that shapes how the agent thinks for a specific domain. Loaded cheaply, invoked via the SkillTool meta-tool.

Hook

An event handler that can intercept lifecycle moments — e.g. PreToolUse to block/rewrite a tool call. Claude Code defines 27 hook events.

Context window

The maximum text the model can see at once — 200K tokens for older models, 1M for Claude 4.6. Once full, older content must be trimmed or summarized.

Compaction pipeline

Five steps that shrink context before each model call, cheapest first: budget reduction → snip → microcompact → context collapse → auto-compact (model summary).

CLAUDE.md hierarchy

Plain-text memory files at four levels: managed (OS), user (~/.claude/CLAUDE.md), project (CLAUDE.md), local (CLAUDE.local.md). Loaded as user context, not hard enforcement.

Subagent

A child AI session spawned by the parent via the Agent tool (Explore, Plan, or custom). Runs in its own isolated context and returns only a summary.

Worktree isolation

A temporary Git copy of the repo that lets a subagent edit files without touching the parent's working directory. One of three isolation modes (in-process, worktree, remote).

Sidechain transcript

A separate .jsonl file that stores a subagent's full conversation so it doesn't inflate the parent's context or session file.

Append-only transcript

Session storage as append-only JSONL lines — new events are only added, never overwriting old ones, so history stays auditable and resumable.

Defense in depth

Security idea: stack independent safety layers (pre-filtering, rule evaluation, mode constraints, ML classifier, sandbox, hook interception, non-restoration on resume) so any one can block harm.

001Lesson 1 · The Bottleneck~8 min

Why teaching AIs one task at a time hits a wall

Imagine how humans get smarter: we try things in the world, get feedback, and try again. An AI agent learns a bit like that too. The paper calls it a loop: worlds give tasks → humans guide learning → the agent acts → the world gives a checkable result → repeat.

That loop works beautifully for one or two kinds of puzzles. Then it gets stuck. The authors of The Trinity point to two bottlenecks that stop us scaling to many kinds of multimodal tasks — tasks that mix images, video, board-like grids, and plain text, often over dozens of steps where a single missed detail can ruin everything.

🏗️

Bottleneck 1: Worlds are expensive

Each new task needs a world that can actually check answers. Building 44 different, reliable worlds by hand — games, puzzles, robot tables, driving tests — is slow and costly.

🧩

Bottleneck 2: The helper is too slow

Capability increasingly depends on the Harness — the helper programs around the AI's frozen brain. Hand-tuning that Harness for every new task diversity cannot keep up.

Until now, most Harness self-improvement picked one of two bad deals. Deal A: make a separate, task-specific Harness for each task family, good for coding or math alone. It overfits — like memorizing last year's exam — and collapses on unfamiliar tasks. Deal B: make one global Harness for everything. It hits conflicts — a rule that helps a puzzle hurts a robot that must also save time and battery.

The paper tests this on 44 benchmarks across five domains, from Mastermind and chess tactics to navigation and long text adventures. With that much surface diversity — photos from a robot camera, video questions, text grids, and pure text — both deals lose ground. That is the wall this course will climb over: instead of teaching task by task, teach by the shared capabilities underneath.

002Lesson 2 · The Harness~10 min

Meet the Harness: six helpers around a frozen brain

Think of the Trinity agent like a frozen brain surrounded by six helpers. The brain is a big foundation model — in the paper it's Claude Opus 5. Its weights, called $\theta$, never change. The helpers around it are called the Harness, written $\mathcal{H}_{\phi}$, and only their setup $\phi$ changes. So learning here does not mean growing a bigger brain; it means building better helpers around the same brain.

Every moment $t$ the agent gets three things you already know: the task $\tau$ (what "win" means), the observation $o_t$ (what the camera or text shows right now), and the public history $\xi_{<t}$ (everything said and done so far that everyone can see). It also has a small controller state $s_t$ (like a step counter) and a budget of tools $\mathcal{C}_{\tau}$. From these, the six helpers fire in a fixed order, each a pure function — same inputs always give same outputs, no secret memory.

Frozen brain $f_\theta$ + changeable helpers $\mathcal{H}_{\phi} = (\Pi_{\text{er}}, \mathbf{M}, \mathbf{I}, \mathbf{P}, \mathbf{F}, \mathbf{L})$
Base helpers $\mathcal{H}_0$ is where everyone starts. Evolution updates $\phi$, never $\theta$.
$$f_t = \Pi_{\text{er}}(o_t, \xi_{<t}) \qquad v_t = \mathbf{M}(\xi_{<t}, s_t, f_t)$$

1. Perception $\Pi_{\text{er}}$ reads $o_t$ with history and extracts clean facts $f_t$ — "fan is left of desk, two cups at positions X,Y". 2. Memory $\mathbf{M}$ merges history, state, and new facts into a useful view $v_t$ — "we already checked cup A, it was empty, so next is cup B by the fan". Memory is the only helper allowed to carry things forward.

$$\text{Cand}_t = \mathbf{I}(\tau, v_t) \qquad d_t = \mathbf{P}(\tau, s_t, v_t, \text{Cand}_t)$$

3. Inference $\mathbf{I}$ lists compatible candidates $\text{Cand}_t$ from task and view — "lift cup-1, lift cup-2, or report 'no cube'". 4. Planning $\mathbf{P}$ ranks them into one directive $d_t$ — "lift cup-2 next, because cup-1 is known empty".

$$\mathcal{C}_t = \mathbf{F}(\mathcal{C}_{\tau}, s_t, v_t, d_t) \qquad (s_{t+1}, e_t, c_t) = \mathbf{L}(s_t, v_t, d_t, \mathcal{C}_t)$$

5. Orchestration $\mathbf{F}$ checks which resources are actually usable now, $\mathcal{C}_t$ — "gripper free, budget left". 6. Loop $\mathbf{L}$ decides to execute $e_t$ (move, lift) or commit $c_t$ (final answer), or withhold action to wait for more evidence, and updates $s_{t+1}$. A strict rule: you can only say a hypothesis is wrong after you have observed a contradiction — no guessing.

Go deeper: because every module is a pure function of public records, the host can verify it. The paper's "host" checks interfaces, lineage, and that a claim has executable evidence before keeping an update. This is why Trinity can trust the feedback that drives evolution.

003Lesson 3 · From Tasks to Capabilities~12 min

Don't group by what tasks look like — group by what they need

Looks can lie. In the figure the same 44 benchmarks are sorted by what they look like — games, puzzles, navigation, social play, long adventures. Colors mark five surface domains. It feels tidy, but it hides something useful.

What actually makes a task hard is not its surface. The paper's key insight: two tasks with totally different looks can need the same hidden skill. Example the authors give: ARC-AGI-3 (little grid puzzles shown as text) and Micromouse (a robot exploring a maze) both live or die on PST — Perception & State Tracking, keeping an accurate picture of what changed.

So the team stopped grouping by surface and grouped by need. Here is how, in plain steps.

  1. Trained agents propose candidate skills K from task specs and from real play traces. A judge merges duplicates, reviewers check coverage. Result: 6 capabilities labeled c,d,a,b,e,f = CFR, GVT, PST, HCI, VEA, VC (from constraint checking to video comprehension) and 30 defect types that prove a skill was missing.
  2. Each training task τ gets its requirement set Kτ — the skills that task really tests, even if the current Harness already passes.
  3. A fixed order c ≺ d ≺ a ≺ b ≺ e ≺ f sorts every set from broadest to narrowest, so the same set always spells the same path.
  4. Those sorted paths are merged like a dictionary:
$$p_{\tau}=\operatorname{sort}_{\prec}(K_{\tau}),\qquad \mathcal{T}=\operatorname{Trie}(\{p_{\tau}:\tau\in\mathcal{B}_{\mathrm{tr}}\})$$

What does that formula do? sort≺ just puts the skill letters in the fixed order. Trie takes all those paths and glues together any shared prefix. Think of an address book: “Main St” is written once, then “Main St → #12” and “Main St → #14” branch off it.

The result is the capability tree T: only 11 non-root nodes cover all 28 training benchmarks. Five totally different benchmarks — AdaPlanBench, Master Keying, Memory Maze, Pooltool Billiards, TextQuests — from three surface domains all land on the same node c → a because they share the same needs. Unseen tasks are slotted onto the finished tree later for checking, without rebuilding it.

Why bother? A flat list of six skill groups is cheaper but weaker. A shared-prefix tree lets child nodes inherit what their parents learned and specialize only on what is new — the foundation for the evolving Harnesses you will meet next.

🧩

Surface ≠ skill

ARC-AGI-3 = colored cells on a grid. Micromouse = corridors. Same need: remember what you saw and where you are (PST).

🌳

Trie trick

Fixed order turns sets into spellings. Trie merges c, c→a, c→d→a … so every shared prefix is learned once and reused.

Go deeper: the 30 defect types are concrete failure patterns. F05 “re-issuing a refuted item” points to PST, F13 “no pre-commit constraint check” to CFR, etc. Counting which benchmarks trigger which defects is how the authors assigned Kτ (Table 7).

Now try it: in the lab, add tasks that look different but need the same chips. Watch how sorting in fixed order and merging prefixes collapses them onto one reusable node.

004Lesson 4 · Tiny Training Worlds~12 min

Why a tiny, simple world can teach a big skill

Imagine four homework assignments that look completely different: a card game, a physics puzzle, a board game, and a text adventure. In the paper's node d, that's exactly what happens — the tasks have different pictures, rules and words, but they all require the same hidden skill: don't commit until you've checked the evidence.

The Trinity's answer is what the authors call Capability-Driven Real2Sim2Real. Instead of copying any one big task, the Creator builds a tiny, simplified simulated world that keeps only that core decision. Think of it like a driving school cone course: no traffic, no weather, just the steering skill you actually need to learn. The big, messy original — with all 28 training benchmarks — is saved for the test.

Not every tiny world counts. First, a host verifier pool auto-checks each world for binding, execution, state transitions, rendering and completion — did it run correctly and can the score be trusted? Then Explorer does a quick screening run with a frozen Harness (no learning yet). Only worlds where Explorer scores in a middle band are admitted. Too easy — Explorer gets ~90% — and there's nothing to learn. Too hard — ~10% — and there's no signal to improve. If it's outside the band, Creator adjusts difficulty along fixed axes like gates, budget or memory load and tries again.

Training in Sim, testing on Real measures true transfer. You train only on the verified, admitted tiny worlds. You evaluate only on the original complex benchmarks. If scores rise there, the capability really transferred — you didn't just memorize a level.

And it does transfer. In Table 3 (module-only, no extra skills), training on the original tasks at capability-tree nodes gets 53.44 Train / 42.31 Unseen. A single Global Harness pooling all 28 environments gets 53.04 / 42.92. Training on the verified synthetic worlds at the same 10 nodes and 11 environments gets 56.95 Train / 47.26 Unseen — the best in the table — with the lowest inference cost at 514.42M tokens on Train and 549.07M on Unseen. Less is more when "less" is better focused.

Try it below: build a tiny world by moving difficulty, set the screening band, and see when a world gets verified and admitted — then watch what happens to the original-task score.

005Lesson 5 · Growing Specialists~12 min

How Harnesses evolve without losing what they already learned

Think of a team of specialists who all share a big handbook. When the handbook gets a new chapter at headquarters, should every specialist copy it right away? Only if the new chapter is actually better. That's the idea behind how the Trinity grows without forgetting.

The big handbook is the frozen model — it never changes. What changes is the Harness around it, the six helpers from Lesson 2. Because different capabilities need different helpers, the paper doesn't make one giant Harness. It grows a whole Harness tree lined up with the capability tree from Lesson 3.

Every node v in that tree — like c or c → d → a — has its own Harness. The paper writes it as

$$H_{E,v}^{(i)} = P_v^{(i)} \oplus L_v^{(i)}$$

P is what it inherited from its parent, L is its own local modules, and \oplus is a right-biased join: if both define the same module name, the local one wins. That way a child can specialize without deleting its parent's work — ancestors are preserved.

Selective inheritance — keep only what beats what you have. Before fixing itself, a child looks at its parent's new version. The host (an automatic checker, not the AI) runs both versions on the same validation tasks and counts completions. The new parent is kept only if strictly higher. Otherwise the child keeps its old P. One bad parent update can't wash through the whole tree.

Then comes local fixing:

$$Z_v^{(i+1)} = \text{Rollout}(P_v^{(i+1)}\oplus L_v^{(i)}, D_v^{(i+1)})$$
$$\tilde{L}_v^{(i+1)} = \text{Evolve}(L_v^{(i)}, Z_v^{(i+1)}, F_v^{(i)})$$

In plain words: run the current Harness (inherited + old local) on the node's admitted tiny worlds D to collect trajectories Z — what it saw, did, and whether the host said it succeeded. Evolver compares wins and losses and proposes a new local module tilde L. The host checks evidence, interfaces, and version lineage; if it passes, it replaces the old local. Feedback F_v^{(i+1)} = \text{Feedback}(Z_v^{(i+1)}, E_v^{(i+1)}) is saved for the next iteration, and children later export whatever was retained.

The Creator side works differently. Explorer keeps a Harness at every node for later routing, but Creator keeps one shared library for building worlds:

$$R_C^{(i+1)} = \text{Consolidate}_{\prec_C}\left(R_C^{(i)} \cup \bigcup_{v} \Delta R_{C,v}^{(i+1)}\right)$$

R_C is that library. Each node proposes fixes \Delta R only when a verifier finds a broken world. At the end of the iteration the host merges them: distinct skills are kept, partial overlaps are merged to keep the complementary parts, and near-duplicates keep the earlier one. By the final iteration Explorer has 29 modules M01–M29 spread across the tree and Creator has 25 modules total.

The topology never changes — the same 11 nodes each time — so validated updates just accumulate. Try it below: pick a child node, test whether its parent's new version deserves to be inherited, then run its local rollout and watch the host decide.

Go deeper: what the symbols mean
v = a capability-tree node (e.g., c→d), i = iteration number, P_v = inherited registry, L_v = local registry, D_v = admitted synthetic curriculum for that node, Z_v = rollout trajectories, F_v = verified feedback for next round, E_v = evaluation receipts. All costs and scores are host-verified, not self-reported.

006Lesson 6 · The Router~10 min

Choosing the right specialist for each new task

After the first lessons, the Trinity has grown a small team of specialists — one Harness for each branch of the capability tree. One is good at constraint checking, another at perception and state tracking, another at hypothesis probing, and so on. Now a new task arrives. Who should do it?

Picking the same Harness for everything fails (too many conflicts). Picking randomly fails too. The paper needs a chooser — the Capability-Aware Harness Router.

Think of it like an emergency dispatcher. The dispatcher never sees the private answer, only the public call: the goal, the first image, and basic metadata. Call this public info x_n for task n. The dispatcher also has a pool of versioned specialists 𝒞 — a subset of the evolved Harness tree ℋ(i) — each with a card that says what capabilities it trained on.

Before acting, the Router runs this rule:

$$ h_n = \pi\bigl(x_n, \mathcal{C}, R(x_n,\mathcal{M}_n), S(\mathcal{M}_n)\bigr) $$

In words: policy π picks one Harness h_n using the task's public info x_n, the candidate pool 𝒞, the retrieved past experience R(x_n,ℳ_n), and summaries S(ℳ_n). It must write an evidence-based reason before execution, then run. After the host verifies the outcome and cost f_n, memory is updated for the next caller:

$$ \mathcal{M}_{n+1} = \text{Append}\bigl(\mathcal{M}_n, (x_n, h_n, f_n)\bigr) $$
The key guardrails: memory ℳ_0 is seeded only with verified, training-side runs from the base Harness — never unseen tasks. Retrieval only brings up to 10 records with cosine similarity ≥ 0.5, from a 20,000-record FIFO. Summaries only cover Harnesses that were actually tried — untried outcomes stay "unknown". Tasks are handled once, in file order, with no fallback if you pick wrong.

Does this help? On the final Iteration-4 tree, Table 4 shows: Random picking scores 52.74 (Train) / 46.23 (Unseen) and burns ~567M/594M tokens. An agent with only public info scores 65.79 / 52.36. Add capability definitions and aggregate performance cards → 70.34 / 58.27. Add retrieved execution experience → 71.27 Train (497.89M tokens) / 60.96 Unseen (541.28M), very close to the Oracle best-of-every-task score of 73.16 / 63.61 — and with fewer tokens, because good matches waste less trial-and-error.

007Lesson 7 · Capabilities Meet Modules~10 min

The paper's evidence that skills link to specific helpers

If you could see what a job needs, you could pick the right helper for it. The Trinity team tested whether that is true: do specific hidden skills line up with specific helper programs in the Harness?

They checked at Iteration 4. Six capabilities (rows): PST perception & state tracking, HCI hypothesis & counterpart inference, CFR constraint checking & feedback repair, GVT goal commitment & value trade-off, VEA video evidence acquisition, and VC video comprehension. And six Harness protocols (columns): Perception, Memory, Inference, Planning, Orchestration, Loop — the same six helpers from Lesson 2.

For each pair they computed a correlation between -1 and +1. Positive (red in the paper) means the protocol tends to be present when the capability is needed; negative (blue) means it tends to be absent.

Strongest positive per row in the paper: PST→Memory 0.306, HCI→Inference 0.744, CFR→Planning 0.274, GVT→Loop 0.444, VEA→Perception 0.347, VC ties Perception & Memory 0.286. Most negative: GVT→Perception -0.361 and PST→Loop -0.313.

Correlation is a hint, not proof. So they ran interventions — actually adding or removing a module and re-measuring score (Table 5, module-only, benchmark-equal mean 0–100).

On the starting Base Harness H₀ at 39.06: adding one relevant module (right helper for the task's capability) jumped to 58.45 — a gain of +19.39 — and tokens dropped from 582.54M to 551.85M. Adding an irrelevant module barely moved the score to 40.08 (+1.02) and tokens stayed high at 583.37M.

On the fully evolved Harness H⁽⁴⁾ at 73.16: removing one relevant module hurt the score to 70.42 (-2.74) and pushed tokens up from 496.70M to 517.26M.

Why this supports the paper's claim: many-to-many still holds. A skill like "hypothesis consistency" can need Memory plus Inference plus Planning together, and one Memory module can serve several skills. The correlations show the pattern; the interventions test causation in a controlled way (same protocol class, similar description length, just different relevance).

In the lab, click cells in the correlation map to add or remove a module and watch the score and token cost change. Try a dark-red match versus an off-diagonal cell — you'll see why the paper says capability requirements can guide which helper to build.

008Lesson 8 · Proof in Simulation and on Real Robots~12 min

Did it work? And did it work on real robots?

Imagine you study for a test using tiny practice quizzes you made up, then take the real exam — cold — and do better anyway. That would mean you didn't memorize answers, you learned the skill itself. That's the test The Trinity set for itself.

First, the scores. With the big AI brain frozen and only the helpers improved, the average score across 28 training benchmarks rose from about 39 to about 73 out of 100 — a gain of roughly 34 points. On 18 completely unseen benchmarks (tasks the system never practiced on and never used to build its capability tree), the average rose from about 37 to about 64 — roughly a 26-point gain. If you count only the 16 unseen benchmarks run in software, it went from about 42 to about 64. Either way, the final unseen score sits clearly above two strong reference Harnesses the authors ran the same way: Codex at about 47.5 and DeepSeek at about 46.2.

It wasn't just one good jump. The first round of fixing was the biggest, but the system kept improving for three more rounds. From round 1 to round 4 it added another 9 points on training tasks and about 6 points on unseen tasks. Some tasks show this plainly: ARC-AGI-3 (tricky grid puzzles) went 41.0 → 53.6, and SciGym (recover hidden science equations) went 45.2 → 57.1. Others barely moved — Mastermind stayed at 88.9 — and one even dipped a little, Eleusis 82.2 → 81.1. That's normal: not every skill benefits equally.

The hard question isn't "did training scores go up?" It's "did scores go up on tasks it never saw?" Because the capability tree and all practice worlds were built only from the 28 training benchmarks, any gain on the 18 unseen benchmarks has to be transfer — the helpers learned a reusable way of checking evidence, not a memorized answer.

Was this expensive? The first round cost more to build the tiny worlds — about 406 million tokens of work for the capability-simulation approach, versus about 212 million if you just practiced on the original tasks. But The Trinity then reuses those worlds. As the rounds continue, building cost falls while scores still rise, and running the final Harnesses is actually cheaper than the starting one: the lowest running cost of any approach in the paper. In simple terms: pay once to build good practice, then reap the savings every time you use it.

The biggest reality check was robots. Two jobs were picked because they both need the same capability the tree calls d → a: don't commit until you have evidence. In SOON, a Unitree G1 must walk from a side room through a doorway and touch the desk beside a white fan within 30 moves, without bumping furniture. In CaP-X, an AlohaMini2 arm must look under three upside-down cups and say if a small cube is there, its colour, and which cup — or correctly say "none" — also within 30 moves. For each job the Harness was kept frozen; the robot got only five practice tries in the simulator to distill into fixed tips. Those five tries don't count toward the score.

At the start, both robots failed. SOON's base helper reached out half a metre too early in simulation and out of reach on the real robot. CaP-X's base helper knocked cups around and answered "no cube" without ever checking the cup that hid it — 0% on the real desk for both, and 0% and 10% in simulation. After four rounds, with the helpers evolved at node d → a, SOON hit 80% in simulation and 60% on the real robot; CaP-X hit 60% in both. The difference you see in the videos is simple: the final helper slows to small steps and waits until the desk is straight ahead, or lifts cups one by one and retries a missed grasp before it reports. Same eyes, same brain — better judgment about when to act.

ABCWord bank

Word bank.

Harness

A frozen large model plus helper programs around it. The paper writes it as H_phi = (Pi_er, M, I, P, F, L) and evolves only the helpers, not the model weights.

Frozen backbone

The large AI model inside the Harness (Claude Opus 5 in the paper) whose weights are never changed during self-improvement. Only the Harness helpers are updated.

Protocol

One of six helper roles: Pi_er (Perception) extracts facts, M (Memory) builds a view of history, I (Inference) lists possible candidates, P (Planning) picks a plan, F (Orchestration) checks tools, L (Loop) decides to act or wait.

Task Tree

A tree of benchmarks organized by surface type: 44 benchmarks in 5 domains and 15 subclasses, e.g., games, puzzles, navigation, social games.

Capability Tree

A tree where tasks that need the same underlying skills are grouped together, even if they look different. Built as a Trie of sorted requirement sets: p_tau = sort_prec(K_tau), T = Trie({p_tau}). Has 11 non-root nodes in the paper.

Capabilities (a-f)

The six shared skills the paper discovers: PST (Perception & State Tracking), HCI (Hypothesis & Counterpart Inference), CFR (Constraint Checking & Feedback Repair), GVT (Goal Commitment & Value Trade-off), VEA (Video Evidence Acquisition), VC (Video Comprehension). 30 defect types map to them.

Creator's Simulated Worlds

Capability-Driven Real2Sim2Real: build small, cheap, checkable simulated worlds that teach just the capability of a node, train the Harness there, then test on the original complex tasks to measure transfer.

Selective Inheritance

How a child node re-uses its parent's helpers: H_{E,v} = P_v ⊕ L_v with right-biased union. The new parent is kept only if it gets strictly more host-verified task completions on the same test; otherwise keep the old one. Ancestor helpers are preserved.

Capability-Aware Router

The per-task chooser that picks one compatible Harness from the tree using public task info plus retrieved verified past executions: h_n = pi(x_n, C, R(x_n,M_n), S(M_n)), then updates memory M_{n+1}=Append(M_n, (x_n,h_n,f_n)). Retrieval needs cosine >=0.5, max 10 records.

Verified feedback / Verifier

Why the paper can trust scores: a host program auto-checks node binding, execution, state changes and completion. Only passed worlds are used; Explorer also screens to keep only worlds in an intermediate-performance band.

RSI Iteration

Recursive Self-Improvement loop where Explorer rolls out, Evolver proposes fixes, and Creator builds worlds, iterated 4 times with the same capability tree topology.

001The problem~8 min

Why Smart AIs Fail as Teammates

Imagine asking a friend: “Fix my bike.” Would they know what’s broken — the chain, the tire, the brakes? Probably not. Most real requests are like that: short, fuzzy, and missing key details.

That’s exactly where today’s smartest AIs stumble. Models like GPT-5 are trained to solve a task alone when given a perfect, detailed prompt. The paper calls this isolated task completion. It works on benchmarks, but not with real people.

The paper measured the gap. A precise task description in their coding data is about 193.8 words long — files, error messages, steps to reproduce. The vague version of the same request is only 11.4 words on average. On research questions (BrowseComp-Plus) it’s 97.1 vs 17.8 words. That’s a lot of missing information.

Key insight: Being smart at solving isn’t the same as being good at collaborating. The paper tracks three separate scores: Productivity (did it solve the task?), Proactivity (did it ask helpfully and efficiently?), and Personalization (did it ask the way you wanted?). Frontier models score high on the first, low on the other two — for example GPT-5 on their coding task scored Productivity 55.8 but Proactivity only 36.6 and Personalization only 13.0.

What happens if you just make the prompt vague? On a function-finding task (SWE-Func-Loc) the same model’s success score (F1, a 0-to-100 measure of finding the right functions) fell from 64.50 to 44.11 — a 20-point drop. Just letting the base model chat didn’t help; it didn’t know when to ask or what to ask.

Only after the paper’s training — where asking well is rewarded — did the score recover to about 56.26 on vague prompts. The lesson of this whole course: collaboration doesn’t come for free. It has to be trained.

Try it yourself below. Drag vagueness from precise to very vague and switch between a base agent that guesses and a PPP-trained agent that asks one good question. Watch productivity fall and then recover.

002Building UserVille 1/3~7 min

Making Instructions Vague on Purpose

Imagine you ask a friend to fix a bug and you just say: “filtering crashes sometimes.” Your friend has no idea which repo, which date, which error. That’s real life — and it’s exactly what the paper copies on purpose.

In lab datasets, prompts are super precise so anyone can grade them. On SWE-Bench Verified the precise prompt averages 193.8 words; on BrowseComp-Plus it averages 97.1 words. Real users are not like that. So UserVille’s Stage 1 is Prompt Vaguenization: an LLM rewrites each precise prompt into a short, fuzzy one.

It follows two simple principles:

  1. Keep at most one key detail and generalize dates, numbers, names, places.
  2. Remove everything else, but keep the original intent as a hint.

Here’s a real example from the paper. Precise (about 60 words): a child missing many times between 2014–2018, with ages 13, 14, 16 and different outcomes. Vague (paper’s output): “According to authorities, what color shirt were they last seen wearing when they went missing in 2018?” One hint remains — the shirt in 2018 — the rest is gone. Word count drops from 193.8 → 11.4 on SWE-Bench (and 97.1 → 17.8 on BrowseComp-Plus).

Key idea: information asymmetry. After vaguenization the agent only sees the short vague prompt. The user simulator secretly keeps the long precise prompt, so it can answer follow-up questions correctly. That gap is the whole point — without it there would be nothing useful to ask.

Why do this? It turns two static benchmarks into interactive tests the paper actually uses: 488 Python SWE-Bench Verified tasks and 100 BrowseComp-Plus research tasks. Every vague prompt now needs collaboration: the agent must decide when to ask, and the simulator can judge if the question was answerable.

In the lab you become the vaguenizer. Pick a precise prompt, choose which details to keep, hit “Make vague,” and watch the word count plunge and the hidden vs. revealed info split — that’s the setup for the next lessons on how the agent should ask.

003Building UserVille 2/3~8 min

Building Users With Different Preferences

Imagine you call customer support. One person wants a quick yes-or-no. Another wants every detail. If the helper uses the same style for both, at least one will be frustrated.

The paper's second UserVille step builds that frustration in on purpose — so an agent can learn to adapt. It creates 20 different user types, each with a clear rule for what counts as a good question.

12 of them were seen during training, like:

  • no_ask — please don't ask me at all
  • concise_question — keep it to one short sentence
  • do_selection — give me A/B/C choices
  • amateur vs professional — can you handle technical questions or not?
  • answer_more — ask at least three questions

And 8 were held out as unseen, hidden until test time, like capital (ALL CAPS ONLY), json (must wrap the question in JSON), lang_ita (Italian only), or length (exactly three sentences). If the agent only memorized the first 12, it would fail here.

The key idea: preferences are not suggestions. Each has its own automatic check. 6 use pure count-or-string rules with no AI judge — for example no_ask is simply -1 if ask_turn > 0. The other 14 use an LLM-as-judge with a preference-specific rubric — for example capital is -0.5 if not all caps.

During training the simulator was GPT-5-Nano. For every training prompt the paper mixes 12 vague variants (one per seen preference) plus 1 precise prompt — a 13× repetition — so the agent sees the same task asked in many different styles.

That is the setup for personalization: the same correct answer can still get a bad score if it was asked in the wrong way. Try it yourself below — pick a fussy user and see if your question passes their exact check and what R_{Pers} penalty the paper would give it.

004Building UserVille 3/3~7 min

How to Grade Good Collaboration

Getting the right answer is only half the job. Imagine an AI fixes your code but annoys you with five confusing questions — or never asks and gets it wrong, so you have to clean up anyway. How do you grade that?

This lesson is the third piece of UserVille: after making prompts vague and giving users different preferences, the paper adds a fair way to grade the interaction itself, not just the final answer.

Three separate grades

For every session UserVille gives three scores:

  • Productivity — did the task succeed? For bug-fixing (SWE-Func-Loc) this is F1, a match score between the functions the agent found and the true ones. For research questions (BrowseComp-Plus) it's EM (exact match judged by the official checker). For full coding it's whether unit tests pass.
  • Proactivity — was asking efficient and not annoying?
  • Personalization — did it respect how you want to be asked?

Proactivity and personalization are the new part. Here’s how the paper makes them concrete.

Low, medium, high — by effort, not topic

The simulator knows the hidden precise prompt. It classifies each agent question by how hard it is for you to answer:

  • Low-effort: the answer is already in that hidden prompt. Minimal thought. Example: if the precise bug report says “blank email crashes validators.py,” asking “what error on blank email?” is low-effort — you already meant that.
  • Medium-effort: the answer is outside the hidden prompt, so you think, then give up with “I don’t know.” Wasted time, no info. Example: “what color should the button be?” when the bug report never mentioned color.
  • High-effort: you’d need outside work — search docs, run the codebase, read release notes. Example: “can you run the repo and paste the trace?”

Trick: if the agent never asks and just guesses wrong on a vague prompt, the paper also counts that as high-effort — because now you must verify and fix its bad patch.

Session score is 0 or 1, not an average. Take the maximum effort across all turns. One high-effort question makes the whole session high. Proactivity = 1 only if the max is Low, otherwise 0. One bad question ruins it — just like one annoying interruption can ruin a chat.

And did it follow your style?

Personalization is even simpler: 1 if the agent followed your stated preference, 0 if not, judged by a rule or by the simulator as judge. Crucially, this score is only averaged over sessions where the agent asked at least one question — if it never asks, there’s nothing to judge for style.

With these two 0/1 rules, UserVille turns “nice to work with” into numbers you can train on. Next you’ll be the judge: try sorting questions into Low / Medium / High and see how a single high-effort question flips the session score — and why the later reward will punish it with -0.5 but only reward a clean low-effort session with +0.05.

005The PPP fix~9 min

Teaching With Three Rewards at Once

Imagine training a puppy with three rules at once: get the toy, don't bark annoyingly, and sit how your owner likes. Reward only "got the toy" and the puppy learns to bark nonstop to get help. The paper had the same problem with AI agents.

They gave the agent one total score made of three parts:

$$R = R_{\text{Prod}} + R_{\text{Proact}} + R_{\text{Pers}}$$

$R_{\text{Prod}}$ is productivity — did it solve the task? In a simplified version, 1 if correct, 0 if not. $R_{\text{Proact}}$ is proactivity — was it efficient to help? $R_{\text{Pers}}$ is personalization — did it follow your style?

The exact math from Section 5.1:
$$R_{\text{Proact}} = (+0.05 \text{ if all low}) -0.1 \times N_{\text{med}} -0.5 \times N_{\text{high}}$$
$$R_{\text{Pers}} = (+0.05 \text{ if fully followed}) + (\text{penalty from Table 7})$$

For example, a penalty of $-0.5$ per violation for capital, json or do_selection, and $-0.1$ for concise or amateur.

Why such small numbers? The $+0.05$ is a gentle nudge — "nice, you asked well." The $-0.5$ is five times stronger than $-0.1$, because a high-effort question ("go read the whole codebase for me") is much more annoying than a medium one ("I don't know" after thinking). The team tested this in Appendix C:

  • No penalty or bonus: agents spammed — 4.65 questions per task, only 51.4% were good.
  • With penalties (-0.1 / -0.5): dropped to 0.81 questions, 89.6% good.
  • With both penalties + bonus: best balance — 1.10 questions, 92.7% good.

And if you train on task reward alone ($R_{\text{Prod}}$ only), the agent gets worse over time at asking and at following preferences — even though it still solves tasks. PPP is needed to keep all three up. Table 1 shows the trade-off: on SWE-Func-Loc the productivity-only ablation is actually slightly higher on productivity (56.77 vs PPP's 56.26), but it collapses on the other two (proactivity 42.45 vs 75.55, personalization 57.43 vs 89.26). PPP wins on the overall average — 62.04 across all dimensions and datasets — because it balances all three.

006How it learns~8 min

Learning in Groups: The RL Engine

An AI learns like a student who only sees a final grade — did the code pass? But the paper's reward is more than that: a task grade plus points for how you asked. How do you turn that into an actual weight update?

The answer is: compare inside a small group. For one vague prompt q, the agent doesn't try once, it tries G = 8 different trajectories from its current policy πold. Think of it as eight parallel attempts at the same homework.

Each trajectory τi is a sequence of tokens — some the agent wrote, some that came from tools or the user. It gets a total reward:

$$R_i = R_{\text{Prod}} + R_{\text{Proact}} + R_{\text{Pers}}$$

That's the 0-or-1 task score plus the tiny bonuses and penalties you saw in lesson 5 (+0.05 for all-low, -0.1 per medium, -0.5 per high, etc.). In a simplified version, rewards are clipped to 0–1 so one outlier can't dominate.

The key trick: don't learn from the raw reward. Learn from how much better you were than your own group average. That's the advantage:
$$\hat{A}_{i,t}=\frac{\text{clip}(R_i,0,1)-\text{mean}(R)}{\text{std}(R)}$$
Above average → positive advantage (do more of this). Below average → negative (do less). Dividing by std keeps updates stable even when rewards are spread out.

Then the model compares its new self πθ to the old self with a ratio for each token t:

$$r_{i,t}(\theta)=\frac{\pi_{\theta}(\tau_{i,t}\mid \dots)}{\pi_{\text{old}}(\tau_{i,t}\mid \dots)}\cdot \mathbf{1}_{\tau_{i,t}}$$

r says "how much more likely is this token now?" The indicator 1LLM token is crucial: it's 1 only for tokens the agent generated, 0 for tool outputs and user replies. We only teach the agent to write better, not to hallucinate tool results.

Finally, GRPO's objective (borrowed from DAPO with Clip-Higher and token-level loss) averages over all tokens:

$$\mathcal{J}=\mathbb{E}\left[\frac{1}{\sum_i|\tau_i|}\sum_i\sum_t \min\big(r_{i,t}\hat{A}_{i,t},\; \text{clip}(r_{i,t},1-\varepsilon,1+\varepsilon)\hat{A}_{i,t}\big)\right]$$

Clipping to 1 ± ε is a safety rail. If r tries to jump too far (the model changing too fast), we cap it. That prevents one lucky group from wrecking training.

In practice the paper used Seed-OSS-36B-Instruct as the base, trained in Verl with learning-rate 1e-6, batch 64, group 8, for 200 steps, with max lengths 32K for function-localization / 65K for full SWE / 41K for web search.

007What changes~9 min

What the Agent Learns to Do Differently

So far we trained an agent to juggle productivity, proactivity and personalization. Did it actually learn to behave differently? The paper looks for three signatures during the 200 training steps, and you can check each one yourself.

First, strategic asking. A good teammate does not ask the same amount everywhere. On vague prompts, the PPP agent on SWE-Func-Loc went from asking in about 50% of tasks to 100% — it learned that vagueness needs clarification. On BrowseComp-Plus vague prompts it went 51% → 85%. But on precise prompts it stayed low, around 5–15%. That is the “minimally disruptive” rule: ask only when missing info really blocks you. Task scores grew more on vague prompts, and the PPP agent even passed GPT-5 there, where guessing hurts most.

Second, quality over quantity. Total questions did grow, but only from about 0.5 to 1.2 per session, and almost all of the growth was low-effort questions — those answerable straight from the hidden precise prompt, like “which file is the bug in?” Medium-effort questions — “I don’t know” traps outside the prompt — rose early then fell again. High-effort questions, which force you to run code or read docs, stayed near zero the whole time. In plain words: the agent first learned to ask, then learned to ask well.

Why the bump? Early in training, any question helps task reward. Later the proactivity reward kicks in: +0.05 if all questions were low-effort, but −0.1 for each medium and −0.5 for each high. Spamming stops paying.

Remove that penalty and the shape flips. The ablation “without Proact” keeps adding medium and high-effort questions through step 200. It becomes what the authors call “lazy” — pushing work onto you instead of doing its own search.

Third, generalization. The same trained model was tested with different user simulators: GPT-5-Nano (56.26 productivity / 75.55 proactivity / 89.26 personalization), GPT-5 (58.06 / 89.45 / 83.25), GPT-4.1 (56.65 / 86.90 / 95.88) and others. Scores moved only a little — evidence it did not memorize one simulator’s style. On the 8 unseen preferences — like json, capital, or lang_ita — PPP stayed around 0.9 personalization, while the ablation without personalization collapsed from about 1.0 to 0.3 on the JSON preference after ~100 steps.

Even on a harder task it had not been trained for, SWE-Full (actually editing and testing code, not just locating functions), the SWE-Func-Loc model transferred: success 0.29 → about 0.36 under vague prompts, with average asks jumping tenfold from 0.10 to 1.8. Importantly, the low-effort share was even higher than before, and the increase-then-decrease pattern for medium/high persisted. It was not just asking more, it was still asking better.

008The payoff~10 min

Does It Work With Real People?

An AI can look brilliant on a benchmark and still be a bad teammate. The paper finally asks: do the lab gains hold up when the "user" is a real person with opinions, not a simulator?

First, the simulated results — all on tricky vague prompts, averaged over 20 different user styles (12 the model saw in training, 8 it never saw). Think of three report cards: did it finish the task (productivity), did it ask efficiently (proactivity), and did it ask the way you wanted (personalization).

Across both coding (SWE-Bench) and research (BrowseComp-Plus), the PPP-trained agent averaged 62.04 out of 100. Its starting point, Seed-OSS-36B, got 45.32. GPT-5 — a much bigger frontier model — got only 40.40 on these vague prompts. That's a +16.7-point lead for PPP.

Zoom in on coding: productivity 56.26 vs 38.59 (+17.7), proactivity 75.55 vs 43.70 (+31.9), personalization 89.26 vs 69.07 (+20.2). GPT-5 had strong productivity (55.83) but terrible personalization (12.96) — it solved, but not how people asked. Remove any one reward and that dimension collapses: without personalization reward, personalization falls to 47.25; training on productivity alone drops it to 48.21.

Key insight: frontier models trade off. GPT-4.1 actually beat GPT-5 on personalization (79.77 vs 71.36 on BrowseComp), and PPP's power is balance — slightly lower peaks than single-objective ablations, but higher on the task that matters.

But simulators are not humans. So the authors ran a live study: 33 programmers on Prolific, each given a real SWE-Bench bug and a random anonymized agent (GPT-5, Seed, or PPP) to chat with. Total: 300 sessions (100 bugs × 3 models). Afterward they rated overall satisfaction 1–5 and answered 9 detailed questions.

Overall: PPP 3.75, Seed 3.45, GPT-5 3.79. Basically tied with GPT-5 and clearly better than its own base. Where did that come from? Not raw solving — PPP fixed the bug 71% of the time vs Seed 70% vs GPT-5 85% (expected — PPP was only trained on finding the right function, not full edits, and is 36B vs GPT-5).

It came from collaboration. PPP asked in 98% of sessions vs about 35% for both baselines. 79% said that amount felt "about right" (vs "asked too little" for baselines), and PPP won on flow and helpfulness. Preference following? 67.7% said "Yes, it followed my preference" — higher than both baselines.

The limit — sim-to-real gap: simulators count a question as low-effort if the answer is in the hidden precise prompt. Real humans also felt more high-effort with PPP — some questions were generic, repeated, or needed outside digging. More asking helps, but only if questions stay targeted. That's why the -0.5 penalty for high-effort exists.

Takeaway: interaction is not optional — without trained asking, vague prompts cost ~20 F1 points and base models can't recover. PPP recovers it, generalizes to unseen styles and tasks, and humans feel the difference.

ABCWord bank

Word bank.

LLM Agent

An AI program that can think step-by-step and call tools — like searching code, running tests, or using ask_user to talk to you — over multiple turns to finish a task.

Prompt Vaguenization

In this paper: taking a precise, self-contained instruction (avg 193.8 words on SWE-Bench) and rewriting it to keep at most 1 key detail, generalize the rest and make it very short and fuzzy (avg 11.4 words). Creates an information gap.

User Simulator (UserVille)

An LLM that pretends to be a user. It holds the hidden precise prompt, answers the agent's questions, and later judges effort and preference following. Configured with 20 different preferences.

PPP Dimensions

Productivity = did the task succeed (F1 on function localization, EM on BrowseComp-Plus, unit tests on SWE-Full). Proactivity = was asking efficient (low effort). Personalization = did it follow your stated style. Together PPP.

User Effort (Proactivity)

Who answers effort. Low-effort: answer is in the hidden precise prompt. Medium-effort: outside precise prompt, user would say 'I don't know' after thinking. High-effort: needs outside work like checking docs/codebase. Session = max over turns; also high if wrong answer without asking.

Personalization Score

Whether the agent obeyed a preference (e.g., no_ask, answer_more,capital, json, joke). 6 prefs use hard rules (count/position), 14 use LLM-as-judge with a rubric. Score = 1 if follow, 0 if not, counted only when agent asked ≥1 question.

Composite Reward

Training signal split into three: R = R_Prod + R_Proact + R_Pers. R_Proact = +0.05 if all low-effort, -0.1 per medium, -0.5 per high. R_Pers = +0.05 if follow, plus negative penalty per violation from Table 7. R_Prod = 1 if task correct else 0.

GRPO (Group Relative Policy Optimization)

Reinforcement Learning method used. For one prompt, sample G=8 trajectories, then reward the better-than-average ones and discourage worse ones in the group. Uses advantage Â = (clip(R,0,1)-mean)/std and a clipped importance ratio r(θ).

Advantage

How good one try was compared to the other 7 tries for the same prompt. Positive if above group mean, negative if below. The model is updated using this, not the raw reward.

Reward Hacking

When an agent finds a cheap trick to get reward, e.g., asking many low-quality questions to game task reward. Paper prevents this with -0.1/-0.5 penalties and shows w/o Proact ablation spams medium/high questions.

Sim-to-Real Transfer

Training with simulated users but testing with real humans. Paper's user study: 33 programmers, 300 tasks (100 SWE tasks × 3 models), PPP 98% ask rate vs 35% baselines, rated 'about right' 79% of time.

001Why short demos fail~6 min

From answering questions to finishing projects

Imagine two AI helpers. You ask both: “write a command to list files.” Easy — one line, done. Now ask: “Over the next 12 hours, explore our messy company drive, figure out why payroll is wrong for 20 people, fix the code, check it works, and hand in a report.” That is not a question. That is a project.

The paper calls this difference short vs long-horizon work in the terminal. The terminal is that black text window where you type commands to control files, code, data and tools — all in one workspace. A terminal agent does not just chat; it types commands, reads what the computer prints back, tries again, and learns from feedback.

A short trajectory is a recording of that loop for just a few turns — say 5 actions. It can teach an operation: how to run a test, call a tool. A long trajectory is 50+ turns. In the paper’s real training data the average is 52.8 turns, and the 90th percentile is 98 turns — meaning 90% of trajectories have 98 or fewer turns and 10% are even longer. That length is needed to capture how humans actually finish projects: collect evidence, use it to make a judgment, change the plan when something breaks, and turn half-done results into a final delivery.

💡 Key gap the paper fixes: making a task look more complex does not automatically make the training data better.

Why? Because during task creation we might accidentally give the agent the answer. Example from the paper: we ask it to “implement a calibration,” but the starting environment already contains a tool that does the calibration for it. The agent just clicks it and passes. No exploration, no debugging, no verification was needed. On paper the task had many steps, but in practice the agent could skip them.

TerminalHorizon is a fully automatic “data factory” to prevent that. Its goal is to build practice worlds where those long behaviours must happen and link together across stages toward one goal — exploring, revising strategy, and verifying — not just demonstrating single commands.

In the lab below, see this trap for yourself. Make the task longer and watch what really counts as work. Try with shortcuts left in the environment vs with shortcuts removed — only the second way forces the agent to do the sustained work the paper is after.

002How to package a job for an AI~6 min

What's inside a terminal task?

Think of a school project packed into a folder you hand to an AI. The folder has to contain everything: what to do, where to start, an example answer, and how you'll grade it. If any piece is missing or unfair, the practice is useless.

The paper gives that folder a name and a formula. A terminal task is a package of five parts:

$$T = (I, E, S, V, M)\qquad \mathcal{P}(T) = (I, E)$$

Each letter is plain English:

  • I — Instruction: the public goal. For example, "reconcile payroll deductions from payroll.csv using rules.txt."
  • E — Environment: the starting workspace — files, data, code tools, and what happens when you run a command.
  • S — Solution: one reference way to solve it. The agent never sees this; it's just an example for the builders.
  • V — Verifier: the private grader — automatic tests that score the final files and states.
  • M — Machine config: limits like time, memory, and which sandbox to run in.

The second part says the agent only gets P(T) = (I, E) — just the instruction and the starting environment. No peeking at the example answer or the hidden tests. That split is what makes training automatic: the AI works from what a human would see.

Why separate public and private? If the AI could read S or V, it could copy the answer or memorize the test. Hiding them forces real problem-solving. The AI must explore E, try commands, and learn from what comes back.

But hiding creates a fairness problem. What if the hidden grader checks something the student could never have known? The paper forbids that with a contract:

$$\mathcal{C}_{sem}(V) \subseteq Sem(I, \mathcal{O}_{pub}(E))$$

In words: every requirement V checks — C_{sem}(V) — must be inside the meaning of the instruction plus what you can discover in the starting environment — Sem(I, O_{pub}(E)). Test data can stay private, but you can't invent a new rule at grading time. If I says "fix payroll using rules.txt" and E has no bonus file, V cannot secretly demand a bonus spreadsheet.

This matters because TerminalHorizon builds 1,535 tasks automatically. Without this rule, many auto-made tasks would be unlearnable. The inspector below lets you break and fix this exact rule.

Finally, the paper writes how a task actually runs, turn by turn:

$$a_t \sim \pi(\cdot \mid I, h_t), \qquad (s_{t+1}, o_{t+1}) \sim P_E(\cdot \mid s_t, a_t)$$

At step t, the agent picks an action a_t — like cat rules.txt — based on the instruction and the history h_t of everything seen so far. The environment P_E then moves to a new state s_{t+1} and shows a new observation o_{t+1} — the file contents, an error, or test output. That loop is what produces a long trajectory, one action-observation pair at a time.

For the curious — what the symbols hide
The history is h_t = (o_0, a_0, ..., o_t). π is the agent's policy (how it chooses). P_E is the world dynamics — filesystem changes, program outputs. The verifier later scores only s_{H}, the final state.

003What good experience looks like~7 min

The 27 habits of a great problem-solver

Think of a great cook. They don't just know single moves like "chop" or "stir." They have habits: taste as they go, trace why a sauce split, split a big dinner into small dishes, double-check with a second thermometer, and change the whole plan when the oven runs hot. An AI agent needs the same.

TerminalHorizon gives names to 27 of those habits — called agentic behavioral patterns — and groups them into 5 families:

🔍

1. Information exploration & judgment

Search with purpose and connect clues. Example: relational tracing — follow call, data-flow, or identity links to find where to intervene. Like following a recipe's footnotes to the source.

🩺

2. Diagnosis & correction

Find and fix what's broken. Example: compare a working vs failing path to narrow the bug, or test one hypothesis and revise it.

🔨

3. Construction & progression

Build step by step. Example: subproblem decomposition & integration — split the goal, solve parts, combine results. Or dependency-driven progression — lay prerequisites that later work actually uses.

✅

4. Verification & assurance

Make sure it really works. Not one check, but many: compare to an expected value, try a different method, re-run for stability, or re-check under new conditions. Plus measurement–comparison–tuning — measure before and after a change and keep only what improves.

🧭

5. Strategy & coordination

Steer the whole journey. Example: evidence-driven strategy revision — drop your current approach when new evidence says it's wrong. Handle coupled objects, background jobs, and changing conditions.

Why name them? Because "long" alone doesn't mean "good." The paper measured what good looks like: its trajectories average 52.8 turns, but more importantly the median longest feedback chain is 25 turns — that's 25 actions in a row where each result informs the next. And each trajectory shows on average 8.6 core patterns working together.

Key insight: One pattern can stretch across many episodes. In the paper's examples, a log line found in step 2 can redirect your plan in step 12, and a verification failure at the end can send you back to re-do step 3. The value is in how patterns connect — not just how many turns you have.

A short demo might show "fix route → test → done." A long-horizon trace shows something richer: distinguish two paths, fix one, discover a missing identity from logs, fix that, hit a crash, change reading logic, then re-verify with multiple checks including the failing case. Exploration, diagnosis, building, and checking aren't separate stages — they support each other.

004Stage 1 engine~8 min

Letting a stranger test your task

Imagine you built an escape room. You know every secret door because you built it. If you test it yourself, you'll breeze through. You won't notice that you left the key taped to the wall. To really test it, you need a stranger who has never seen your notes.

That's the core trick behind Stage 1 of TerminalHorizon. Building a hard task is not enough — the environment you built might already do the hard work for the agent. Your job is to find that leak and rebuild.

🔄

Inner loop

Fix one task: build → let stranger try → diagnose leak → rebuild. Repeat until the stranger must do the real work.

🗺️

Outer loop

Pick the next task: look at all finished tasks and the leaks you found, then choose new professional work that covers missing habits.

The outer loop is run by a Planner Agent. It looks at the tasks you already accepted, Db, and all the feedback records, Fb, and plans the next batch of research briefs:

$$ \mathcal{Q}_{b}=\operatorname{Plan}(\mathcal{D}_{b},\mathcal{F}_{b}; n_{b}) $$

In plain words: Qb is the set of new topics to investigate, nb is how many slots you have. Each brief says what real-world work to study, what skills aren't covered yet, and which sources to read.

A Deep Research Agent then reads docs, code repos, and issue reports to turn a brief into a task seed z — a draft goal plus the real evidence an agent would need to explore. A Construction Agent builds a candidate package T=(I,E,S,V,M) around that seed. Remember from last lesson: only I (instruction) and E (environment) are public, and the verifier V must stay discoverable from them.

Now the key step: an Independent Challenger who never saw the seed, the reference solution, or the private tests tries the task using only what the agent would see, P(T). It produces a trajectory τr (the full turn-by-turn record) and a score ρr. A reviewer Asyn then diagnoses what happened:

$$ \tau_{r} \sim \operatorname{Rollout}(\pi_{B}; \mathcal{P}(T_{r})), \quad d_{r}=\mathcal{A}_{\mathrm{syn}}(T_{r},\tau_{r},\rho_{r}) $$

Here πB is just the challenger's way of acting, and dr is the diagnosis: did information leak? Did the agent pass by taking a shortcut? Was the intended exploration actually needed?

A passing run can still be bad training data. If your radio-calibration task ships with a tool called mscal solve-bandpass that already does the math and writes the right file, the challenger can pass in 3 clicks without ever implementing calibration. It looks successful, but the trajectory teaches almost nothing.

Horizon Gap Analysis compares the seed's intended work with what the challenger actually did, and traces the missing work to a file, tool, or relationship you supplied. Then Reconstruction rebuilds the task while keeping the same goal:

$$ T_{r+1}=\operatorname{Refine}(T_{r}; z, \tau_{r}, d_{r}) $$

In the radio example, the fix removed the fitting routines but kept inspection, applying calibration, and residual feedback, and made public that the two spectral windows vary differently over time. The next challenger now had to write the fitting code, see high residuals, revise its model, and check holdout data — a 15+ step chain instead of 3.

The inner loop repeats: run again, check again. When it finally passes with real work preserved, the task is accepted. Then the batch updates:

$$ \mathcal{D}_{b+1}=\mathcal{D}_{b}\cup\mathcal{A}_{b}, \quad \mathcal{F}_{b+1}=\mathcal{F}_{b}\cup\Delta\mathcal{F}_{b} $$

Accepted tasks Ab join the collection, and all the new feedback ΔFb — what leaked, what was fixed, how many rounds it took — guides the next batch. In the paper this wasn't rare: the RabbitMQ recovery task needed 5 rounds to force real application-level retry work, and a family benefits task needed 4.

005Stage 2 engine~7 min

Same goal, harder journey

An accepted task is not the finish line — it's the starting point. Stage 2 of TerminalHorizon asks: can we make the same goal require a harder journey, so the agent's habits of exploring, fixing, and verifying have to stretch across more stages?

Think of a photo-library job. Goal: rebuild a curated library after a rescan. Instead of inventing a whole new topic, Stage 2 keeps that goal and adds a twist that the old solution can't handle. That's Progressive Horizon Expansion. In symbols the paper writes it as:

$$\tilde{T}^{(g+1)} = \operatorname{Expand}\left(T^{(g)};\, \delta^{(g)}\right)$$

Read it as: take the prior task T(g) (generation g), apply a proposal δ(g) describing what's new, and you get a candidate child task T̃(g+1). A child is only accepted if the prior reference solution S does not already satisfy the new verifier — otherwise you haven't added real work.

🧩

4 ways to deepen

Broader roles: reuse old artifacts for a related duty.
Deeper mechanisms: expose a simplified dependency.
Richer evidence: add records that must be cross-checked.
Method upgrade: force a redesign of the old approach.

🔗

3 ways to link stages

Evidence-dependent: later choice needs earlier findings.
Action → feedback: earlier tool output changes next fix.
Instance variation: objects change each run — inspect and adapt.

Two real lineages from the paper show this. Photo-library Branch A starts with a one-way import. G1 becomes a two-way sync with a concurrent rating conflict (5 → 4 vs 3) that must be flagged by policy. G2 adds retirement/restoration vs later edits. G3 splits file groups and switches the primary rendition — files must be re-identified by digest before curation.

Branch B takes the same prior task a different way: infer photo identity from metadata first, then merge curation into an independently edited destination, then handle transformed bytes that still share an identifier.

The hotel scheduling lineage does it with time. G1 adds attendee travel times between venues. G2 closes Harbor Hall — lunch moves to the Ballroom, which collides with the plenary, which moves to Seaview: three moves for one closure, committed atomically. G3 makes equipment concrete: a mobile display needs 15 min teardown + 20 min transfer + 20 min install, so Workshop A must move to Oak and slip to 17:30. Each generation's new grading still obeys the verifier contract from Lesson 2 — only what the instruction and visible environment reveal.

Key insight: longer is only useful when later work depends on earlier work. Stage 2 designs that dependency on purpose, and blocks expansions the old solution could already pass.

006What we built~6 min

1,535 worlds for an agent to practice in

Imagine training an AI like training a scientist. You could give it 1,535 different labs to practice in — some about computer chips, some about stars, some about farm records or hospital schedules. In each lab, it must explore, build, fail, check its work, and finally deliver something real. That's what the authors built: not 1,535 exam questions, but 1,535 fully runnable worlds where an agent can type commands, see results, and learn.

Together those worlds produced TerminalHorizon-3K: 1,535 environments and 2,852 trajectories. How? For each environment, they asked a strong teacher model (DeepSeek-V4-Pro-0813) to try twice inside the same harness that runs the tests, Terminus2. That's $1{,}535 \times 2 = 3{,}070$ attempts. After filtering, $2{,}852$ were kept for training — about 93% — but kept for a careful reason we'll see below.

Big numbers that matter: mean 52.8 turns per trajectory, and 90% are shorter than 98 turns (P90 = 98). The median longest chain of linked feedback — where each tool output actually guides the next action — is 25 turns. That's not just "more commands"; it's a sustained conversation with the computer. The authors also sampled 300 tasks from each of several other synthesis methods under the same teacher and found theirs substantially longer. Each trajectory also averages 8.6 core behavioral patterns out of the 27 defined earlier.

Diversity matters too. The terminal is just the keyboard — the jobs cover 25 professional domains, including chips, physics, astronomy, education, agriculture, healthcare, finance and more (Figure 14). A payroll-reconciliation task and a radio-telescope calibration both happen through the same text interface, but they bring different files, rules, and ways to check success. That helps the trained agent transfer beyond coding.

How did a fully automatic factory stay clean? Two checks. First, process-based filtering — not "did it pass?" A reviewer model (gpt-5.6-luna) read every full trace and kept it only if it showed trajectory validity (coherent, traceable actions, no leaked private answers), environment-grounded progress (decisions follow file contents, logs, errors), and multi-turn training value (connected exploration, fixing, and checking). A failed run that diagnoses honestly can be kept; a lucky shortcut is dropped.

How they proved no cheating? Decontamination vs 3,251 evaluation items across 12 benchmarks (Terminal-Bench, AutomationBench, VitaBench, τ2-bench, MATH-500, GSM8K, AIME, KOR-Bench). No exact 13- or 14-word copy was found. The closest 5-word overlap was tiny ($J_5 < 0.006$). From short math overlaps they picked 190 suspicious pairs for human-style review. Result: 0 contaminated — so all 1,535 tasks were retained.

In short: automatic doesn't mean sloppy. The engine created breadth (25 domains), depth (52.8 turns, 25-step feedback chains, 8.6 patterns), and cleanliness (3 quality filters + 0 contamination).

007Does it work?~7 min

Small data, big jump — and reasoning stays

Imagine two students studying for a marathon exam. One memorizes 32,000 flashcards. The other runs just 3,000 full practice exams — exploring, making mistakes, fixing them, and finishing the paper. Who learns more? The paper tests exactly this trade-off.

The practice-exam student is TerminalHorizon-27B. It starts from the strong open model Qwen3.5-27B and gets extra training by copying good long trajectories — this is supervised fine-tuning (SFT). In simplified form: show the model thousands of full "see, type, check, revise" runs and train it to imitate them. The recipe was tiny by modern standards: 3 rounds over the data, learning rate 1×10⁻⁵ with a gentle cosine cool-down, context up to 262,144 tokens, on 144 GPUs.

Even with that little data, the jump on coding exams was large. On the industry standard Terminal-Bench — real terminal jobs scored by a hidden checker — scores went: TB 1.0 from 46.3% to 55.0% (+8.7), TB 2.0 from 41.6% to 55.8% (+14.2), and TB 2.1 from 46.82% to 60.67% (+13.85). The key comparison: Terminal-Universe-27B used the same base model and same harness but 32,000 trajectories and reached 52.8% on TB 2.0. TerminalHorizon beat it with fewer than one-tenth as many — about 3k vs 32k. Longer, denser experience mattered more than just more examples.

Data efficiency takeaway: quality of the practice matters. One 53-turn trajectory that links exploration → diagnosis → revision → verification teaches more than ten short demos that each show a single command.

The gains didn't stay in the terminal. On real-world productivity tasks the same pattern repeated: AutomationBench pass rate 5.5% → 17.2% (+11.7) and partial credit 26.4% → 49.7% (+23.3), VitaBench cross-domain 20.5% → 31.8% (+11.3), and τ²-bench Airline 79.0 → 84.5 and Retail 84.9 → 87.5. Agents that learned to follow feedback in the terminal got better at following customer instructions too.

A common worry: does training on terminal work make a model worse at math? Here it did the opposite. All five general-reasoning exams were preserved and rose a bit: MATH-500 96.9 → 98.9, GSM8K 96.3 → 97.3, AIME 2024 93.3 → 96.7, AIME 2025 86.7 → 93.3 (+6.6), and KOR-Bench Cipher 90.1 → 91.2.

It wasn't a fluke of one size. On TB 2.1 every size jumped double-digits: 27B +13.85%, 35B-A3B +13.11%, 122B-A10B +14.98%. Growing the dataset from 1k to ~3k trajectories kept improving with no sign of flattening. And who teaches matters: the DeepSeek-V4-Pro teacher averaged 53.5 turns and a 30.3-turn feedback chain with 50% task success, vs GLM-5.2's 46.1 turns, 19.2 chain, 44% — longer linked work came with better learning.

00812 hours alone~8 min

Why the patient agent wins

Imagine you have 12 hours to finish a research project alone in a lab. No teacher will peek over your shoulder. You can test anything — but no one tells you if your final answer is actually right until the end.

This is the RSI-Exam in the paper: 4 different jobs, each with a 12-hour budget, an 8GB computer, and a hidden grader the agent never sees during work. The question is not "can you write code?" but "can you keep improving after your first solution, and save the best version?"

The paper's showpiece is multi-view point-cloud fusion. You get noisy 3D dots from several camera views. View 1 sets the coordinates. The other views are slightly rotated and shifted, and many dots are unreliable. You must line them up, throw out bad dots, and output a clean 3D scene. The public check only verifies your file format — it does not tell you if the scene is correct. The real score is the F-score over 9 unseen scenes: how many real surfaces you covered, and how many fake dots you avoided.

The trap: proxy vs true goal. Base model Qwen3.5-27B found a shortcut. If you just copy points close to View 1, your proxy score — agreement with View 1 — looks amazing: 0.8994 on average, and 1.0 at the 0.05 distance threshold. The agent wrote "excellent, ready to submit" and stopped after 12.1 minutes. But hidden score? Only 48.04 (on a 0–100 scale) and a normalized score of 21.93. It looked perfect by its own yardstick and missed the rest of the scene.

TerminalHorizon-27B did something different. It also tried the near-reference trick and got proxy ~0.989 — but then it asked: "wait, who contributed these points?" It ran a leave-one-view-out check: hide one view, see if the rest can still rebuild it. Coverage collapsed. Evidence said the metric was rewarding copying, not reconstructing.

So it changed its method and its way of measuring. It used distance-filtered rigid alignment, then 2 rounds of global refinement against all other views, then kept high-confidence points from the merged cloud — not just near View 1. Hidden mean F rose 48.04 → 77.68 and the paper's normalized score rose 21.93 → 48.96 (+27.03).

Three other 12-hour jobs show the same pattern (normalized 0–100, Table 5):

  • Robot routing + macros (warehouse with balls): Horizon kept compressed button count 281.11; base found 286 but later deleted compression and submitted 466.35. Scores 14.63 → 39.72 (+25.09). Horizon used the full 12h, base quit at 11.42h.
  • Tidal friction inversion (find seabed friction from 6 basins, test on 8 hidden): Horizon added depth features, Huber loss, and refit after dropping 2 bad gauges. RMSE 0.021873 → 0.009386 (~57% drop). Scores 27.41 → 48.15 (+20.74). Base quit at 1.12h.
  • 2048 strategy (16 hidden games): Both added expectimax search. Horizon added merge reward + selective caching and reverted a later tweak that looked good on a subset but hurt the full 8 public seeds (59,509 → 65,084). Hidden mean 23,183 → 38,626, scores 37.54 → 45.25. Base quit at 1.28h after calling its work "complete."
Zoom in: why "longer" alone is not the win. Figure 7 shows base flatlines early, Horizon dips then climbs. Progress came from three linked habits the paper trained: continue beyond the first solution, revise the experiment that judges you, and keep a verified best-so-far through final delivery. Without those links, extra hours just repeat mistakes.

009What we taught~1 min

Take the exam

You've built the whole factory — from packaging a fair task to catching leaks to growing harder journeys. This last stop locks in the two ideas that every exam question comes back to.

First, long-horizon does not mean "more turns." A worksheet can be 50 short problems. A science project is 50 linked steps toward one goal: you explore for clues, make a judgment, build something, get feedback that it's wrong, change your strategy, and prove the fix. The TerminalHorizon paper called these reusable habits agentic behavioral patterns — 27 of them in 5 families, like relational tracing (follow links between files to find where to fix) or measurement-comparison-tuning (measure before and after to decide keep or revert). Its best data packed an average of 8.6 patterns into one connected story, with a median feedback chain of 25 steps where each result guides the next. That's the gap between typing a lot and learning to finish.

Second, those patterns only appear if the environment preserves the real work. That's why two fixes mattered more than any prompt trick.

1) Challenge-guided reconstruction finds leaks. Send in a stranger — the Independent Challenger who didn't help build the task. If it passes in 3 turns by calling a pre-installed solve-bandpass tool, you found a leak: the environment solved the hard part for the agent. You rebuild so the real analysis and verification are left to do.
2) Progressive expansion extends dependencies. Once a task is good, keep the same goal but add new requirements that depend on earlier results — so the old solution alone can't pass. That forces exploration to continue across stages instead of restarting.

When both work, you get what the paper measured and then proved: not just 52.8 turns on average (P90 = 98), but training data dense enough that ~3,000 examples beat 32,000 short ones on Terminal-Bench, and a patient agent that questions its own proxy score can win a 12-hour research race by keeping the best verified deliverable.

010~0 min

You've followed a full factory for teaching AI to do real work — not just answer a question, but carry a project across hours. This last stop is a chance to step back, connect the pieces, and see what you now own.

It started with a simple gap. Short demos can show how to run a command, but they don't show how to finish a job: gathering clues, trying something, getting feedback, changing your plan, and turning half-done results into something you can ship. Complex tasks alone don't fix that — if the starting files already contain the answer, the agent can shortcut and never learn the habits.

The big idea behind TerminalHorizon is not "more turns." It's preserving the real work and linking it across stages so one discovery can shape a decision many steps later. Longer is only valuable when it's connected.

To do that, the paper built a two-stage engine. First, build and let a stranger test it: a Planner picks what to try next, a Researcher grounds it in real professional work, a Builder packages it, and an Independent Challenger — who never saw the build notes — tries to solve it. If the Challenger breezes through using a pre-installed solver, that's a red flag. Gap analysis points to the leak, and the Builder removes it. That loop ran up to five times in cases like radio calibration and RabbitMQ recovery.

Then, grow the same goal deeper. Once a task is solid, it's not done — it's a parent. The engine adds new requirements that the old solution can't satisfy and forces the new work to depend on earlier evidence, actions, and results. Photo libraries split and re-merge, hotel venues close and force re-planning. Each generation still obeys the fairness rule you learned: the hidden grader checks only what the public instructions and environment make discoverable.

From that engine came TerminalHorizon-3K — 1,535 environments, 2,852 trajectories averaging 52.8 turns with a median feedback chain of 25, spanning 25 domains from chips to healthcare, carefully filtered and decontaminated. Training just that ~3k of long-horizon experience lifted a 27-billion-parameter model by double digits on terminal and real-world productivity tasks, while keeping math and reasoning strong — and doing it with less than a tenth of the data some other methods needed.

And in the 12-hour tests, the difference was patience: the base model nailed a proxy score and quit; the Horizon model questioned that score, diagnosed coverage, reverted bad ideas, and shipped the verified best. That's the habit the data teaches.

ABCWord bank

Word bank.

Terminal

A text-based workspace where you type commands to control files, code, tools and data. Like the black screen hackers use in movies — but it's just a powerful way to get work done.

AI Agent

An AI that can take actions on its own in a digital environment — not just answer, but explore files, run code, see results, and try again.

Trajectory

One full record of an agent trying a task: what it saw, what it typed, and what the computer showed back, turn after turn.

Task Environment

Everything the agent can interact with for a task: files, programs, data, and rules for what counts as success.

Verifier (private grader)

A hidden automatic checker that scores whether the agent really solved the task — separate from what the agent can see.

Long-horizon task

A task that takes many linked steps over time, where you must use earlier results to decide what to do next. Short tasks are just a few commands.

Agentic behavioral pattern

A reusable problem-solving habit agents show, like 'follow links to find where to fix' or 'change plan when new evidence arrives'. The paper defines 27 of them in 5 families.

Supervised fine-tuning (SFT)

Training by showing the model many good examples of full trajectories and asking it to imitate them. SFT = Supervised Fine-Tuning.

Benchmark

A fixed set of tasks used to measure progress fairly, like an exam everyone takes.

Decontamination

Checking that none of the training tasks were accidentally copied from the exam tasks, so gains aren't just memorization.

RSI-Exam

A test where an agent gets 12 hours to keep experimenting, improving its own method, and submitting a final deliverable — Recursive Self-Improvement Exam.

Public information P(T)

The set of things the agent is allowed to see (instruction + environment). Hidden things like the reference solution and private tests are not included.

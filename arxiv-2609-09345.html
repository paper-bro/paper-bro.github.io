001Lesson 1~7 min

The Internet's Secret Handshake

When you open a website, your computer and the server do a quick secret handshake. Your computer picks a random 32-bit number called the Initial Sequence Number, or ISN — think of it as a starting page number for this conversation. It sends: “Hi, I’m starting at page n.” The server must reply with ack = n+1, meaning “got it, I expect page n+1 next.” If a fake reply gets that number wrong, your computer just throws it away.

DNS, the internet’s phone book, works similarly but quicker. Your computer asks “what’s the address for example.com?” and tags the question with a 16-bit Transaction ID (TXID). The answer only counts if the TXID matches and it comes back to the right temporary UDP source port (about 14 to 16 bits of randomness) and the right addresses. Together that’s like a combination lock with over a million or even billions of combinations.

An off-path attacker is someone who cannot see your traffic at all. They can send packets pretending to be someone else (IP spoofing, which one study found still works in about 14.9% of network prefixes), but they can’t listen in. With only guessing, they should almost always lose — a single wrong TXID or wrong ISN+1 means failure, and there are 65,536 TXIDs or about 4 billion ISNs to try.

So why worry? The paper asks: what if the attacker has a tiny helper already on your device — a normal-looking app with no special permissions, that also can’t see traffic, but can ask the operating system innocent questions? Alone each is off-path, but together they might leak just enough to shrink that combination lock from billions to a few thousand.

That teamwork is the paper’s core idea. A malicious app can watch how the system hands out ports or handles packet filters and quietly tell its far-away partner (called the ARN) what it learned. The partner then does the spoofed guessing, but now with a much smaller range.

This still matters because not everything is encrypted. The paper cites a large study finding 33.74% of Android apps explicitly allow cleartext HTTP, and 2,790 out of 35,000 actually sent HTTP traffic. Those connections can still be hijacked if the secret numbers leak.

In the lab below, try being the off-path attacker yourself. First guess a 32-bit ISN blind, firing hundreds of guesses. Then flip on the insider helper that narrows the range to about 2,000 possibilities — like the Linux attack in the paper — and see how the math flips from impossible to doable.

002Lesson 2~9 min

How Your Computer Picks a Secret Number

Your computer needs to pick a secret starting number every time it opens a new connection. That number is called the ISN — Initial Sequence Number. It's 32 bits long, so there are about 4 billion possibilities. The trick is: it has to look random to outsiders, but it also has to follow rules so old packets don't get mixed up.

🔒

The recipe

Every OS uses a mix of a secret hash + a clock. The secret part stays the same for the same connection. The clock part ticks forward.

⏱️

Why the clock?

Without a clock, two connections with the same addresses could reuse the same ISN. The ticking clock makes sure each new ISN is a little bigger than the last one for about two minutes.

On Linux and Android (kernel 7.0.0-rc6, the version the paper inspected in net/core/secure_seq.c) the formula is:

$$ ISN = H_{k}(4\text{-tuple}) + t \; \mod 2^{32} $$

Here's what each piece means. $H_{k}$ is a keyed hash — think of it as a blender that takes the connection's 4-tuple (your IP, your port, server IP, server port) plus a 128-bit secret key $k$ made when the computer boots, and outputs a fixed pseudo-random number. $t$ is the current time counted in tiny ticks: 64 nanoseconds per tick on Linux/Android, 128 nanoseconds per tick on macOS and iOS (which use the same formula in XNU's tcp_new_isn()). $"\mod 2^{32}"$ just means wrap around after 4,294,967,296, like a clock wrapping from 11 back to 0.

Windows is different inside, but the shape is similar. By reverse-engineering tcpip.sys and the function TcpCreateAndConnectTcbRateLimitComplete, the authors found:

$$ ISN = H_{k}(4\text{-tuple}) + \text{offset} \; \mod 2^{32} $$

There $\text{offset}$ isn't just time — it also depends on recent connection activity and on one of four internal buckets the port lands in. We'll come back to buckets in the lab.

The big insight: for a fixed 4-tuple, the hash part never changes. So if you see one ISN at time $t_1$ and want to guess the next ISN at $t_2$ with the same 4-tuple, the hash cancels out:
$$ ISN_{2} = ISN_{1} + (t_{2}-t_{1}) \; \mod 2^{32} $$
Knowing one sample plus the elapsed ticks lets you predict the next ISN by just adding the time difference.

That collapses the 4-billion search. If an attacker can secretly learn one ISN and its timestamp for a given server (using tricks you'll see in the next lesson), they can estimate a future victim's ISN to within the uncertainty of the timing — often just hundreds or thousands of candidates instead of billions. The paper shows this works because the same server IP and port + same victim port means the same 4-tuple, so the same $H_k$.

In the lab, build the ISN machine yourself: set the secret hash and two times and watch the prediction appear. Then flip the 4-tuple and see the hash jump — your old sample becomes useless. Toggle the Windows mode to see why about 25% of port pairs are "correlative" and give a stable difference.

Go deeper: Windows keeps four ISN buckets. The bucket is picked by a hash of the 4-tuple. Two source ports that fall in the same bucket and are used within less than a millisecond see almost the same bucket state, so their ISN difference $Δ_{p_1,p_2}=ISN(p_1)-ISN(p_2) \mod 2^{32}$ stays almost constant across trials. That's why the Windows attack precomputes $\Delta$ for many pairs.

003Lesson 3~8 min

The Helper Already Inside

One attacker on the internet should not be able to hijack your connection — your numbers are too hard to guess. One shady app on your phone should not either — it is not allowed to peek at other apps' traffic. The scary part is what happens when they team up.

That team is the paper's threat model. Player one is an unprivileged malicious app already on your device. Think of it as a nosy roommate who can use the hallway phone but is not allowed to open your mail. It cannot use raw sockets, it cannot sniff packets, and on modern Android it cannot even read /proc/net/tcp easily. It can only do normal things any app can do: open its own sockets, call bind(), call connect(), ask the system what time it is.

Player two is the Attacker Remote Node (ARN) — a computer far away on the internet. It is off-path, meaning it also cannot see the traffic between you and the real server. But it has one superpower the app lacks: it can send packets that pretend to be from someone else. This is called IP spoofing — writing a fake return address on the envelope.

The two never need to see your real traffic. The app quietly learns a secret piece (like which port you used) and sends it to the ARN over a normal message. The ARN then fires the fake reply at just the right moment.

For this to work the paper makes two everyday assumptions. First, your home router keeps the same port number when it translates your private address to the public internet — a port-preserving NAT, which is the common case. Second, the ARN can guess your public IP (it learns it whenever you contact anything on the internet) and the network actually delivers spoofed packets. That last part still happens a lot: studies cited in the paper found about 14.9% of IPv4 prefixes and 30.5% of networks still allow spoofed traffic through.

With that foothold, the team chases two prizes. For TCP hijacking they need to learn the 4-tuple (your IP, your port, server IP 192.0.2.123, server port 80) plus your secret ISN during the handshake. For DNS cache poisoning they need the UDP 4-tuple plus the stub resolver's UDP source port, then they can brute-force the 16-bit TXID.

Where does the ARN sit? Ideally both attackers are far away. But one classic trick for leaking the ISN uses special IP header fields called LSRR and SSRR — Loose/Strict Source and Record Route — that say "please send this packet via this middle stop first." Those options are old debugging features and most routers now drop them; an early study found only about 8% of routers even supported source routing. To get around that filter, the paper also tests a split layout: a capturing-ARN quietly inside your local network to catch the LSRR-forced SYN and read its ISN, plus an injecting-ARN outside to shoot the spoofed reply. No ARP spoofing or full interception is needed — just that one forced detour.

So: being on the device is not the same as seeing traffic. The OS walls are real, but they leak tiny hints through shared behavior. The lab lets you turn those walls on and off to feel why the pair is stronger than either alone.

Try this in the lab: start with the normal unprivileged app (no raw socket) and spoofing allowed. See how the team can still hijack. Now toggle off bind() or block spoofing — watch the success lights go out. Switch the ARN from outside to local and notice why IP-options attacks need that local helper when routers filter LSRR.

004Lesson 4~10 min

How to Steal a Number You Can't See

Your computer’s secret number, the ISN, lives inside the kernel. A normal app is not allowed to read it — it can’t just open a packet and look. So how does a sneaky app steal it anyway? Think of a locked mailroom that won’t show you the letter, but will let you ask “give me back only the first N bytes” where you get to pick N with a tiny program. If you can make N depend on the secret, the size of what comes back tells you the secret.

That is exactly what the paper does in its preprocessing step. For the target you want to attack — say a web server at 192.0.2.123 on port 80 — the malicious app builds a cheat-sheet ahead of time. For every possible source port p your device might use, it stores: the ISN it saw for the 4-tuple (your IP, p, 192.0.2.123, 80) and the exact time it saw it. Later, when the victim’s real app picks a port, the attacker looks it up and adds the time that has passed to guess the new ISN.

A 4-tuple is just four numbers that name one connection: source IP, source port, destination IP, destination port. For a fixed 4-tuple the secret hash part Hk stays the same, so only time moves the ISN.

How do you fill that table without seeing traffic? The paper shows two tricks.

1. The cBPF length trick (Linux and Android, works for IPv4 and IPv6). cBPF is an old Linux feature that lets an unprivileged app attach a tiny filter to its own socket. The filter can load a byte from the packet at a fixed position — in this case, one byte of the acknowledgement number that mirrors the ISN — and then tell the kernel how many bytes to return. The app never sees the full packet, but it learns the byte value because the kernel obediently truncated the packet to that length. Do this four times with four different offsets, make four HTTP requests, and you have all four bytes = the full 32-bit ISN.

2. The IP options detour (IPv4, cross-platform). IP has optional headers called source routing. One called LSRR lets the sender say “please route this packet via this extra address first.” The malicious app sets this option with setsockopt(..., IP_OPTIONS, ...) when it sends a SYN. If the network allows it — about 8% of routers historically did, and in the paper’s tests the capturing attacker was put on the local network so routers don’t need to allow it — that SYN takes a detour through the attacker’s remote node (ARN). The ARN simply captures the packet and reads the sequence number directly. No filter, no math, just a forced pit stop.

The cost difference is striking. On Linux, building the whole table with cBPF took about 305 seconds and 290 MB of traffic in the paper’s setup; the same table with IP options took only 22 seconds and 2 MB. On Windows, where the attacker must test many port pairs to find “correlative” ones, it ballooned to about 1300 seconds and 1.53 GB. The paper goes further than this lesson and details exactly how each filter is crafted and how LSRR is set, but the core idea is the same: make the system’s own allowed operations leak.

Try it below: pick which byte to leak with the cBPF filter and watch the returned length reveal it. After four clicks you’ve rebuilt the number. Then flip on the LSRR detour and see why the IP-options route makes the same theft instant.

005Lesson 5~10 min

Finding the Right Door

To guess the victim's secret number you need two things: which door the connection used — its source port — and the exact moment the door opened. Without the right port you look at the wrong entry in your stolen table; without the right time your time math is off.

On Linux, Android, Windows, macOS and iOS the attacker can't just ask "what port did the victim pick?" The system hides it. The paper tests five ways to find it. Think of each as a different way to check which doors are already locked.

The fastest is to read the system's own guest list. On Linux that's /proc/net/tcp; on Windows it's GetExtendedTcpTable (and GetExtendedUdpTable for DNS). They answer in about 0.04 milliseconds on Linux and 72 microseconds on Windows. Android blocks this list for normal apps, so it needs something sneakier.

That sneakier trick abuses how Linux picks ports. Simplified, for a fixed triple of (your IP, server IP, server port) Linux computes

$$ base\_port = (Table[h_1] + h_2) \bmod R + min\_port $$

where R = 28232 (range 32768 to 60999), Table has 65,536 entries, and the keys that make h_1, h_2 rotate about every 10 seconds. If that base port is free it is used; if not, the kernel tries base+2, then +4, and so on.

After handing out port p it then does Table[h_1] += 2 × r where r is random 1 to 8. That means the next port for the same destination must be one of p+2, p+4, ... p+16. Small increments, very predictable.

If you know the last port was p, block p+2 through p+14 yourself with bind(). The kernel has no choice but to give the next victim p+16. When your own attempt to bind p+16 suddenly fails, you have learned the victim's port — and you timed it.

This is Method 2 in the paper. It takes only 0.006 ms per check — the fastest of all. The paper measured the alternatives on Linux too: trying every port with bind() ("bind-all") takes 46 ms, and asking for any free port with bind(0) and sampling takes 429 ms and needs about L log L tries to be sure.

macOS, iOS and Windows are even simpler: they normally hand out ports sequentially, like ticket numbers. Windows occasionally jumps to a new random start, but over short times you can still guess the next ticket. That's why the paper's preferred method is sequential prediction on macOS (276 microseconds), iOS (222 microseconds) and table monitoring on Windows.

006Lesson 6~10 min

Hijacking the Handshake

The hard part — figuring out the secret number — is done. Now the malicious app and its distant partner have to use it before the real server does. This is a race, and the prize is the handshake itself.

Think of the four stages like a heist movie. Stage 1: make a cheat sheet. The malicious app quietly builds a table: for every source port p it might see, it saves one real ISN and the time it was created for the connection (your IP, p, 192.0.2.123, port 80). Stage 2: watch the door. When you click a link, the app spots which source port you actually got and notes the time almost exactly when your SYN leaves. Stage 3: estimate. Because the hashed part $H_k(\text{4-tuple})$ is the same for that port, the new ISN is roughly the old one plus elapsed time:

$$ ISN_{victim} \approx ISN_{ref} + (t_{victim} - t_{ref}) \mod 2^{32} $$

You don't know the exact instant, so you don't get one number — you get a small window of candidates. The paper measured how small: about 1,600 for Linux, 4,500 for Android, 8,000 for macOS, 6,000 for iOS, and 12,000 for Windows. That's thousands to try instead of 4 billion.

Stage 4: hijack. Your computer already sent its SYN. The attacker waits just a couple milliseconds to be sure it's on the wire, then floods you with fake SYN-ACK packets, each guessing a different acknowledgment number. Remember: a SYN-ACK is only accepted if

$$ ack_{SYN-ACK} = ISN + 1 $$

Wrong guesses make you send a RST and you ignore them — the paper shows you just shrug them off. The first guess with the right $ISN+1$ makes you reply with an ACK and you think the handshake is done. Next the attacker does it again, this time with a fake HTTP response inside a PSH-ACK packet. For data packets TCP is a little more forgiving, so the attacker can even take bigger steps.

The whole thing only works if the fake arrives first. The paper writes this as a simple inequality:
$$ RTT_{victim\leftrightarrow ARN} + T_{brute\_force} < RTT_{victim\leftrightarrow server} $$
On Linux the authors measured $RTT_{victim\leftrightarrow server} \approx 108\text{ ms}$ but $RTT_{victim\leftrightarrow ARN} \approx 5\text{ ms}$, and sending 1,600 SYN-ACKs at ~145,000 packets/sec took only $11\text{ ms}$. $5+11=16 < 108$, so there was plenty of room. Even when the real server is behind a CDN, it isn't always close — one measurement from Israel to a Verizon site on Akamai still took $170\text{ ms}$, leaving the same window open.

Windows needs one extra trick. Its ISNs come from 4 buckets, and ports that fall in the same bucket behave similarly if used within a fraction of a millisecond. The app pre-tries many pairs and keeps the ones where the difference $\Delta_{p1,p2}=ISN(p1)-ISN(p2)$ stays stable — about 25% of pairs are "correlative." At attack time it quickly opens a connection from the correlative $p2$, the ARN captures $ISN_2$, and it estimates $ISN_1 \approx ISN_2 - \Delta_{p1,p2}$. The rest is the same flood-and-win race.

007Lesson 7~9 min

Poisoning the Phone Book

DNS is the internet's phone book. You ask for example.com and a helper on your device — the stub resolver — asks a real DNS server for the address. It then writes the answer in a little cache so the next visit is fast.

That shortcut is dangerous if someone can slip in a fake answer. A fake DNS reply is accepted only if it matches several matching fields exactly: the IP addresses, the UDP 4-tuple (source and destination IPs and ports), and two secrets the resolver picks per query — the UDP source port (about 16 bits of randomness) and the TXID, a 16-bit ID on every query. Guess both right and arrive before the real reply, and the resolver caches your lie.

The paper assumes no extra protection like DNSSEC, DoH, DoT, or DNS cookies — which is still the default for the stub resolvers it attacks.

Think of it as a locked mailbox with two dials: port dial + TXID dial. The unprivileged malicious app can't see the dials, but it can feel which port is in use, leaving only the TXID to brute-force.

Why Linux was easy to poison

Ubuntu's default systemd-resolved uses a record-based cache. That means it saves every record inside a reply separately, even records about names you didn't ask for. Legitimate CNAME chains do this, like a.example CNAME b.example.

An attacker abuses that. The malicious app first asks the resolver to look up a name the attacker controls, like random.attacker.test. The attacker controls that server, so it can simply wait and not answer right away. While the clock is ticking (the paper says the timeout is at least 1 second), the remote attacker floods fake replies for that query that also smuggle in:

$$\text{random.attacker.test CNAME example.com}$$ $$\text{example.com A 192.0.2.66 (attacker)}$$

If one fake reply has the right source port and TXID and beats the delayed real reply, the resolver caches example.com → 192.0.2.66. Future visits to the victim name go to the attacker — even though you never queried it directly. The paper also showed this can overwrite an already-cached good entry.

Why Android and Windows were harder

Android and Windows use a query-based cache: they only cache an answer for the exact name you asked. No extra-record trick. To poison example.com, the app must trigger a query for example.com itself. Now the attacker cannot delay — the real server replies in 50–100 ms.

That leaves a tiny race window:

$$T = \text{RTT}_{\text{victim-resolver}} - \text{RTT}_{\text{victim-ARN}}$$

In the paper's Android test, that was 60 ms minus 14 ms = 46 ms. Inside that window the app must find the resolver's source port (Android picks randomly from 1025–65534, Windows from 49152–65535) and the remote node must blast TXID guesses.

Split your time wisely. If you spend x time scanning ports at rate A, and T-x time sending guesses at rate R:

$$P_{succ}(x)=\frac{A\cdot x}{\text{portRange}} \cdot \frac{R\cdot (T-x)}{65536}$$

Left part is fraction of port space you checked. Right part is fraction of 65,536 TXIDs you tried. Multiply them because you need both right.

The deeper pattern: this is x·(T-x) times constants, a parabola that peaks at x = T/2. The best strategy is to split the window equally between port scanning and TXID guessing. Then
$$P_{succ}=\frac{A\cdot R\cdot T^{2}}{4\cdot \text{portRange}\cdot 65536}$$ Windows has an extra limit: after 5 wrong TXIDs the resolver drops the query, and only one TXID guess can actually be cached per attempt, so each try succeeds with just 1/65536 no matter how many packets you send. macOS and iOS are even stricter: after a single bad reply mDNSResponder switches to TCP for about 10 seconds, which blocks this off-path brute-force entirely.

008Lesson 8~8 min

Did It Work? And How to Fix It

So did the paper's tricks actually work? Yes — and the numbers show why a tiny helper app changes everything.

On Linux the team hijacked TCP almost every time: 97% with the cBPF leak over IPv4 and IPv6 using only about 1,000–1,600 guesses for the 32-bit ISN, and 99% with IP-options routing. The remote attacker was on AWS with a 5 ms round-trip to the victim, while the real server was 108 ms away, so 1,600 fake SYN-ACKs sent in 11 ms easily won the race. Android hit 80–86% with 4,500 guesses, macOS 100% with 8,000, iOS 96% with 6,000, and Windows 87% with 12,000. Without the insider, guessing 4 billion ISNs would never win.

DNS was similar. Linux's system cache could be poisoned in a single round: 97% using fast /proc monitoring (65,000 fake replies in 0.65 seconds), 99% by trying every port, 68% with the slower bind(0) sampling. Windows and Android needed repeated tries because they cache only the exact name you ask for, but still succeeded 100% in the experiments — averaging about 515 seconds on Windows (71,000×5 packets) and 471 seconds on Android (10×8,000 packets) after clearing a 640-entry cache.

Naive vs clever: a naive Android attacker guessing both port and TXID out of 4.23 billion combos gets about 17,000 guesses in the 46 ms window — success chance about 4 in a million. Expected time: roughly 250,000 tries × 0.55 seconds ≈ 38.6 hours. With the leaked port (half the window for port scan, half for TXID) it drops to minutes. Windows naive would spray 16,384 ports per try for ~54 minutes; the paper's method uses just 5 packets per try and averages ~8.5 minutes.

That's why local isolation matters even when an app can't sniff. The fixes the authors proposed don't try to stop spoofing on the internet — they close the leaks inside the device:

  • Show each user only their own connections in /proc/net.
  • Rate-limit bind and connect per user, so an app can't scan ports thousands of times a second.
  • Split ephemeral ports into privileged and unprivileged halves, and make port picking truly random instead of p, p+2, p+4…
  • Make the secret-number formula include who asked:
    $$ISN = H_k(\text{4-tuple}, UID) + t \mod 2^{32}$$
    where UID is the user ID. Two users with the same IPs and ports then get unrelated hashes, so one cannot predict the other's ISN.
  • Clean cBPF output — zero the sequence and acknowledgment numbers before returning data — or block cBPF on TCP for unprivileged apps.
  • Require special permission to use source-routing IP options LSRR/SSRR, which forced SYNs through the attacker.

The vendors listened. The paper was disclosed April 29, 2026: Linux patched both leaks as CVE-2026-53236 (cBPF) and CVE-2026-53249 (IP options); Android inherited the Linux fix; Apple said it is working on restricting source routing; Microsoft and Google acknowledged the reports. The full paper has extra mitigations and a longer discussion — here we've kept the core idea: the internet's secret handshake is only secret if your own device doesn't whisper it.

ABCWord bank

Word bank.

TCP

The internet's reliable delivery system. It numbers every byte and checks replies to keep order.

ISN

Initial Sequence Number. A 32-bit random-looking start number each computer picks when opening a TCP connection.

3-way handshake

The three messages SYN -> SYN-ACK -> ACK that open a TCP connection. Both sides exchange ISNs.

4-tuple

Four values that define one connection: source IP, source port, destination IP, destination port.

UDP

A quick, unreliable transport used by DNS. No handshake, just query and reply.

DNS

The internet's phone book. Translates names like example.com to IP addresses.

stub resolver

Helper program on your device that asks the real DNS server for you and caches answers.

TXID

16-bit ID on each DNS query. Reply must match it to be accepted.

ephemeral port

Temporary port a device picks to send from. Picked from ranges like 32768-60999 on Linux.

cBPF

Old Linux packet filter that can run tiny programs in kernel and choose how many bytes to give back to an app.

IP options

Extra header fields in IP packets. LSRR/SSRR let sender suggest routers to pass through.

RTT

Time for a packet to go there and back. Attack here is a race against this time.

ARN

Remote attacker node that teams up with a shady app on the victim. Can send fake packets but can't see real traffic.

IP spoofing

Pretending to be someone else by faking the source address on a packet.

procfs / /proc/net

A file system that lets apps see system info like active connections. Restricted on modern Android.

DNS cache poisoning

Sneaky trick: putting a wrong domain-to-IP mapping into a DNS cache so future visits go to attacker.

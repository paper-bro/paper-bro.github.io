001Lesson 1 — The hook~5 min

The last-second net: catching bugs before 3.5 billion people see them

Imagine you ship a small code tweak to a system used by 3.5 billion people every day. The codebase is hundreds of millions of lines long, and thousands of changes are proposed every day. If your tweak hides a serious bug, how quickly would you want to know?

At Meta, every proposed change is called a diff. A diff has a parent — the code before your edit — and a child — the code after. The moment you submit that diff to the Continuous Integration system, before it lands into the main codebase and before it reaches production, there is a brief Just-in-Time window. That is the cheapest place to catch a bug: the author still remembers what they meant, no users are hit, and a fix is a tiny edit.

Wait a few hours until the diff is reviewed, or a day until it is in production, and the cost explodes. Other engineers have built on top of your code, users may have seen broken behavior, and fixing means rollbacks, hotfixes, and incident reports. The paper calls this the Catching JiTTest Challenge: automatically generate a test that fails on purpose on the buggy diff, right at that Just-in-Time moment, with enough accuracy that engineers trust it.

The core tension: generating many tests is computationally expensive, and if most failing tests are false alarms — the test is wrong, not the code — engineers get slowed down and start ignoring the signal. High true-positive rate with negligible drag on velocity is the goal.

Meta cannot afford to try this for every diff. The solution is targeting. Overnight, using spare computers, a model called Diff Risk Score (DRS) looks at diffs submitted the previous day and flags the small fraction most likely to cause a severe regression, trained on past risk. Only those high-risk diffs wake up the catching test generators the next morning. That keeps the expensive search focused where severe failures actually cluster.

In this course you will follow how Meta built two diff-aware generators, how they filter out false alarms with rules and LLM judges, and how they proved it works starting from 22,126 generated tests — preventing 4 severe failures before they ever reached production.

002Lesson 2 — Hardening vs Catching~6 min

Tests that pass vs tests that fail on purpose

Think of two different jobs for a test. One job is to be a guard that you leave behind. The other job is to be an alarm that goes off right now.

Meta needs both, and they behave in opposite ways. A hardening test is built to pass on today's code, called the parent revision. If it passes, it lands into the codebase and waits. If some future change breaks what it checks, it will fail then and warn you. It's like a smoke detector you install today to catch a fire next year.

A catching test is built to fail on purpose right now. It is made for one specific proposed change, called a diff. It passes on the parent, but fails on that diff. That pattern — PASS on parent + FAIL on diff — is called a weak catch. It is a candidate alarm: "hey, this change altered behavior!"

Weak vs strong: same alarm, different truth.
A weak catch only says the test failed. Whether it should have failed depends on the general oracle — the true intended behavior, which is often vague or unwritten. If the failure points to a real bug, it's a strong catch (a true positive). If the test is wrong about what was intended, it's a strictly weak catch (a false positive). Same red light, opposite meaning.

Here's the twist that makes catching powerful. A hardening test has to be made without knowing what future change will come — it can't see the diff in advance. A catching test can. It is Just-in-Time: it is generated after the diff is submitted, with the diff in hand, and it can aim directly at what changed.

In the Harden and Catch framework from the paper, a test can in principle be both — hardening for the future and catching for today. But in practice a test that catches the current diff cannot land together with that diff, because it fails on it. You either fix the code so the test passes, or you discard the test if it was strictly weak.

003Lesson 3 — The oracle problem~5 min

Who decides what's a bug? The oracle problem

Imagine two tests that both go PASS on parent → FAIL on diff. One caught a real bug. The other is out of date and complaining about an intentional change. From the computer's view they look identical. How do you tell them apart?

That's the oracle problem. An oracle is just the rule that decides what is correct.

💥

The easy oracle

Implicit oracle: some failures are always bugs, no matter what you intended. A crash, a NullPointerException, a web server that is down. You don't need a spec to know that's wrong. The paper calls this the implicit oracle.

📝

The hard oracle

General oracle: the real, intended behavior. What should the code do? This is often vague, undocumented, or only hinted at in a diff title like “better relevance” or “charge fee on refund.” You have to guess intent from code + title + summary + discussion.

When that guess is wrong, you get a strictly weak catch: a test that fails on the diff and passes on the parent, but should not fail. It's a false alarm. The paper found these come from very human patterns: brittle reflection, a method made private on purpose (should_be_private_smell), a bad mock, a data provider that builds wrong inputs, requiring key-value pairs in the exact same order, or just flaky infrastructure.

That matters because a general-oracle mistake is not obvious. A diff that says “make helpers private” should break a test that calls that helper — the test is now wrong, not the code. But a diff that says “add logging” should not flip a checkout check from true to false. Same FAIL signal, opposite meaning.

Why this is the #1 challenge: If most alarms are false, engineers start ignoring all alarms. The paper calls this development drag. Catching tests are worthless if they slow down the thousands of diffs Meta reviews every day. So every catching pipeline needs a second step — an assessor that scores each failing test from -1.0 (almost certainly a false alarm) to +1.0 (almost certainly a real bug) to filter the noise.

Think of it like a smoke detector. A detector that goes off every time you make toast isn't helpful, even if it once catches a real fire. You need a way to tell toast from fire before you wake the whole building.

004Lesson 4 — Baselines: how far old methods get you~6 min

How well do old methods catch? (Spoiler: not well)

Imagine you want to catch a mistake in a new edit to the code — called a diff. You could try an old approach: make a test from the old code (the parent), without even looking at the new edit, and hope it happens to break on the new edit. How often would that work by luck?

Meta checked. In a study of 22,126 real generated tests, they measured five approaches side by side. Three of them were baselines — old hardening methods reused to try to catch.

First, the luckiest baseline: coincidental catches. Meta already runs a hardening pipeline that tries to make tests that pass on the diff. Sometimes those failing tests happened to pass on the parent. That pattern — pass on parent, fail on diff — is a weak catch. But it was rare: 13,001 tests → 29 weak catches = 0.2%. That's about 1 in 500. Too rare to build on, so Meta stopped counting on it.

Next, two real hardening generators applied to the parent instead of the diff, to see if tests meant for the future would accidentally catch the current change:

  • TestGen-LLM — an LLM that tries to cover uncovered lines: 4,499 tests → 89 weak catches = 2.0%, covering 43 of 1,185 diffs = 3.6% of diffs. If you also required those tests to add new line coverage, it dropped to 1,440 → 14 = 0.9%. Same idea, stricter rule, fewer catches.
  • ACH — a mutation-guided system (it makes tiny fake bugs called mutants and tries to kill them): 754 tests → 6 = 0.8%, covering 5 of 322 diffs = 1.6%.
Big picture: a hardening test built without seeing the future diff fails on only about 1% of arbitrary future diffs (0.8% for ACH, 0.9% for TestGen-LLM needing coverage, 2.0% without). That's useful for hardening over time — roughly 1 in 100 changes will be caught later — but terrible if you need to catch a bug right now.

Why so low? Neither hardening method looks at the diff. They guess what some unknown future change might break. That's like preparing for any possible pop quiz — you will help sometimes, but not often for this quiz.

This is the baseline the paper wants future work to beat. Diff-aware methods should do much better because they do look at the diff — which we will see in the next lesson.

005Lesson 5 — Diff-aware workflows~7 min

Two smarter nets: Dodgy Diff and the Intent Detective

Older test generators are blind to your change. They make a test for the parent — the code before your diff — and hope it later fails on some unknown future diff. The paper showed that works only about 1% of the time. If you want a test that fails on this specific diff, you have to look at the diff itself.

That is what the two new workflows at Meta do. They are diff-aware, meaning they use the diff as input when they try to make a test fail.

The simple net: Dodgy Diff

Imagine your diff is already a bug. That is the whole trick of the dodgy-diff workflow. It treats the diff as if it were a mutant — a tiny artificial bug made from the parent — and asks the LLM test generator to make a test that can tell parent and mutant apart. The test should PASS on parent, FAIL on diff.

Because it never guesses your intention, it tries to make as many distinguishing tests as it can. It will generate a lot of weak catches, even if some will turn out to be false alarms later.

The detective net: Intent-Aware

The second workflow tries to be smarter. It first asks an LLM to infer the intent of the diff from the code plus the diff title and summary.

  1. Infer intent. Example: “refactor duplicate access check to be cleaner.”
  2. List risks. How could that intent go wrong? Maybe a role that should stay blocked now passes.
  3. Make a mutant per risk. Each risk becomes its own tiny bug inserted into the parent.
  4. Generate a test that passes on parent but fails on that risk-mutant.
  5. Keep it only if it also fails on the real diff. Then it is a weak catch.
Why make fake bugs to find real ones? This uses the coupling hypothesis — a simple, well-studied idea: tests that catch simple made-up bugs often also catch real bugs that are similar. If your real diff shares a flaw with one of the risky mutants, the test for that mutant will expose it.

What Meta measured

For ten days in November 2025 both diff-aware nets ran in production alongside the older baselines, on the same set of diffs. For those four approaches together Meta generated 9,125 tests. Out of the full study of 22,126 tests, the results in Table 1 were:

  • Dodgy diff: 1,621 tests gave 41 weak catches = 2.5% per test, covering 26 of 654 diffs = 4.0% of diffs.
  • Intent-aware: only 811 tests gave 52 weak catches = 6.4% per test, covering 49 of 617 diffs = 7.9% of diffs.

That is roughly 4 times more weak catches per test than the hardening approaches (which were 0.8% to 2.0%) and about 20 times more than the coincidental baseline (29 of 13,001 = 0.2%). The intent-aware net was also the most efficient per diff: it found at least one weak catch in almost twice as many diffs as dodgy-diff (7.9% vs 4.0%), even though it made fewer tests overall.

The paper is careful: these two workflows are just first versions. Intent was inferred only from code, title and summary — not from emails, discussions or task docs. Better context could raise both numbers further. But even this simple intent step already more than doubled the reach.

006Lesson 6 — Filtering false alarms~6 min

Sifting signal from noise: LLM judges and rule detectives

Imagine your fire alarm went off 10 times a day and 9 times it was toast burning. You'd start ignoring it. That's the core danger for catching tests at Meta: most code changes are fine, so most failures are false alarms.

Meta's fix is a second step after finding a weak catch — a test that passes on the parent and fails on the diff. A small judge looks at that failure and guesses: is this a real bug or is the test itself wrong? The paper calls these judges assessors.

Every assessor outputs one number, a score from -1.0 to +1.0:

  • -1.0 = sure false alarm (a strictly weak catch — the test should not have failed)
  • 0 = no information — the judge abstains
  • +1.0 = sure real bug (a strong catch — the failure matches the true intended behavior, the general oracle)
Think of -1 to +1 as a confidence dial. The assessor never sees ground truth, only clues, so it votes with confidence.

Two very different judges

1. LLM-as-Judge ensemble. This uses three large models — Llama 3.3-70B, Gemini 3 Pro, and Claude Sonnet 4 — and gives them the same four clues: the test code, the failure trace (error message and stack), the diff itself, and the inferred intent from Lesson 5 (title + summary).

It produces two scores. For Llama, the model answers “yes, this is unexpected” or “no,” and the log-probability of that first token is stretched to -1 to +1 — called TP Prob. For all three models, each also votes High = 1.0, Medium = 0.0, or Low = -1.0 on “how likely is this a real bug?” The median of the three votes is the Bucket Med score. Each also writes a short explanation of what changed and why it looks unexpected.

2. RubFake — the rule detective. This is not an LLM. It is deterministic: it checks for exact patterns the team learned by hand-reviewing 600 weak catches with engineers confirming the answers.

🚩

False-alarm patterns (14)

From Table 2 — all 14 patterns. 13 are high likelihood: broken_test_runner (infra crashed), reflection (test pokes private internals), type_missmatch (method type changed), bad_mock_smell, should_be_private_smell, method_must_be_protected_smell, mock_broken, data_provider_broken, not_implemented_exception, key_value_pair_change (order doesn't matter), undefined_variable, expecting_particular_calls_to_functions, web_server_down; plus 1 low likelihood: flakiness.

🎯

Real-bug patterns (9)

From Table 3. Examples: empty_container (list became empty though code didn't touch it), unexpected_key_change, changed_bool (true became false but the defining expression wasn't changed), null_value, monotonic_change (only new feature intended, but old behavior changed), refactor that should preserve meaning.

Why you need both

The team found the LLM judges and RubFake don't strongly agree. Rank correlations were modest — Spearman ρ at most 0.535 — and agreement scores like Cohen's κ and Fleiss' κ were mostly Poor to Slight (near 0). That is actually good news: it means they look at different signals and are complementary, not redundant.

And the filter works: when the Llama score was -1 or the ensemble bucket was at 0 or below, the filtered cases were false alarms with over 98% precision. Automatically removing those cut human review workload by about 70% — letting the same reviewers handle roughly 4× as many cases. The rules keep getting better as engineers label more examples, but they are still imperfect — an open problem for future work.

007Lesson 7 — Did it work for real engineers?~6 min

Proving it with 41 real engineers (and 4 disasters averted)

Until now we have counted weak catches — a test that passes on the parent revision and fails on the new diff. But a weak catch is just a candidate. The real question is: does an engineer look at it and say “yes, that’s a bug”?

From mid-September to the end of October 2025, Meta did the simplest possible check. When a catching test flagged a diff, a bot sent the author a short chat: “this expression used to be true and now is false — expected?” No test code to read, just: is the changed behavior intended?

The engineers answered 41 times. Out of those 41 reach-outs, 8 were confirmed true positives — real bugs. That is 8 / 41 ≈ 19.5% precision as the engineer experienced it. Of those 8, 4 would have caused serious production failures if they had landed. The other 4 were also useful: 2 led the team to add defensive code to stop a future regression, and 2 led the authors to abandon the diff entirely. The 33 false alarms? Engineers dismissed them in a few minutes because the question was so easy to answer — the paper calls the drag on developer speed “negligible.”

Four disasters averted from just 41 conversations may sound small, but most bugs are trivial. Public bug trackers and the literature suggest only about 5% to 20% of bugs are severe. Here, 50% of the caught bugs (4 of 8) were severe — because Meta only ran the check on high-risk diffs flagged overnight by its Diff Risk Score. Targeting where severe bugs cluster gives a high return on effort.

That 19.5% is from a small sample, so the paper also sanity-checks the assessors on a much larger set: 22,126 generated tests and hundreds of diffs already labelled by human review as Good (Accepted or Closed — landed) versus Bad (Abandoned, Changes Planned, Needs Revision, Reverted — not landed). Good/Bad is not perfect ground truth, but reviewers have been good at filtering bugs since the 1970s.

If the assessors — the rule-based RubFake and the two LLM judges — were guessing randomly, they would score Good and Bad diffs the same. They did not. For the simple “dodgy diff” workflow, all three assessors gave true-positive scores significantly more often on Bad diffs, and the LLM judges gave false-positive scores significantly more often on Good diffs (Fisher’s exact test, p < 0.05). In short, they agreed with the human reviewers.

Why trust “significant”? With many tests, a tiny difference can look significant by chance. The authors ran 100,000 shuffles where they randomly re-labelled Good vs Bad. A “significant” result with a small effect happened about 4% of the time — close to the 5% you expect. But a medium or large effect happened less than 0.001% of the time. Most of the paper’s observed differences were medium, so they are almost certainly not luck.

There is more to do — intent was inferred from only code + title + summary so far, and even the combined assessors are imperfect. But the takeaway from lesson 7 is concrete: catching Just-in-Time, filtered and delivered as a one-sentence sense-check, stopped 4 severe failures with minutes of cost. 008Lesson 8 — Bonus and big picture~5 min

Bonus hardening and why targeting wins

You asked the AI to make a test that fails on purpose to catch a bug. It tried. Sometimes it succeeded and you got a weak catch. Sometimes it failed to fail — the test just passed.

Here's the surprise the Meta team found in Table 6: those "failed" attempts are not waste. When you try to make a catching test, most tests end up passing on both versions. The diff didn't break them. That means the test passed on the parent and also passes on the new code. By definition, that's a hardening test — a test you can save to guard the future.

In one month of running the two catching workflows (11 Nov to 11 Dec 2025) they generated 8,797 tests in total from 2,729 diffs. Of those, 7,987 passed on both parent and diff. That's 90.8% that become free hardening tests, even while the workflows were hunting for catches. Broken down for the passing (hardening) subset: the intent-aware workflow gave 2,551 passing tests from 1,271 diffs (from 2,923 tests on 1,471 diffs total), and dodgy-diff gave 5,436 passing from 1,763 diffs (from 5,880 tests on 1,982 diffs total). You get to do both jobs at once: hunt for bugs now and collect protection for later.

💡 Key insight: Trying to make a failing test is a two-for-one deal. If it fails as hoped, you may have a catch. If it passes, you have a new hardening test for free. That's why the paper suggests running catching-first — hardening comes along for the ride.

Why does where you hunt matter so much? Most bugs in the wild are not severe — studies and bug-trackers like Bugzilla put severe bugs at about 5% to 20% of all bugs. If you test random changes, you spend a lot of effort for mostly small fixes.

Meta did the opposite. They ran targeting overnight on spare computers using a Diff Risk Score that flags risky diffs from the previous day. Only those flagged diffs got the expensive catching generation. Result from the real engineer deployment: of 8 confirmed bugs caught from 41 alerts, 4 would have caused serious production failures. That's 4 of 8 = 50% severe, far above the normal 5–20%. Targeting puts your net where the big fish swim.

And it stays cheap for engineers. An alert was just a chat message like "this now goes from true to false — expected?" A false alarm took a few minutes to dismiss, not hours of debugging. Combined with the LLM + rule assessors that cut human review by 70%, the whole thing runs without slowing velocity.

Go deeper: limits and next steps — The paper is honest about them. So far intent was guessed only from code plus title/summary, not emails or design docs. It was only backend systems (hundreds of millions of lines) at one company. And assessors are still imperfect; they agree only a little with each other (which is actually good — they give different clues). Future work: richer context for intent, better combined judges, and testing beyond backend code. The course simplifies the exact risk model and assessor math; the paper has the full statistical tables.

The big picture: diff-aware and intent-aware generation plus two complementary judges makes Just-in-Time catching scalable and industrial-strength. You don't need perfect prediction if you target well, filter smartly, and keep the human check ultra-light.

ABCWord bank

Word bank.

Diff

A proposed code change submitted to Meta's review system (Phabricator CI). Has a parent revision (before) and a child revision (after).

Parent revision

The version of the code before the proposed change. Catching tests must pass here and fail on the diff.

Hardening test

A test that passes when created and lands in the codebase to guard against future regressions. Fails later = possible regression.

Catching test / JiTTest

A test designed to fail on the current diff (and pass on its parent) to catch a bug before it lands. Cannot land itself if it fails.

Weak catch

A test that fails on the diff and passes on its parent. Candidate bug signal, not yet verified.

Strong catch

A weak catch that should fail according to the true expected behavior. It's a true-positive bug found.

Strictly weak catch

A weak catch that should NOT fail. The test itself is wrong / mismatched to intent. A false-positive.

Implicit oracle

Obvious failures that are always bugs regardless of spec, like crashes or null-pointer exceptions.

General oracle

The true, often vague or undocumented, intended behavior of the system. What the code should do.

Mutant / Mutation testing

A small artificial bug seeded into code to test if tests can detect it. Used by ACH and the catch workflows.

Assessor

An automated judge that scores a weak catch from -1.0 (sure false-positive) to +1.0 (sure true-positive) to filter noise.

Targeting

Diff Risk Score. A nightly model that flags high-risk diffs from the previous day to focus catching generation where severe bugs are likeliest.

Severe failure averted

A human-confirmed bug found by a catching test that would have caused a serious production failure if not stopped.

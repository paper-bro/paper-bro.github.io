001The problem~6 min

Why Building a Super-AI Is Usually Too Expensive

Training a top AI is like building a skyscraper: the taller you go, the more steel, workers, and time you need. For the last few years, "taller" meant one thing — more parameters, those billions of tiny knobs the model tunes to predict the next word. But a funny thing happened: the best models got so big that almost nobody could afford to build them.

DeepSeek-V3 is 671 billion parameters in total. That is not a typo. For comparison, a very strong open model like LLaMA-3.1 is 405 billion, and Qwen2.5 is 72 billion. If you ran all 671 billion knobs for every single word, the electricity bill alone would be brutal. So the DeepSeek team cheated — in a clever, published way.

Only 37 billion parameters are actually awake for any one token. Think of it as a hospital with 671 billion doctors on staff, but only a team of 37 billion enters the room for each patient. The rest wait their turn. This design is called a Mixture-of-Experts, and it is why DeepSeek-V3 can look like a giant but pay like a much smaller model when it does work.

The headline numbers from the paper — exactly as reported:
671B total / 37B active per token · trained on 14.8 trillion tokens · 2.788 million H800 GPU-hours total = 2,664k pre-training + 119k context extension + 5k post-training · at 2 dollars per GPU-hour = 5.576 million dollars · about 180k hours per trillion tokens, which is 3.7 days on 2,048 H800 GPUs. And it was stable: zero irrecoverable loss spikes or rollbacks.

Why does that matter? The paper's goal was to match closed labs — GPT-4o and Claude-3.5-Sonnet — while staying open and cheap, and to do it without the training collapsing midway. Stability is rare at this size. Longer context was also required: the model first learned on short 4k-token windows, then was stretched to 32k and finally 128k tokens so it can keep track of a whole book.

002Background you need~8 min

The Memory Problem of Talking AIs

Imagine you're reading a mystery novel and trying to guess the next word. To do it well, you don't stare at every past page equally — you glance back at the clues that matter. Attention is the AI's version of that glance.

DeepSeek-V3, like all modern language models, works in a loop. It turns words into tokens — small word-pieces — then into vectors, which are just lists of numbers. For DeepSeek-V3 each token's vector ht has d = 7168 numbers. The model pushes that vector through 61 layers. Each layer has two jobs: attention (decide which past words to look at) and a feed-forward network (think with what you gathered). Then it predicts the next token, adds it, and repeats.

Here's the attention intuition. For every past token, the model makes a Key and a Value. For the current token, it makes a Query. Think of the Query as a question — "I'm looking for the animal that sat" — and each Key as a label on a past word — "cat: animal", "mat: furniture". The model scores how well they match:

$$w_{t,j} = \text{Softmax}_j\left(\frac{\mathbf{q}_{t}^{T}\mathbf{k}_j}{\sqrt{d_h+d_h^R}}\right)$$

qtT kj is just a similarity score — big if Query and Key point the same way, small if not. Dividing by √(dh+dhR) keeps the numbers from exploding when vectors are long. Softmax turns those scores into weights that sum to 1 — 10% on "The", 70% on "cat", and so on. The output is a weighted sum of the past Values:

$$\mathbf{o}_{t} = \sum_{j=1}^{t} w_{t,j}\, \mathbf{v}_j$$

So the model literally mixes past meanings together, weighted by relevance. DeepSeek-V3 does this with 128 heads in parallel — 128 different Query/Key/Value sets — so one head can track grammar while another tracks who did what.

Why this gets expensive: the KV cache. To generate word 10,001, the model must still remember the Keys and Values for words 1 to 10,000 — otherwise it would recompute everything from scratch. That memory is the KV cache. Its size grows linearly with context length: twice the tokens, twice the memory. For DeepSeek-V3's 128K-token context, that's tens of gigabytes just for remembering.

The other place parameters live is the feed-forward networks, or FFNs. In a normal dense model, every token goes through the same big FFN. DeepSeek-V3 will later split that into specialists, but for now picture one big brain doing the thinking after attention has gathered the clues.

The paper keeps the full math for attention with rotation, compression and output projection, but the core idea above is what matters here: attention = weighted looking-back, KV cache = the price of remembering.

003Innovation 1~10 min

A Backpack That Holds More: Compressing Attention

Talking AIs have a memory problem. Every time a Transformer writes one more word, it has to look back at all the words before it. To do that fast, it saves two little notes for each past word — called a Key and a Value. Together they are the “KV cache.” For a 128,000-word conversation, that cache gets huge — too big to fit on one GPU.

DeepSeek-V3 fixes this with a trick called Multi-head Latent Attention (MLA). Think of a backpacker who needs 20 books but doesn’t want to carry 20 heavy books. She takes photos of all the pages, compresses them onto one tiny memory stick (512 photos instead of 16,384 pages), and only carries that stick. When she needs a page, she prints it again.

Paper idea in one line: don’t cache the big Keys and Values. Cache a tiny latent (hidden) vector and rebuild the big ones only when you need them.

Here’s how the paper writes it. First, the model takes the word’s vector ht (size d = 7168) and squeezes it down:

$$\mathbf{c}_t^{KV} = W^{DKV}\, \mathbf{h}_t$$

ctKV is the compressed memory stick. WDKV is just a matrix that projects from 7168 numbers down to only dc = 512 numbers. That’s more than 10× smaller. The paper also squeezes the Query (the question we’re asking right now) the same way: ctQ = WDQ ht to dc' = 1536, then expands it again later.

When attention needs the real Keys and Values, it expands the stick back:

$$\mathbf{k}_t^{C}=W^{UK}\mathbf{c}_t^{KV},\qquad \mathbf{v}_t^{C}=W^{UV}\mathbf{c}_t^{KV}$$

WUK and WUV are the “printers” that blow the 512 numbers back up to the full size needed for 128 heads × 128 numbers per head. A small extra piece called the decoupled RoPE key ktR (size 64) is kept separately to remember word order — in the paper WKR is 64 × 7168, so ktR is just 64 numbers.

Then attention works normally:

$$\mathbf{o}_{t,i}=\sum_{j=1}^{t} \mathrm{Softmax}_j\!\left(\frac{\mathbf{q}_{t,i}^T \mathbf{k}_{j,i}}{\sqrt{d_h+d_h^R}}\right) \mathbf{v}_{j,i}^{C}$$

In words: for each head i, compare your Query q to all past Keys k, turn the scores into weights with Softmax, and mix the Values v. The paper uses 128 heads, dh=128, dhR=64.

What actually gets cached? Only the blue-boxed vectors in Figure 2: ctKV (512 numbers) and ktR (64 numbers) — 576 numbers total, about 1.1 KB per token in BF16. Not the big ktC and vtC (32,768 numbers, 64 KB). During training the same squeeze saves activation memory too. Result: inference needs far less GPU memory, but quality stays like normal attention (MHA).

004Innovation 2~9 min

Instead of One Big Brain, 256 Small Ones

Imagine a hospital with one doctor who must handle everything — heart surgery, broken bones, baby checkups. That doctor would need to know it all, and every patient would wait for the same person. Now imagine a hospital with 256 specialists plus one general doctor who sees everyone. Each patient is sent to just a handful of specialists who are best for their case. That's faster, and each specialist gets really good at their job.

DeepSeek-V3 does the same with its Feed-Forward Networks. In a normal Transformer, every token — think of a token as a word-piece — goes through the same big FFN. In DeepSeek-V3, all FFNs except the first 3 layers are replaced with DeepSeekMoE layers. Each MoE layer has 1 shared expert that every token uses, plus 256 tiny routed experts. For each token, only 8 routed experts are switched on.

$$ s_{i,t} = \mathrm{Sigmoid}(\mathbf{u}_t^{T}\mathbf{e}_i) $$

This is the token-to-expert affinity. u_t is the token's current state, e_i is the centroid — the address — of expert i, and Sigmoid squashes the score to 0 to 1. High score means "this expert wants this token." The layer picks the 8 experts with the highest s — that's TopK.

$$ g_{i,t} = \frac{s_{i,t}}{\sum_{j\ \text{chosen}} s_{j,t}} \quad \text{and} \quad \mathbf{h}'_t = \mathbf{u}_t + \mathrm{FFN}^{(s)}(\mathbf{u}_t) + \sum_{i=1}^{256} g_{i,t}\,\mathrm{FFN}^{(r)}_{i}(\mathbf{u}_t) $$

g_{i,t} is the gating value — the normalized weight. Only chosen experts get a non-zero g. The output adds the general doctor (shared expert) and the weighted specialists. Think of it as "we listen to 8 opinions, but weigh louder voices more." The paper also adds a practical rule: each token can be sent to at most M=4 different machines (nodes), to keep network traffic down.

Why 256 small experts instead of 8 big ones? Many small slots mean finer choices — one expert can learn Python loops, another poetry rhyme, another algebra. The shared expert handles common grammar that everyone needs. With hidden size 2048 per expert and 61 layers, this adds up to 671 billion total parameters stored, but only about 37 billion active per token — so it feels like a small model at run-time, with the knowledge of a giant one. And because the balancing is good, the paper reports no token dropping during training or inference — no patient is turned away.

005Innovation 3~10 min

The Traffic Cop Who Doesn't Grade the Students

Imagine 256 tiny experts all wanting work, but a bossy hall monitor shouts: “everyone must get exactly the same number of jobs in every single classroom.” The result? No one gets to specialize. The math whiz has to write poems, the coder has to fix pipes. Learning gets worse.

That bossy monitor was the old fix for “routing collapse” — when most tokens rush to a few popular experts and the rest sit idle, wasting GPUs. The usual fix adds an extra penalty to what the model is trying to minimize:

$$\mathcal{L}_{\mathrm{Bal}} = \alpha \sum_{i=1}^{N_r} f_i P_i$$

Here $f_i$ is how often expert $i$ was picked in one sequence, and $P_i$ is its average score $s_{i,t}=\mathrm{Sigmoid}(\mathbf{u}_t^T \mathbf{e}_i)$ — how much each token “liked” that expert. With $\alpha=0.0001$ it pushes every single sequence toward perfect balance. It keeps GPUs busy, but the paper shows it hurts accuracy because it punishes natural specialization: a code sentence should favor code experts, even inside one sequence.

DeepSeek-V3 fires the grading monitor and hires a traffic cop instead. The cop doesn’t grade the students; she just holds a little sign $b_i$ for each expert and only uses it to decide who goes where:

$$g'_{i,t}=s_{i,t}\;\text{ if }\; s_{i,t}+b_i \in \mathrm{TopK}(\{s_{j,t}+b_j\},K_r)$$

$b_i$ is never used in the final answer weight and never gets a gradient. It’s just added to the score $s_{i,t}$ to pick the top $K_r=8$ out of $N_r=256$ routed experts. After each big batch (thousands of tokens across many sequences), the trainer checks real load: if expert $i$ was overloaded, $b_i$ goes down by $\gamma$; if underloaded, $b_i$ goes up by $\gamma$. For DeepSeek-V3, $\gamma=0.001$ for the first 14.3 trillion tokens, then $0$.

Why batch-wise beats sequence-wise: the old loss demands balance inside each sequence. The bias trick only demands balance across the whole batch. Inside one math sentence math experts can spike to 2× their fair share — as long as a story sentence elsewhere lets other experts catch up. Figure 9 proves it: the bias model shows clear spikes by domain on the Pile (arXiv, GitHub, Books), the auxiliary-loss model looks flat at 1.0.

The payoff shows up in tests. On a 16-billion-parameter MoE and on a 229-billion one, the bias-only version beat the auxiliary-loss version on most benchmarks. And when the authors tried a batch-wise auxiliary loss that allowed the same flexibility, it matched the bias method (validation loss 2.253 vs 2.258). In other words, flexibility — not magic — explains the win, and it lets experts specialize without wasting GPUs.

006Innovation 4~8 min

Why Predict One Word When You Can Predict Two?

Imagine learning chess by only ever guessing the very next move. You will get okay. Now imagine you have to guess the next two moves in a row, and you get told if both were right. You have to plan deeper — not just “what looks good now,” but “what makes sense for what comes after.” That is exactly what DeepSeek-V3 does with words.

Most language models train to predict one token ahead: given everything so far, what is token t+1? DeepSeek-V3 adds a Multi-Token Prediction (MTP) trick. At every position it predicts two tokens ahead, not one, while keeping the normal left-to-right order.

The MTP setup: In the paper DeepSeek-V3 uses D = 1 extra module, so total predictions per position = 2. The embedding layer and the output head are shared with the main model to save memory.

How does the extra prediction work? The paper keeps the full causal chain with a small sequential module. In a simplified version:

$$ \mathbf{h}_i^{\prime k} = M_k\,[\,\text{RMSNorm}(\mathbf{h}_i^{k-1});\,\text{RMSNorm}(\text{Emb}(t_{i+k}))\,] $$

This says: take the hidden state from the previous depth h_i^{k-1} (for k=1 that is the main model’s hidden state), and glue it together with the embedding of the future token t_{i+k}. A learned matrix M_k mixes them. Then that mixed vector goes through a Transformer block at that depth:

$$ \mathbf{h}_{1:T-k}^{k} = \text{TRM}_k(\mathbf{h}_{1:T-k}^{\prime k}) $$

and finally the same shared output head that the main model uses turns it into probabilities for the next token:

$$ P_{i+k+1}^{k} = \text{OutHead}(\mathbf{h}_i^{k}) $$

So for k=1, the module looks at “what the main model thought so far” plus “what the word after next really is” and tries to predict the word in between — but during training it must do this sequentially, not in parallel like some earlier work. Each depth gets its own cross-entropy loss:

$$ \mathcal{L}_{\text{MTP}}^{k}=\text{CrossEntropy}(P_{2+k:T+1}^{k}, t_{2+k:T+1}) \quad\text{and}\quad \mathcal{L}_{\text{MTP}} = \frac{\lambda}{D}\sum_{k=1}^{D}\mathcal{L}_{\text{MTP}}^{k} $$

λ is just a weight: 0.3 for the first 10 trillion tokens, then 0.1 for the last 4.8T. It is added on top of the normal next-token loss.

Why bother? Two reasons. First, learning: denser signals and “pre-planning.” The model cannot be lazy and only optimize for the immediate word; it has to build representations useful two steps ahead. In the paper’s ablation (Table 4) this consistently helps — for example HumanEval Pass@1 goes from 20.7 to 26.8 on a small 15.7B model and from 44.5 to 53.7 on a large 228.7B model, with similar lifts on BBH, DROP, and GSM8K. Roughly, same inference cost (you throw the MTP module away after training) but better scores.

Second, speed: you can keep that one MTP module at inference and use it for speculative decoding. The main model guesses word 1, the MTP module guesses word 2 based on it, and you verify both. The paper reports the second token is accepted 85% to 90% of the time, giving about 1.8× tokens per second.

007Innovation 5~10 min

Faster, Smaller, Still Smart

Doing every multiplication in 32-bit is like buying everything with $100 bills — safe, but you carry a heavy wallet and move slowly. DeepSeek-V3 noticed most of its heavy work is just big matrix multiplications (called GEMMs) in the Linear layers, and those can run in 8-bit (FP8) — roughly twice as fast and half the memory.

But there is a catch: 8-bit numbers have a tiny range. You have to pick a scale — how much to shrink real numbers so the biggest one just fits into FP8.

$$ \text{scale}=\frac{\max|x|}{\max_{FP8}},\quad x_{FP8}=\text{round}(x / \text{scale}) $$

If you pick one scale for a whole tensor (thousands of numbers), one loud outlier — a single feature much bigger than the rest — forces the scale to be huge, and all the small, important values get crushed to zero. The paper shows this ruins accuracy.

The fix is fine-grained quantization. Instead of one scale, give every tiny tile its own scale, computed live from its own biggest value (online max-abs).

📦

Activations: 1×128 tiles

Take 1 token × 128 channels at a time. Each tile gets its own scale. An outlier can only spoil its own tile.

🧱

Weights: 128×128 blocks

Take 128 in × 128 out weights per block. Same idea — small groups adapt to outliers.

That lets the model safely use the precise E4M3 format (4 exponent bits, 3 mantissa bits) everywhere, instead of the looser E5M2 others use.

There was a second math bug to fix. On H800 GPUs, the chip's Tensor Core does FP8 math but only keeps about 14 bits when adding up the products. When the inner size K is large (K = 4096 is common), that truncation makes the answer wrong by up to ~2% — not okay when you're training on 14.8 trillion tokens. So every NC=128 steps, the paper copies the partial sum to a CUDA core and adds it up in full 32-bit (FP32), including the per-group de-scale. Two groups of chips work in turns so nothing waits.

This FP8 trick doesn't run alone. Most layers stay in BF16/FP32 — embeddings, the final output head, MoE routing, normalizations and attention — and master weights and gradients stay in FP32 (optimizer moments in BF16 to save memory). Activations saved for the backward pass and tokens sent between nodes are also kept in FP8 (with power-of-2 scales) to cut memory and network traffic. To hide that network wait, DeepSeek-V3 uses DualPipe: 16-way pipeline across layers and 64-way experts across 8 nodes, so while one micro-batch does attention, another does its all-to-all send. Only 20 of 132 SMs handle communication.

Together: fine tiles protect outliers, 128-step promotion protects addition, and DualPipe hides communication — giving ~2× speed with less than 0.25% extra error.

008Results~9 min

The Strongest Open-Source Model — At Half the Price

Imagine two students taking the same final exam. One memorizes every textbook word-for-word and writes slowly. The other condenses notes to a tiny backpack, works with 256 specialist tutors but only asks 8 per question, glances one step ahead while writing, and does arithmetic in shorthand. Both pass — but the second finishes cheaper and just as well. That second student is DeepSeek-V3.

The paper's scoreboard is blunt. DeepSeek-V3 cost 2.788 million H800 GPU-hours total: 2,664K for pre-training on 14.8 trillion tokens, 119K to stretch context to 128K, and 5K for post-training. At 2 dollars per hour that's $5.576M. On the builders' 2,048-GPU cluster that's 180K hours per trillion tokens — about 3.7 days per trillion — so the whole pre-train finished in under two months. And throughout, the authors report zero irrecoverable loss spikes and zero rollbacks, which is rare for a 671-billion-parameter run.

Was cheap math still accurate? The team checked FP8 (8-bit) training against the usual BF16 (16-bit). On two scales — ~16B and ~230B parameters — the relative loss difference stayed below 0.25%, inside normal randomness. In their Figure 10 the two loss curves sit essentially on top of each other after smoothing. That matters because most savings came from FP8 matrix math, fine-grained 1×128 tiles, and promoting accumulation to FP32 every 128 elements — all from Lesson 7.

Where it leads: on code and math, V3 jumps furthest ahead. Chat version scores MATH-500 90.2% (next best Qwen2.5 72B is 80.0%), AIME 2024 39.2% vs 23.3% for Qwen, LiveCodeBench COT 40.5% vs 36.3% for Claude-3.5-Sonnet, and Codeforces 51.6th percentile. Even in English knowledge it ties the best: MMLU 88.5% next to GPT-4o 87.2% and Claude 88.3%. Base-model Table 3 shows the same pattern before any chat tuning: MMLU 87.1, MATH 61.6, MBPP 75.4, HumanEval 65.2.

Long context wasn't sacrificed for cost. After pre-training at 4K length, the team did two short extensions — 1,000 steps to 32K then 1,000 to 128K using YaRN — and then gave the model the "Needle In A Haystack" test: hide one fact somewhere in up to 128,000 tokens and ask for it. V3 finds it wherever you hide it, shown as a solid green sheet in Figure 8. That long memory is directly enabled by MLA's small KV cache from Lesson 3, which stores only a 512-dim latent vector ctKV plus a tiny RoPE key instead of the full 7168-dim keys and values.

Chat benchmarks complete the picture. Arena-Hard, where real people vote on open-ended answers, V3 hits 85.5% vs Claude-3.5's 85.2% and GPT-4o's 80.4% — the first open-source model over 85%. AlpacaEval 2.0 is 70.0% vs about 51% for GPT-4o. And Chinese factuality, where earlier models lagged, flips: C-SimpleQA 64.8% vs GPT-4o 59.3% and Qwen 48.4%.

The paper is careful: V3 still trails Claude on some engineering code like SWE-Verified (42.0% vs 50.8%) and needs large deployment units. The full report also has extra ablations and hardware suggestions we don't cover. But the through-line is simple: compress memory (MLA) + use only the right specialists (MoE with bias-balancing) + look one token ahead (MTP) + do math in 8-bit without losing precision + overlap communication (DualPipe) = top-tier results at roughly half the usual bill.

ABCWord bank

Word bank.

Token

The basic unit of text the model reads and writes, like a word piece. DeepSeek-V3's tokenizer has 128,000 different tokens.

Attention

How a language model decides which previous words to pay attention to when predicting the next word. It compares a Query vector with Key vectors to weight Value vectors.

KV cache

The memory a model keeps while writing text, storing Keys and Values for all previous tokens so it doesn't recompute them. It grows with context length.

Low-rank compression

A way to shrink vectors by projecting them into a much smaller space with a matrix, then projecting back later. MLA does this to save KV cache.

Mixture-of-Experts (MoE)

An architecture where each token is sent to only a few small feed-forward networks (experts) out of many. DeepSeek-V3 has 671B total parameters but only 37B active per token.

Token-to-expert affinity

A score for how much a token wants to go to a particular expert: s(i,t) = Sigmoid(u_t^T e_i). Top scores are chosen.

Shared expert

A shared small network that every token uses, plus routed experts that only some tokens use. DeepSeek-V3 uses 1 shared + 256 routed experts per MoE layer, activating 8 routed per token.

Routing collapse / load imbalance

When most tokens go to the same few experts, leaving others idle. It wastes GPUs. Traditionally fixed with an extra loss term.

Auxiliary-loss-free bias

A number b_i added only for deciding routing: token goes to expert if s(i,t)+b_i is in Top-K. After each step, b_i is decreased by γ if overloaded, increased if underloaded. The real output still uses s(i,t).

Multi-Token Prediction (MTP)

Training the model to predict not just the next token but D future tokens at each position. DeepSeek-V3 uses D=1 and combines the loss as L_MTP = λ/D Σ L_MTP^k with λ=0.3 then 0.1.

FP8 mixed precision

Using 8-bit floating point (E4M3: 4 exponent bits, 3 mantissa bits) for most matrix multiplications to run 2x faster and use half the memory, while keeping sensitive parts in BF16/FP32.

Fine-grained quantization

Turning high-precision numbers into FP8 by scaling groups. DeepSeek-V3 uses 1×128 tiles for activations and 128×128 blocks for weights, computing the max value online for each group.

DualPipe pipeline parallelism

Splitting model layers across GPUs and feeding micro-batches in both directions so computation and communication overlap. DeepSeek-V3's DualPipe has bubbles (PP/2-1)(F&B + B -3W) vs (PP-1)(F+B) for 1F1B.

All-to-all communication

Tokens being sent between nodes that hold different experts. DeepSeek-V3 limits each token to ≤4 nodes and overlaps IB (50 GB/s) and NVLink (160 GB/s) transfers.

Speculative decoding

Reusing the MTP module at inference to guess the next 2 tokens and verify them, getting 1.8× tokens per second with 85-90% acceptance for the second token.

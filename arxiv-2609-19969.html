001The problem~6 min

The agent that remembers too much

Imagine an AI agent that helps you for a whole afternoon: it reads your whole codebase, browses docs, runs code, and chats. By hour three it has seen close to a million tokens — words, code, images. That is the new normal for “long-horizon” agents, and it creates a very physical problem: where do you keep all those notes?

While it reads, every Transformer keeps a KV cache — a short-term memory of Keys and Values for every past token. Think of it as sticky notes the model writes so it does not have to re-read everything when it generates the next word. Reading the prompt in one big batch is called prefill and is heavy on compute. Generating one token at a time is called decode and is heavy on memory reads from that cache.

DeepSeek-V4 had two kinds of notes. Global KV covers the whole million-token history — powerful but grows with length and lives in the chip’s fast memory (HBM). SWA KV covers only the last W = nwin = 128 tokens — a small sliding window that is cheap because its size is bounded, but it cannot see far-away facts. For long sequences, global KV dominates the runtime cost.

There are also two places to pay. Runtime global KV must stay in HBM so decoding stays fast. Persistent KV is what you keep on disk/host SSD to reuse a prefix next turn instead of re-reading it. Both have tight limits: HBM size, SSD size, and the bandwidth to move caches around. Together they cap how many agents you can serve and how much each agent costs.

DeepSeek-V4.1-Flash was built to push those limits directly. It is a 552-billion-parameter backbone that can handle 1M tokens, but it is taught to act much smaller. Thanks to the tricks in the next lessons, its global KV footprint — always in HBM — is just 890 bytes per token. That is about 1/4 of DeepSeek-V4-Flash and about 1/437 of the original DeepSeek-V1. Its persistent footprint — always on SSD or host — is about 1/8 of V4-Flash. Figure 1(b) shows that steady generational drop. And despite the much smaller memory, it scores higher than V4-Flash on agent tasks.

The rest of the course explains how: halving the reading, sharing notes across layers, searching less, writing in shorthand, and replaying just enough to forget safely. The paper also details training on 45T tokens and many deployment optimizations that go beyond this introductory view.

Try it: use the lab to turn “bytes per token” into real gigabytes. Drag context length from 4K to 1M and toggle HBM vs SSD to feel why cache compression is a deployment-cost story, not just a clever math trick.

002Background you need~7 min

How an AI pays attention

Imagine you are answering a long chat. For every new word you write, you glance back at the words you have already seen and ask: which old words matter most for this next word?

That glance is what researchers call attention. In the words the paper uses, the new word makes a Query (Q). Every old word has left behind a Key (K) — like a label saying “I am about this topic” — and a Value (V) — the actual meaning to mix in. For a new token, the model does three steps:

  1. Score: compare its Query to every old Key with a dot-product. Big score means “this old word looks relevant.”
  2. Weigh: turn those scores into weights that add to 1 (a softmax — just a fair way to share 100% of attention).
  3. Mix: make a weighted average of the old Values using those weights. Tokens with higher weight count more.

If a model does step 1 against all past tokens, that is full attention. It can reach any far fact — but for a million-token prompt it is huge to store and to scan every time.

So DeepSeek-V4.1-Flash uses two cheaper helpers together. Sliding-Window Attention (SWA) only scores the last W = 128 tokens for each query. That size never grows with context length, so it is cheap and bounded. The downside: it cannot see a definition from 10,000 tokens ago.

Sparse global attention fixes that. A tiny indexer quickly scores all past entries and picks just the Top-K = 512 best ones for the real attention to read. Think of an index at the back of a book — you do not reread every page, you look up the few pages the index points to. Each layer then attends to its local window plus those 512 distant picks.

Why a 552B model can act like 16B: Most layers are Mixture-of-Experts (MoE). The backbone has 552 billion parameters in total, split into 384 specialist experts plus 1 shared expert per MoE layer. For each token the router wakes only 6 routed experts + 1 shared expert. So the model has a huge library, but only a tiny team works on any one word — 8B active in prefill, 16B in decode.

One last split helps everything else click: prefill means reading the whole prompt at once (say N tokens), while decode means making one new token at a time and reusing the stored Keys and Values — the KV cache — instead of recomputing them. Prefill is heavy on math. Decode is heavy on memory reads. The next lessons shrink both.

Try it below: drag the blue query word along a 60-word strip. Switch between Full, SWA (last 8), and Sparse Top-6 + local. Watch how many tokens it can see, which distant words it keeps, and how the weight bars change. The bonus grid shows how MoE picks just 7 experts out of hundreds for each token.

For the curious — the math behind the toy: for query q and keys kj, score sj = q·kj / √d. Weights wj = exp(sj) / Σ exp(si). SWA sets sj = -∞ when query - j ≥ W. Sparse keeps W local plus the Top-K scores elsewhere. MoE output is Σ ge·Experte(x) over the chosen experts with router weights ge.

003Idea 1: do half the work~7 min

Doing only half the reading

Imagine you have to read a 40-page packet before you can answer. Normally someone at a factory has to copy all 40 pages for every new question. That's prefill: handling every one of the $N$ prompt tokens through all $L$ layers, work that grows like $N \times L$.

DeepSeek-V4.1-Flash splits those 40 layers into two halves: a 20-layer causal encoder that reads the whole prompt, and a 20-layer decoder that will write the answer. Here's the shortcut: the decoder doesn't rebuild its big global memory from its own pages. It gets it projected straight from the encoder's final notes.

The decoder's global memory for every layer above half is just a projection of the encoder's last state. In words: take the hidden state after layer $L/2$, call it $H_{L/2}$, and multiply it by a small learned matrix for that layer.
$$C_{l}=H_{L/2}\,W_{l}^{KV},\quad Z_{l}=H_{L/2}\,W_{l}^{Z},\quad \text{for } l > L/2$$
Here $C_{l}$ is the decoder's global key-value memory at layer $l$, $Z_{l}$ is its compression weight, and $W_{l}^{KV}, W_{l}^{Z}$ are the layer's own projection matrices. All 20 decoder layers reuse the same $H_{L/2}$.

What about the local memory, the sliding window ($n_{win}=128$ tokens in this paper)? That part still comes from each layer's own work, layer by layer. So you keep full local detail, but you skip the heavy global recomputation during prefill.

Count the work. Without the trick: about $N \times L$ operations. With the trick: $N \times L/2$ for the encoder plus a tiny fix-up of $n_{win} \times L/2$ tokens to rebuild the decoder's sliding windows. For a long prompt where $N$ is thousands and $n_{win}$ is only 128, that's roughly $N \times L/2$, or about half. The paper makes this exact — it activates only 8B parameters per token during prefill, but still uses the full 16B during decode when it actually writes.

That half-saving shows up everywhere agents pay most: reading big codebases and long chats. And for writing, look at Figure 2 below: the cost to make one new token stays almost flat even as context jumps 256-fold from 4K to 1M tokens — only about a 25% rise for V4.1-Flash, versus a steep climb for earlier models. The paper weights cheaper math as smaller (BF16 counts as 1, FP8 as 0.5, FP4 as 0.25), so part of that flatness comes from using fewer bits too.

004Idea 2: share notes~8 min

One set of notes for many floors

Imagine a 40-story building where every floor keeps its own copy of the same million-page library. That's what early long-context models did: each attention layer stored its own full set of notes for every token it had seen. Useful, but wildly wasteful.

DeepSeek-V4.1-Flash asks: what if floors share notes? Its trick is called Compressed Sparse Attention 2 (CSA2). It squeezes memory three ways at once, and the biggest win comes from the third way — sharing across layers.

📦

1. Smaller entries

Each stored value is shrunk from 16 bits to 4 bits (more in the next lesson).

🗜️

2. Fewer entries

With compression ratio m=2, two tokens are squeezed into one stored entry. m=1 means no squeezing.

🔗

3. Fewer copies

Most layers don't store their own copy at all — they borrow from another layer. This lesson is about #3.

CSA2 also cleans up the design. Compared to the earlier CSA in DeepSeek-V4, it drops the overlapping 2m source entries and the extra positional embedding during compression, and it creates the small search keys — called indexer K — by projecting them directly from the stored main memory (main KV), instead of via a separate path. Same job, simpler plumbing.

Every CSA2 layer is given one of three jobs when the model is built. All three still make their own query (Q) and keep their own local sliding-window memory (SWA KV, the last 128 tokens), so local detail is never shared. What differs is the long-range part:

  • Full mode: makes its own main KV and indexer K, and runs the helper search to pick fresh Top-512 most useful entries. This is the librarian who builds a new shared shelf.
  • Reindex mode: reuses the main KV and indexer K from the last Full shelf, but rescores them with its own query to pick a fresh Top-512. Same books, personal short-list.
  • Reuse mode: reuses both the main KV and the Top-512 list picked by the last searching layer. No new search at all. Just read what your neighbor found.

Sharing the KV and the Top-512 list is what cuts storage. Skipping the search is what cuts compute.

The paper's concrete layout makes the trade-off clear. The encoder has 18 CSA2 layers (m=2) in 3 groups of 6: each group has 1 Full + 5 Reuse. The decoder has 20 layers (m=1) in 5 groups of 4: the first group is 1 Full + 3 Reuse, the other four groups are 1 Reindex + 3 Reuse. That's only 4 layers that ever create a new long-range copy, serving all 38 CSA2 layers. In the paper's numbers, that is 32 indexer heads (dim 128), Top-K = 512, 64 query heads (dim 512), and n_win = 128. Together with FP4, it lands at 890 bytes per token in HBM — roughly one quarter of DeepSeek-V4-Flash.

005Idea 2b: search less~7 min

Don't re-search the whole haystack

Imagine an AI reading a whole codebase. To answer your question it has to find the few useful notes among a million past tokens. In the last lesson those notes were shared across layers — but sharing alone doesn't solve the searching.

Even if layers reuse the same memory, each indexer that chooses which notes to read would still have to score every past token. At 1 million tokens, that's 1 million scores per query, per deeper layer. That's the bottleneck the paper attacks next.

The fix is a two-step shortcut, used only in the decoder and learned during training: first narrow the whole stadium to one section, then search only that section.

Here's how the Hierarchical Sparse Indexer does it. The first layer in Full mode still does the full scan — it scores every causally visible position. But it doesn't just keep its own Top-512 for attention. It also votes by blocks: each block of 8 consecutive positions gets the maximum score inside it, the 2,048 highest-scoring blocks are kept, and all their positions become a candidate pool.

That's $2{,}048 \times 8 = 16{,}384$ positions. The example numbers are from the paper: 2,048 blocks, 8 positions per block, pool 16,384, final Top-K 512.

Later layers behave differently. A Reindex layer reuses the same shared memory, but it only scores inside that 16,384 pool and picks its own fresh Top-512 within it. A Reuse layer does no scoring at all and just copies the latest Top-K. The pool is fixed in size, so the work for every deeper indexer no longer grows with context length — it's constant, or $O(1)$.

Why constant? If context is $N$, a normal indexer costs about $N$ scores per query. With a pool of size $P=16{,}384$, deeper indexers cost $P$ scores per query, no matter if $N$ is 64K or 1M. The first layer still costs $N$, but you pay that once, not in every layer.

Without this, even with cross-layer sharing, each Reindex layer would still scan 1M entries. With it, DeepSeek-V4.1-Flash can keep its per-token decode cost nearly flat all the way to 1M tokens — that's the flat curve you saw in Figure 2.

006Idea 3: tiny numbers~7 min

Writing notes in shorthand

Think of an AI's memory as a page of handwritten notes — one line per past token, full of numbers. The smaller you can write each number, the more pages fit in your pocket. DeepSeek-V4.1-Flash does exactly that: it shrinks the numbers themselves.

There are three sizes of handwriting. BF16 uses 16 bits per number, FP8 uses 8 bits, and FP4 uses about 4 bits. Cutting from 16 to 4 should cut memory by 4×, and the paper counts it that way when it measures compute: it weights a BF16 operation as $1$, FP8 as $0.5$, and FP4 as $0.25$. Halve the bits, halve the bytes in HBM (the fast memory next to the chip) and on SSD (the long-term storage).

V4 already wrote its little helper notes — the indexer queries and keys — in FP4, using training that knew about the rounding in advance. V4.1 goes further and writes the main KV cache — the big memory that holds the compressed global context — in FP4 too.

How do you write in 4 bits? You pick a tiny alphabet and share a magnifying glass. The chosen format is E2M1: 1 sign bit, 2 exponent bits, 1 mantissa bit. That gives only 8 positive levels — $0, 0.5, 1, 1.5, 2, 3, 4, 6$ — plus their negatives. Every group of 16 numbers shares one E4M3 scale (an 8-bit scale) that says how big "1 unit" is for that group. So a value is stored as scale × level.

Why is that safe to do without a second, global scale (which NVFP4 normally adds)? Because you need enough range to cover the biggest number you'll see. That format can represent up to $448 \times 6 = 2688$, since the biggest E4M3 scale is $448$ and the biggest E2M1 level is $6$. DeepSeek checked its real numbers: after its normalization, a KV value is at most about $\sqrt{512} \approx 22.6$, and in training the biggest seen was around $10$. So $2688$ is over 100× larger than needed — dropping the extra global scale loses no accuracy and makes the layout simpler.

Two details matter. First, the rounding happens after RoPE (the rotation that encodes position), because that worked just as well and is cheaper during decoding — and SWA KV, the short local window, stays in FP8 because it is more sensitive to rounding. Second, this is not post-hoc rounding after training. It is quantization-aware training (QAT): during training the model actually practices with the "snap to grid" step, then de-quantizes before attention, so it learns to be robust to the coarser grid.

Together, this FP4 main cache plus the sharing trick from the last two lessons (CSA2 cross-layer reuse) is what pushes the global KV from V4-Flash down to $890$ bytes per token — about $1/4$ as big. And as a free bonus, the paper squeezes the glue between layers too. Normally three small kernels shuffle the residual streams around; Single-Pass mHC shifts the mixing coefficients by one block — using $A_{l-1}$ instead of $A_l$ in $$X_{l+1}=B_l X_l + C_l\,\mathcal{F}_l(A_{l-1}X_l)$$ — so one fused Mega-mHC kernel can do it all, cutting ideal activation traffic from $(4n+4)d$ to $(2n+2)d$, about half.

007Idea 4: cheap remembering~7 min

A good-enough replay

Imagine your laptop saved every chat forever. That's what the persistent KV cache does: it keeps past turns on SSD or host memory so you can resume instantly for up to 72 hours. In DeepSeek-V4, about half of that always-stored baggage was the sliding-window memory — called SWA KV.

That sounds odd, because SWA is tiny by design. Each layer only remembers the last $W=n_{\text{win}}=128$ tokens. But V4 had to snapshot that little window at two places — the end of your prompt and the end of the model's answer — for every layer. $L$ layers × $W$ tokens, times two snapshots, adds up. For short, choppy chats with many turns, you were paying to store almost half your SSD budget on notes you'd only need for a few minutes.

Why not just throw the SWA notes away and recompute them when you need them? In theory you can. In practice, exact recomputation is brutal. A sliding window stacks: layer 2's window depends on layer 1's window, so to rebuild all $L$ layers perfectly you must re-run the last $L \times n_{\text{win}}$ tokens. With 40 layers and $W=128$, that's 5,120 tokens — even if your new message is just "ok, fix it." DeepSeek-V4 tried this idea as "Zero SWA Caching" and found the compute cost too high to ship.

The paper's fix is to be approximate on purpose. SWA Bounded Replay replays only the last $n_{\text{win}}$ tokens (128, not 5,120) and, for any query at position $i$, truncates its window to $[\max(s,\,i-W+1),\,i]$ where $s$ is where the replay started. The left edge is a little wrong — but experiments show the answer quality barely moves.

This one trick is used in two places. Encoder SWA Bounded Replay lets the long-lived prefix cache depend only on the small global memory. SWA memory is no longer kept on SSD at all; instead it lives in a tiny pool carved from 10% of host RAM, with a TTL of minutes, not days. It recycles fast enough to cover almost all live sessions. When you hit global memory but miss SWA memory — which now always happens — the system just replays $W$ tokens to fake the local context.

Decoder SWA Bounded Replay does the same for the 20 decoder layers in the new Causal Encoder-Decoder design. Without it, you'd still need to run the decoder over $L/2 \times n_{\text{win}}$ tokens just to build decoder SWA for the first decode steps. With bounded replay you always run only $W$ tokens through the decoder, no matter how long the cached prefix is. The decoder's rebuilt SWA is also approximate and is used only for decoding, never written back to the cache.

Put together with the earlier shrink of global memory to one-quarter, dropping SWA from disk cuts what must live on SSD to roughly one-eighth of V4. That's the trade-off the paper wanted: pay a tiny bit of extra prefill (replaying $W$ tokens) to save a huge amount of persistent storage — and keep the per-layer work down to 15 kernels in prefill and 11 in decode for the cheap Reuse layers.

008So what?~8 min

What we can afford to remember now

Imagine you could keep a whole library in your backpack, but the backpack never gets heavier. That is what DeepSeek-V4.1-Flash tries to do for AI memory. After the tricks in the last lessons — halving the reading, sharing notes across floors, searching a short list, writing in shorthand — the question is: did the backpack stay light and did the grades go up?

First, how much was remembered during training. The team pre-trained on 45 trillion tokens of text and images together, kept as a 7-to-1 mix of text to multimodal data. That is 45,000,000,000,000 tiny word-and-image pieces. The backbone has 40 layers with hidden size 5,120, organized as 20 encoder layers and 20 decoder layers. Each layer has 1 shared expert plus 384 specialists and wakes only 6 per token. That is why the model totals 552 billion backbone parameters but activates just 8 billion during prefill (reading the prompt) and 16 billion during decode (writing the answer). For comparison the earlier Pro model was about three times larger — 1.6 trillion total parameters vs 552 billion here, so Flash is roughly 1/3 the size — and it activated about three times more per token (49 billion vs 8 billion/16 billion).

Training ran in stages: most tokens at 64 thousand length, then stretched to 1 million at 34 trillion tokens. Learning rate warmed up for 2,000 steps to 2.6×10-4, held to 28 trillion, then coasted down to 2.6×10-5 by 40 trillion. The vision encoder itself (32 layers, 16 heads) first learned from 47 billion image-text pairs at small 224-pixel size, then was sharpened on 236 billion tokens of charts, OCR and code at up to 1,344 pixels.

Base-model payoff: With only about 1/3 total and 1/4 active parameters of V4-Pro-Base, V4.1-Flash-Base matches or beats it. In Table 1: MMLU-Pro 74.1% vs 73.5%, BigCodeBench 60.6% vs 59.2%, HumanEval 79.4% vs 76.8%, GSM8K 93.0% vs 92.6%. And on all held-out sets it has the lowest bits-per-byte — meaning it predicts the next token better.

Post-training added reasoning and agentic skills with the usual recipe — supervised fine-tuning, then reinforcement learning, then on-policy distillation — no new algorithm, just much more diverse synthesized tasks and environments. On agentic code tests Flash leaps past its predecessor and sits with the frontier closed models: Terminal-Bench 2.1 90.6% beats Opus-5 at 89.1% and GPT-5.6 Sol at 88.8%; DeepSWE v1.1 74.2% edges Opus-5 74.0% and GPT-5.6 Sol 73.0%, up from 54.4% for V4-Flash; Automation-Bench 54.8% and CyberGym 88.1% are best among open models. MathArena Apex stays level at 65.6% and Codeforces rises to 3471 from 3289.

Where does the gap remain? On the hardest science-oriented agentic tests, Flash still trails: Terminal-Bench 3.0 30.0% vs 43.3% for Opus-5, and Terminal-Bench 4.0 31.2% vs 51.8%. Multimodal visual agents beat the best open rival Kimi-K3 but not the biggest closed systems. The paper is also honest about fragility: because CSA2 sometimes picks the wrong Top-512 and SWA Bounded Replay is approximate, extreme long-context retrievals or odd cache-resume edges have not all been stress-tested.

The effort knob — in one formula: At deployment you pick a scalar effort b from 1 to 100. Public API tiers map to low=50, high=75, max=100. During training the length penalty is $$k(b)=k_0 \exp\!\left(-\frac{b-b_{\min}}{\tau}\right) \quad\text{and}\quad r^{len}_{b,j}=-\min\!\left\{C_{\max},\,k(b)\frac{\ell_{b,j}}{L_{norm}}\right\}$$ $\ell_{b,j}$ is reasoning tokens, $k(b)$ shrinks exponentially with $b$. Low $b$ = strong penalty, short answer. High $b$ = weak penalty, longer reasoning. Going 25→100 lifts the 8-benchmark average 67.1% → 76.3% at ~2.5× tokens, but most gains come by 60–80 — the last step to max costs 1.6–1.8× agent tokens for a small bump.

Put together, the memory diet worked: a Reuse-mode layer now runs in just 15 fused kernels for prefill and 11 for decode, EPD disaggregation lets vision, prefill and decode scale separately, and you get a cheaper million-token assistant that is also smarter. Try the lab below: compare Flash to its predecessor and to closed models across benchmarks, then drag the effort slider and watch accuracy climb with diminishing returns — that is the cost-quality trade-off you can actually choose at runtime.

ABCWord bank

Word bank.

KV cache

The short-term memory an AI keeps while reading. For each token it has seen, it stores two lists of numbers (Keys and Values) so it doesn't have to recompute them when generating the next word.

HBM and SSD

Fast memory right next to the AI chip (HBM) vs. slower, much larger storage (SSD on disk or host RAM). The paper shrinks what must live in each.

prefill vs decode

Reading the prompt in one big batch (prefill) vs. generating one new token at a time (decode). Prefill is heavy on compute; decode is heavy on memory reads.

attention (Q, K, V)

How AI decides which past words to look at. It makes a Query from the current word, compares it to Keys of past words, and mixes their Values.

sliding-window attention (SWA)

Attention that only looks at the last n_win tokens (128 in this paper), not the whole million. Cheap, but blind to far-away info.

Mixture-of-Experts (MoE)

An AI with many specialist sub-networks (experts). Only a few experts are woken up per token, so total parameters can be huge while active ones stay small.

compression ratio

Keeping many tokens as one combined entry. Ratio m=2 means two tokens share one stored entry, halving storage.

indexer / Top-K

A tiny helper that scores every past entry and picks the most useful Top-K (512 here) for the real attention to read.

quantization (FP4, FP8, BF16)

Storing numbers in fewer bits. FP4 means about 4 bits per number instead of 16 (BF16) or 8 (FP8) — much smaller, but less precise.

bounded replay

Re-computing only the last n_win tokens to fake the missing sliding-window memory, instead of replaying L × n_win tokens or storing it forever.

backbone vs activated parameters

All weights in the model (552B) vs. how many actually run for one token. Here 8B in prefill, 16B in decode.

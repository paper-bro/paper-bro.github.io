001The problem~6 min

Why loop a model instead of making it bigger?

Imagine you need a 112-story tower. You could buy 112 different floors and stack them — that's a normal big model. Or you could buy just 28 floors and run the elevator through them 4 times, re-using the same floors over and over. You save storage space, but you pay with extra trips.

That trade-off is why looping matters right now. Modern AI chips get faster at math much more quickly than they get more memory. The paper cites this hardware trend [1] as the motivation: we can afford more computation, but we cannot easily afford to store ever-more parameters.

A looped model re-uses the same physical Transformer block T times. Resident = what you store (e.g., 28 layers ≈ 730M parameters). Logical = what you execute when you count re-uses (e.g., 112 passes ≈ 2.9B unrolled). Memory stays flat; compute grows.
🔁

Ouro-family

R284 — tie the whole 28-block stack and run it ×4.
28 × 4 = 112 logical executions.

🥪

Huginn-family

P8R128C8 — 8 untied prelude layers, a 12-block core ×8, 8 untied coda layers.
8 + 12×8 + 8 = 112 logical.

Both families end at the same logical height — 112 — with the same 28 layers stored. The paper makes this apples-to-apples: same dense scale (~730M resident / 2.9B unrolled), same logical depth, same data (TxT360) and same training tokens, tested at 42B, 84B, 168B and 336B tokens (58 to 460 tokens per parameter). Even the sparse MoE version later is matched the same way: 8B resident loop vs 32B feedforward for the same 3.2B unrolled-active compute.

But until now, everyone compared whole recipes that bundled three knobs together. The authors write one shared recipe with five equations: a prelude P, how the loop starts φ, whether you re-inject the input each lap W, the repeated body R, and a coda C. Ouro vs Huginn differ on all three at once — where the loop sits, whether you re-inject, how you start — so you can't tell which knob actually helped.

The cleanup in this paper is to turn Ouro into Huginn one knob at a time from scratch and measure. Try the seesaw below: pick Ouro and Huginn presets to see how both reach 112 without storing 112, then drag the loops to feel why resident memory stays low while compute climbs.

002Background~7 min

What's inside a Transformer tower? A one-lesson crash course

Think of a language model as a tall tower of identical Lego chunks. Each chunk is one Transformer block: first it lets words pay attention to each other, then it runs each word through a little feed-forward calculator. The paper uses the same decoder-only design for every model, so the tower shape — not the brick — is what changes.

In this paper a block is always: attention with 24 query heads and 6 key-value heads (head size 64, RoPE base 1e6 to encode positions) plus a SwiGLU feed-forward layer. Hidden size is 1536, so each block turns a list of 1536-number vectors into a new list of 1536-number vectors, keeping the length the same.

The paper writes the whole journey with five short equations, but they are just an assembly line. Starting from tokens x:

$$\mathbf{x}_0 = E_{\theta}(\mathbf{x}) \;\;\text{(look up embeddings)}$$
$$\mathbf{e}=P_{\theta}(\mathbf{x}_0) \;\;\text{prelude: first few blocks run once}$$
$$\mathbf{z}_0 = \phi_{\theta}(\mathbf{e},\bm{\xi}) \;\;\text{how the loop starts}$$
$$\tilde{\mathbf{z}}_t = W_{\theta}(\mathbf{z}_t,\mathbf{e}) \;\;\text{optionally re-inject the input, then } \mathbf{z}_{t+1}=R_{\theta}(\tilde{\mathbf{z}}_t)\text{ for }T\text{ loops}$$
$$\mathbf{h}=C_{\theta}(\mathbf{z}_T) \;\;\text{coda: last few blocks run once}$$

Pθ is prelude, Rθ is the tied recurrent core that is reused, Cθ is coda. Wθ is the per-step input write, φθ is the initializer that sets the loop's starting state, sometimes from the prelude e and sometimes from random noise ξ.

Resident vs unrolled — stored vs executed. Resident layers = how many distinct blocks you store: P + R + C. Logical depth = how many block-executions you run: P + R×T + C. Both Ouro and Huginn store 28 layers but execute 112: Ouro as $28 \times 4 = 112$ (write as $R_{28}^{4}$), Huginn as $8 + 12 \times 8 + 8 = 112$ (write as $P_{8}R_{12}^{8}C_{8}$). Unrolled parameters count the same idea in parameters: 730M stored becomes 2.9B applications when unrolled.

For the MoE models the paper keeps attention, normalization and residuals exactly the same and only swaps that feed-forward calculator. Instead of one dense SwiGLU (width 4352), each block gets 25 SwiGLU experts (width 2432 each) and a router picks the top-2 per token with a sigmoid score. No shared experts. That is why the MoE loop still stores 8.0B resident (32B unrolled) but only uses 793.9M active per pass — about 3.2B unrolled-active after looping — see Table 6 geometry.

The two feedforward baselines anchor everything: D28 has 28 distinct blocks and matches resident count; D112 has 112 distinct blocks and matches logical depth. Use the lab to build your own sandwich and watch resident stay flat while logical depth grows with loops.

Try it: start with Huginn — 8 prelude, 12 recurrent, 8 coda, 8 loops = 112 logical. Now drag to Ouro — 28 recurrent, 0 prelude/coda, 4 loops = also 112. Toggle to MoE view to see how 8B stored can do 32B worth of work. What happens to resident when you add coda layers but keep loops the same?

003Framework~7 min

The paper's big cleanup: three separate choices

Think of a chocolate-chip cookie recipe. One bakery loops the whole dough 4 times. Another makes a starter, loops just the middle 8 times, then adds a finish. If you taste the final cookies and one is better, what made the difference — the starter and finish, the extra reminders of the recipe, or the way they started the dough?

This is exactly what happened with looped models. Two families — Ouro and Huginn — both reused weights to reach the same total work (112 logical layer-uses from 28 stored layers), but they bundled three choices together. Comparing the final cookies can't tell you which ingredient mattered.

The paper's cleanup is to write every looped model the same way, in five short steps:

$$\mathbf{e}=P_{\theta}(\mathbf{x}_0)\qquad \mathbf{z}_0=\phi_{\theta}(\mathbf{e},\bm{\xi})\qquad \tilde{\mathbf{z}}_t=W_{\theta}(\mathbf{z}_t,\mathbf{e})\qquad \mathbf{z}_{t+1}=R_{\theta}(\tilde{\mathbf{z}}_t)\qquad \mathbf{h}=C_{\theta}(\mathbf{z}_T)$$

In plain words: e is what you get after the prelude P reads the token embeddings x0. z0 is how you start the loop (φ). W is whether you re-inject the input before each lap. R is the tied middle block you actually loop T times. C is the coda that decodes after the last lap. Ouro sets P and C to "do nothing" and never re-injects; Huginn uses 8 untied prelude layers, 8 untied coda layers, a 12-block core looped 8 times, and a weighted re-injection.

Key insight: with this shared notation, the three knobs separate cleanly — 1) envelope where the loop sits (P,R,C), 2) injection what and whether W reads, 3) state how φ starts the loop. Only then can you test one knob at a time while keeping stored layers = 28 and logical depth = 112 exactly matched.
🏗️

Envelope

Ouro: R28^4 (28×4). Huginn: P8 R12^8 C8 (8+12×8+8). Same math, different sandwich.

🔁

Injection

Keep reminding the loop of the input? α⊙z + δ⊙W_in e vs doing nothing.

🎲

State

Start from the input z0=e or from noise z0=ξ? Single state or two-level H/L?

That separation gives the paper its three fair questions — Q1 envelope, Q2 injection, Q3 state — each tested from scratch on the same data and token budgets. 004Q1: Envelope~7 min

Where you put the loop matters most

Imagine two ways to reuse the same 28 puzzle pieces to build a 112-step tower. In one, you stack the whole 28-piece chunk 4 times in a row. In the other, you build a special 8-piece entrance, then loop a 12-piece middle section 8 times, then add an 8-piece exit. Both reach the same height — 28 × 4 = 112 and 8 + 12×8 + 8 = 112 — and both store only 28 pieces in memory. The paper asks: does where you put the loop change what the model gets good at?

Call the first design the full-stack loop, written $R_{28}^{4}$ (R for recurrent body, 28 blocks, repeated 4 times). Call the second the sandwich, written $P_{8}R_{12}^{8}C_{8}$ (P = 8 untied prelude layers, then a 12-block loop 8 times, then C = 8 untied coda layers). Everything else — total stored pieces, total logical steps, data, and training time — is kept exactly the same. The only difference is the envelope: where recurrence lives.

To compare them, the paper uses $\Delta$, short for "difference." $\Delta$ = (sandwich score) − (full-stack score) on the same test. If $\Delta$ is positive, the sandwich wins. At the biggest training budget — 336 billion tokens, which is 460 tokens per parameter — the differences are striking:

Biggest wins are for step-by-step reasoning from what's in front of you: MATH500 $\Delta$ +12.00 (from 20.80 to 32.80), GSM8K +7.05 (54.97 to 62.02), DROP +2.61 (36.38 to 38.99), BBH-CoT +2.47 (45.83 to 48.30). Knowledge-heavy or strict-format tasks don't follow: ARC-Challenge $\Delta$ −0.94 and HumanEval+ −1.22.

Why that pattern? Think of the sandwich as giving jobs to different parts. The untied prelude learns to encode the input well once. The tied middle loop can then focus on refining an answer over and over without also having to remember how to decode it. The untied coda learns to decode the final refined state into words. When a task is "use the passage and work it out step by step" — like math word problems or DROP's passage questions — that division helps. When a task is mostly "recall a fact you memorized" or "follow an exact code-output contract," extra refinement alone doesn't help, and sometimes slightly hurts.

This isn't a one-time fluke. The paper checks the same two designs at four training budgets — 42B, 84B, 168B, and 336B tokens — and the sandwich's lead on MATH500, DROP, and BBH-CoT shows up at every checkpoint. That's the evidence for Finding 1 and Finding 2 in §3.4.1: the sandwich envelope consistently improves instance-conditioned, multi-step derivation, but does not consistently improve stored-knowledge or strict-spec tasks.

005Q2: Input injection~8 min

Should each lap get a map refresher?

Imagine you’re doing 8 laps around a building to solve a puzzle. Would you want a fresh look at the map at the start of every lap?

That’s what input injection does. The model’s looping state is called $z_t$ — its working memory on lap $t$. The fixed input is $v$ — the map. Injection mixes them before the next lap:

$$ D(z_t, v) = \alpha \odot z_t + \delta \odot W_{in} v $$

In words: keep a weighted bit of your old thought ($\alpha \odot z_t$) and add a weighted bit of the projected input ($\delta \odot W_{in} v$). $\odot$ just means element-by-element multiply. $W_{in}$ is a learned projection that reshapes the input to fit the state.

Where do $\alpha$ and $\delta$ come from?
They’re not hand-picked. The paper uses a diagonal write from earlier work [5]: $\delta = \text{softplus}(b_\delta)$ (a smooth positive version of $b_\delta$) and $\alpha = \exp\{-\delta \odot \exp(a)\}$ (so if you inject more $\delta$, you automatically keep less of $z_t$). Two tiny learned vectors $b_\delta$ and $a$ control the blend.

The paper tested two maps. In the sandwich model $P_8R_{12}^8C_8$, the map is $v=e = P_\theta(x_0)$ — the 8-layer prelude’s contextualized reading of the tokens. In the full-stack model $R_{28}^4$ (no prelude), the only map available is $v=x_0$ — the raw token embeddings.

📄

Helps when answer is in the prompt

At 336B tokens, adding the prelude-write improved BBH-CoT +6.63, HumanEval+ +5.49, MBPP+ +4.23, MMLU +2.53, DROP +1.39. All need to recover instructions, examples, or a passage later. Raw-write helped full-stack too: BBH +1.80, MBPP +4.50, HumanEval +2.44.

🧮

Can hurt when you must wander away

Same mid-loop write hurt MATH500 −3.60 and GSM8K −2.51 (full-stack hurt less: MATH −1.60, GSM8K +0.53). Repeatedly yanking the state back toward the input may stop it from building up intermediate math steps.

Net result? The injected sandwich still wins overall. With injection on for both, the prelude-loop-coda model beats the injected full-stack on 8 of 10 benchmarks (losing only ARC-Challenge and HellaSwag). The envelope advantage from Lesson 4 makes up for the math dip.

006Q3: State design~7 min

Do fancy starting states or brains-within-brains help?

Imagine two ways to start a relay race. In one, you start exactly where your teammate handed you the baton. In the other, someone drops you at a random spot and then keeps shouting the original directions. Which helps you finish faster? The paper asks the same about looped models: where should the loop's memory start, and should it have one workspace or two?

Earlier lessons showed the two biggest wins: putting the loop in the middle (the sandwich) and re-injecting the prelude output each lap. Here everything else is frozen: the same P8R128C8 sandwich, the same prelude-write, the same 730M stored parameters and 112 logical executions, trained on 336B tokens (460 tokens per parameter). Only the latent organization changes.

That organization is the recipe for z0 — the first value of the recurrent stream before the first loop iteration. The paper tests three recipes:

  • Single state starting at e: $z_0 = e$, where $e = P_{\theta}(x_0)$ is the contextualized output of the 8-layer prelude. Plain words: start the loop exactly where the prelude left off.
  • Single state starting at random ξ: $z_0 = \xi$, with $\xi \sim \mathcal{N}(0, I_d/d)$. Plain words: sample a random cloud of numbers (mean 0, small variance $1/d$) and start there. The prelude output $e$ is still re-injected each step via $W_{\theta}$, so the random start doesn't erase the input.
  • Shared high/low (H/L) states: two workspaces sharing the same loop block $R_{\theta}$. $H=2$ slow cycles, $L=3$ fast refinements per cycle = 8 total body uses: $$ \bar{R}_{\theta}(s;e)=R_{\theta}(W_{\theta}(s,e)) $$ $$ z_{L}^{i,j+1}=\bar{R}_{\theta}(z_{L}^{i,j}+z_{H}^{i};e),\quad z_{H}^{i+1}=\bar{R}_{\theta}(z_{H}^{i}+z_{L}^{i,L};e) $$ Plain words: each fast L-update gets the current slow H-state added in, then goes through the shared block; each slow H-update gets the final L result added in. Same block, different additive conditioning.
Result at 336B tokens: neither fancy start helps reliably.
Random $z_0=\xi$ vs $z_0=e$: only 2 benchmarks improve by more than 1 point (ARC-C +3.34, GSM8K +1.22) while 4 get worse by more than 1 (MMLU −1.29, MATH500 −1.80, HumanEval+ −1.83, MBPP+ −2.11).
Shared H/L vs $z_0=e$: 3 gains >1 (ARC-C +2.23, DROP +1.80, HumanEval+ +1.22) but 3 losses >1, including MATH500 −7.20, GSM8K −2.19, MBPP+ −2.64. Full numbers are in Table 4 of the paper.

This doesn't mean random starts are useless forever. The authors stress what's not tested here: whether random starts help the model find the same answer from different starting guesses (path independence) or extrapolate to more loops than it trained on. In this matched setup with persistent injection $W_{\theta}$, random noise just adds sampling cost without consistent gain, and the shared H/L hierarchy adds scheduling complexity without consistent aggregate gain.

The paper also separates this from the fancier H/L in HRM-Text [56], which uses two different blocks for H and L. That version is still being evaluated and is not what was tested here.

007MoE transfer~8 min

Do the lessons survive when experts join?

You've seen the sandwich envelope help math and the daily reminder help context tasks. But those were tiny-ish dense models where every block does the same job. What happens when we swap each block's inner MLP for 25 specialists and only call 2 per token?

That's a Mixture-of-Experts, or MoE. Think of a hospital: 25 doctors on call per floor, but you only pull in 2 for each patient. The whole building has way more doctors total (resident parameters), but each patient only sees a few (active parameters). The paper keeps everything else the same and asks: does Huginn still beat Ouro when both get experts?

Setup is carefully matched. Every feed-forward is replaced by 25 SwiGLU experts, width 2432, top-2 routing. Both looped models have the same 28 routed physical layers: 8.0 billion resident parameters, but only about 0.794 billion active per pass. Loop it and you count reuses: about 32.0 billion resident-equivalent and 3.2 billion unrolled-active. They train 500 billion tokens — that's about 630 tokens per active parameter — on the same data. The giant reference is a normal 112-layer feedforward MoE with 32.0 billion residents, same logical depth and same compute budget.

Result: Huginn still wins 8 of 10. At 500B tokens, Huginn_MoE minus Ouro_MoE (Δ) is GSM8K +4.70 (83.62 vs 78.92), MATH500 +3.60 (53.40 vs 49.80), MMLU +2.78 (66.81 vs 64.03), DROP +1.95 (59.65 vs 57.70), plus small wins on HellaSwag, TriviaQA, HumanEval+ and MBPP+. It only loses ARC-C −0.86 and BBH-CoT −0.20.

Why? Watch the experts. A perfect load would spread tokens evenly; lower load-balancing loss means more balanced. The paper reports a normalized loss where uniform = 1.0. At 500B, Huginn is 1.571, the feedforward giant is 1.652, Ouro is 1.899. Lower is better, so Huginn uses its experts most evenly.

It also uses them differently each lap. Across adjacent loop passes, the top-1 expert switches 49.4% of the time for the same token and layer. That isn't noise — it's useful. The authors froze the test: keep pass 1's expert picks for passes 2–8, but still recompute the mixing weights for those fixed experts. Accuracy fell on all 6 probes they tried: MMLU −11.2, ARC-Easy −9.6, BoolQ −8.7, ARC-Challenge −8.3, PIQA −1.5, COPA −1.0. Same weights allowed, different experts blocked = worse. So iteration-specific routing matters.

008Results & why matter~7 min

The payoff and what's still open

Think of two kitchens cooking the same 112-course menu. One builds 112 separate stations. The other keeps just 28 stations and runs the middle 12 stations on loop 8 times, with an 8-station prep area before and an 8-station plating area after. The second kitchen stores 75% less equipment but does the same amount of cooking — it trades storage for repeats.

That's the dense payoff. At 730M resident parameters and 336B tokens (460 tokens per parameter), the paper walks step by step from Ouro R284 — 28 blocks × 4 = 112 logical executions — toward Huginn P8R128C8 — 8 + 12×8 + 8 = 112. Adding the sandwich envelope (untied prelude and coda) and then the persistent input write drove the gains. Switching the start from z0=e to random ξ did not: 2 gains over 1 point, 4 losses over 1 point. A shared high/low workspace (H=2 cycles, L=3 updates per cycle, 8 body calls total) also showed no reliable win — 3 gains over 1 point, 3 losses over 1 point, with MATH500 down 7.20. The full Huginn-style build ends up beating Ouro on all ten benchmarks, but the credit goes to where you loop and that you keep whispering the input, not to fancy starting states.

Apples-to-apples means matched FLOPs. Unrolled-active counts parameter applications with reuse. Huginn MoE and the 112-layer feedforward giant both do about 3.2B unrolled-active applications per token. Huginn just stores the weights once (8.0B resident) instead of 112 times (32.0B resident) — hence 75% fewer stored parameters for the same work per token.

The payoff survives with experts. Replace every feed-forward with 25 routed experts (width 2432, top-2) and train to 500B tokens at about 630 tokens per active parameter. Huginn MoE still beats Ouro MoE on 8 of 10: GSM8K 83.62 vs 78.92 (+4.70), MATH500 53.40 vs 49.80 (+3.60), MMLU 66.81 vs 64.03 (+2.78), DROP 59.65 vs 57.70 (+1.95). More striking, against the 32B giant that never loops: Huginn MoE (8B) beats it on DROP 59.65 vs 56.81 and GSM8K 83.62 vs 80.82, ties MATH500 53.40 = 53.40, and stays close elsewhere. Averaged over benchmarks, the lag to the giant shrinks from 4.96 points in the dense world to 1.71 points with MoE, narrowed on 8 of 9 comparable benchmarks — and it shrinks that way all through training, not just at the end.

What's still open is honest about limits. The paper only ran one practical size — dense 730M and MoE 8B resident / 0.8B active (32B/3.2B unrolled) — not hundreds of billions. It did not repeat everything with many random seeds to map wobble. It left the fancier separately-parameterized H/L modules (as in HRM-Text) unevaluated, and it tested MoE only as whole recipes, not knob-by-knob like the dense ablations. Those matched MoE ablations, a full scaling ladder, and system co-design to turn the memory win into real speed are the next to-do list.

ABCWord bank

Word bank.

Looped / Recurrent Model

A language model that applies the exact same Transformer block(s) multiple times in a row, reusing weights to get more logical depth without storing more parameters.

Transformer Block

One reusable chunk of the model (attention + MLP with normalization and residual connections). In the paper hidden size 1536, 24 query heads, SwiGLU MLP width 4352.

Resident Parameters

Parameters actually stored in memory. Example: 28 physical blocks = 730M dense or 8.0B MoE resident.

Logical Depth / Unrolled Parameters

Total block executions when you count reuses. 28×4 =112 or 8 + 12×8 +8 =112 logical executions. Unrolled-active counts the same idea for active MoE parameters (0.8B → 3.2B).

Iteration Envelope (Pθ,Rθ,Cθ)

Where recurrence sits. Ouro: R28^4 (28-block stack ×4). Huginn: P8 R12^8 C8 (8 untied prelude + 12-block loop ×8 + 8 untied coda).

Input Injection / Input Write Wθ

Re-adding input information before each loop step: D(z_t,v)= α⊙z_t + δ⊙W_in v with δ=softplus(bδ) and α=exp{-δ⊙exp(a)}. Ouro variant uses v=x0 (raw embeddings), Huginn uses v=e=Pθ(x0) (prelude output).

Recurrent-State Design

How the loop state starts and is structured. φθ: Ouro z0=x0, Huginn z0=ξ~N(0, I/d). Shared H/L variant: 2 high cycles ×3 low updates =8 body applications with additive conditioning between H and L states sharing one Rθ.

Mixture-of-Experts (MoE)

Mixing many expert MLPs per layer and routing each token to the top-2 (here 25 experts, width 2432). Total stored = large, per-token active = small.

Load-Balancing Loss

Auxiliary loss measuring how evenly tokens spread over experts. Uniform =1.0, lower is better. At 500B tokens: Huginn MoE 1.571 < feedforward 1.652 < Ouro 1.899.

Expert Switch Rate

How often the same token/layer picks a different top-1 expert on next iteration. Huginn MoE mean 49.4% across adjacent iterations on 48-input probe set; freezing identities hurts accuracy.

Apples-to-Apples / Matched Controls

Models compared at same resident or active scale, same logical depth (112), same data (TxT360), same tokens (336B dense, 500B MoE) and matched training/inference FLOPs.

Benchmark Groups

The paper's three question groups: General knowledge (ARC-C, HellaSwag, MMLU, TriviaQA), Reasoning over context (BBH-CoT, DROP), Math (MATH500, GSM8K), Code (HumanEval+, MBPP+).

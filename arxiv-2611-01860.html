001The avalanche~6 min

Why Graphics Needed a Map

Imagine you have to read every paper about AI that makes 3D worlds. In early 2024 it was a stack you could carry. By September 2026, the survey collected more than 300 papers — and analyzed a set of 350 papers from January 2024 to September 2026 — and the pile was growing almost exponentially. This is Figure 1a: a curve shooting up. No small team can read that fast by hand.

There is a second problem. Even when two teams build the same thing, they call it by different names. The survey counted the names authors gave to the part that checks the work — “feedback module,” “verifier,” “critic,” “inspector,” and more — and the part that makes the plan — “planner,” “orchestrator,” “coordinator,” and more. Figure 1b shows a word cloud of those names. Without a shared vocabulary, you cannot tell that two papers did the same trick.

This survey’s answer to both problems was to build two things: 1) a unified taxonomy — a 4-part checklist that gives every system the same labels, and 2) an agentic literature system — an AI librarian that finds new papers, reads their text and figures, labels them with that checklist, and saves evidence so later runs can add papers or revisit old labels.

You will see that 4-part checklist in the next lessons. For now, think of the core idea: if we all describe an agent the same way, we can finally compare designs across 2D drawing, 3D objects, CAD, and animated scenes — even when authors used different words.

The survey is not just counting. By applying the same labels to 350 papers, it could spot patterns humans would miss: which kinds of feedback are most common, which fix-strategies are rising, and where different tasks need different tools.

002What counts?~7 min

Code + Eyes + Do-Over: What Makes an Agent Agentic?

Imagine two robot interns. You tell both: “build a chair.” Intern A writes code once, hits run, and slides the wobbly result across the table — missing leg and all. Intern B writes code, looks at what it made, says “that leg is floating,” fixes just that part, and checks again.

That look-and-fix loop is the whole idea here. In graphics, pictures are not painted pixel by pixel. They are built by code — modeling steps, shading programs that color surfaces, and physics simulators that make things fall or bend.

The survey in this course gives a strict test for when we can call a system agentic. It needs all three:

  1. An LLM makes some decisions — a large language model chooses what to do next, not a fixed script.
  2. It runs operations in a graphics program — it actually creates or changes content in Blender, FreeCAD, a shader, a simulator, etc.
  3. Feedback changes what it does next — what it sees after running (a render, an error, a physics wobble) influences the next action.
Think “Code + Eyes + Do-Over.” Code to act, eyes to see the result, and a do-over driven by what was seen.

That third rule is the filter. The paper says these are not agentic, even though they use AI:

  • A network trained from scratch to spit out a shape directly — no LLM deciding steps and no tool use.
  • A single-pass LLM that writes Blender code once and never looks at the render.
  • A system that only uses feedback later to train the model, or just to score the final image — feedback has to steer the next action during the task.

A multi-step pipeline can still count, as long as the LLM’s next choice depends on the graphics result. No do-over, no agentic.

Try it yourself below — build the same chair three ways and watch the checklist. Notice which builder actually earns the label, and how the same loop works whether the “eyes” are a rendered image or a physics test.

003A shared language~8 min

The 4-Piece Toolkit: A Common Language

Imagine 350 recipe books all describing how to make a cake, but one calls it “whisking,” another calls it “beating,” and a third calls it “aeration.” You’d think they were different steps — until you line them up side by side.

That’s what happened in graphics AI. More than 300 papers through September 2026 — 350 in the final set the survey analyzed — all build systems where an AI writes graphics code, runs it, looks at the result, and fixes it. Each paper invented its own words for the same parts. The survey’s answer: give everyone the same checklist.

📋

Specification

What you ask for and what you get.

🧠

Base Model

Which AI brain decides.

🔧

Harness

How it plans, checks, and fixes.

🎨

Interface & Tools

How it touches graphics software.

Specification has three sub-choices. Task: 2D Graphics (posters, charts, SVG), Static 3D (a CAD chair, a Blender cabin), or Dynamic 3D (a swinging door, a fluid sim). Input form: language like “make a cozy reading nook,” an image, a video, an existing 3D scene to edit, or a document like a paper excerpt. Output: a program (say, Blender Python), a structured spec (like a JSON layout a solver turns into furniture), an editable artifact (objects you can still move after), or just rendered image/video.

Base Model is the decision-maker. Type: an LLM reads text and code; a VLM also looks at images — for example, comparing a render to your reference photo; a Hybrid pairs them, like a Claude coder plus a Gemini critic. Training: most papers use models off-the-shelf with no extra training — just prompting. Some do supervised fine-tuning (show it many correct graphics programs) or reinforcement learning (reward it when the geometry is right). The survey found the first option dominates.

The big insight: teams mostly kept the same brains and innovated on how the brain is harnessed — how it plans steps, what feedback it sees, and when it patches vs restarts. You’ll explore that harness next.

Every paper in Tables 2–4 gets the same icons for these choices, so you can compare a poster-maker and a CAD-builder in one glance — even if the authors called the parts by different names.

Now build your own: in the lab, mix and match Task, Input, Output, and Base Model and see the plain-English description update. Watch for when a text-only LLM can’t actually see your image — and why staying off-the-shelf keeps costs low.

004Plan, act, fix~9 min

The Harness: Planning, Trying, Checking, Fixing

An agent that just writes code once will almost always get something wrong — a missing piece, a floating object, a wrong shade. The paper calls the machinery that lets it notice and repair the harness: the harness runs the code, shows the result back to the model, stores what happened, and decides how to try again.

First, how does it plan? The paper finds three levels. Hard-Coded means the order is fixed in advance, like assembly-line steps. Hybrid fixes the big stages but lets the AI decide how to do each stage — for example Articraft fixes the steps “make parts, then make joints.” Non Hard-Coded lets the agent invent the steps as it goes. Workflows can then be sequential (one after another), parallel (do different rooms at the same time), or graph-structured (a tree with branches to explore alternatives).

When feedback arrives, the agent needs an update strategy. The survey lists five, and a single system may use several:

  • Regeneration: throw away and remake the whole thing.
  • Local patch: fix just one part, like moving a single cap.
  • Rollback: undo to a saved checkpoint when a fix made things worse.
  • Replanning: change the plan itself, not just the artifact.
  • Candidate selection: try several versions and keep the best.
Key insight: over time, local patching rose from 50.0% to 83.0% of systems. Fixing a piece is usually cheaper and safer than restarting everything — especially when CAD operations depend on each other, while scene objects can be moved independently.

Fixing only works if checking works. The verifier is whatever judges the result, and the feedback signal is what it returns:

  • Verifiers: self (agent checks itself), critic (a second agent), programmatic (a geometry rule like “are parts connected?”), environment (run physics and see if it falls), human (you).
  • Signals: binary (pass/fail), score (0–100), ranking (A beats B), diagnosis (what is wrong and where), plus raw observations — images, scene structure, or error logs.

Finally, memory decides what the agent remembers. Working memory is the current call, short-term is this run’s history (past renders, past fixes), long-term is across tasks (reusable skills). Reach can be local (one sub-agent’s private notes) or global (shared). SceneSmith, for example, keeps scene checkpoints globally and restores them when critic scores drop; LL3M keeps render histories short-term to verify that lowering a detached hydrant cap actually attached before keeping it.

005Touching pixels~8 min

How Agents Touch Graphics: Tools, Actions, and What They See

How does an AI actually touch a 3D world? Not with hands — with code, forms, tool buttons, and sometimes mouse clicks. The survey found every system picks from the same small menu, but papers call the choices by different names.

First, the action type — the shape of the instruction the agent sends. Think of asking a workshop to make you a metal bracket:

  • Code / script: you hand over a full program with loops and variables. Most control, most ways to make a typo. Example: a Blender Python script that builds a hydrant and sets metallic = 0.6.
  • Structured spec: you fill in a JSON form the system understands, like {"part":"top","material":"metal"}. A solver or interpreter then builds it. Safer, but you can only say what the form allows.
  • Tool / function call: you pick a pre-made tool — set_material(top, metallic=0.6) — and give it arguments. Less to write than code, but limited to the tools exposed.
  • GUI action: you drive the app like a person: click, drag, type shortcuts. This reaches any human workflow, but the agent must find the button and remember what is selected.

A system can mix them — code remains code even if sent via a tool executor, and a GUI drag remains GUI even if encoded as a function call.

Second, the graphics software — how much help the app gives the agent:

  • Agent-native: built for agents, like Articraft’s SDK where parts, joints, and validation share the same named entities.
  • Agent-adapted: a normal app plus a helper layer that translates requests and returns structured state, like Blender with scene-query tools and curated viewpoint renders.
  • General-purpose: plain Blender Python, Manim, or FreeCAD GUI with no agent helpers. The agent must follow the app’s own conventions.

Whether the source is open is treated separately — closed tools can still have documented APIs.

Third, the tools and resources available. The paper groups tools into graphics operations (make geometry), perception models (see — segmentation, depth, or a VLM reading a render), and validators (check — collision, support, stability, or overlap solvers). Resources are the reusable knowledge: asset libraries, example trajectories, and docs/rules.

Key split: what you edit vs what you see. The survey insists we track them separately. An agent might edit code but observe only pixels (a rendered image). Pixels hide occluded geometry and physics state, so viewpoint choice matters. That is why BlenderAlchemy (left in the figure) pairs visual critique with program edits, while ShapeCraft (right) uses component structure to guide where a texture prompt applies.

Which brings us to representation — how the content is stored influences what can be fixed. Code keeps operations and dependencies; geometry keeps shape and topology (faces/edges you can address); scene structure keeps object identities and support relations; dynamic state keeps velocities and particle attributes; pixels keep appearance; learned state keeps embeddings. If your editable representation has no per-part UV mapping, you cannot fix a texture seam by editing it — no matter how clearly you see the seam in pixels.

Try it below: do the same metal-texture task four ways and watch which representation lets you be precise, which snaps to presets, and which depends on clicking the right pixel.

006AI reading AI~7 min

An Agent That Reads Science For Us

Try reading 350 papers by hand. They span CAD, animation, simulation and 2D design, they appear faster every month, and they often call the same idea by different names. You would drown.

The authors had the same problem. Their collected corpus grew to more than 300 papers through September 2026, and the final analyzed set held 350 papers from 2024 to September 2026. So they built a second kind of agent — not to make images, but to read science for us.

Think of it as an AI librarian with three jobs in a loop, shown in Figure 3 below.

1. Discovery — make a reading queue

First it searches. Like a researcher, it scans publication listings and the web with customized queries, refines the query when hits look weak (a ReAct-style loop), merges duplicates, checks that each version is the real published one, and de-duplicates related works. Then, given a date cutoff and a reading budget — say, “only 3 papers this run” — it ranks abstracts and fills a queue. Uncertain or unread candidates wait for the next run.

2. Annotation — read and label with evidence

Next it actually reads. It opens the full text and looks at figures and tables with dedicated tools, the same way the PaperQA2 approach does: gather supporting evidence before you decide.

It then assigns the unified taxonomy labels from Lesson 3 — specification, base model, harness, graphics interface — and writes down design insights and limitations. Crucially, it keeps facts separate from its own interpretation, notes exactly where each claim came from, and flags the case when evidence is too weak to be confident.

The paper ran this with GPT-6 Astra at medium reasoning effort, using research tools from the SWE-agent harness. The harness gives the model a portable “skill”: instructions plus resources it can reuse in other agent setups.

3. Curation — check and remember

Before saving, automatic checks run: are all required fields there? Do the labels use only allowed taxonomy terms? If not, the entry is returned for fixing. These checks catch missing or inconsistent entries, but — as the authors note — they do not guarantee the labels are correct.

Each paper is saved independently. That matters because records persist across runs. A new paper can be added next week without erasing old work, and an old annotation can be revisited when a new version appears or new evidence shows up.

Why this matters: without evidence plus persistence, you get a chatbot that confidently mislabels papers and forgets yesterday. With it, you get a living map you can verify and update. Table 1 in the paper shows the payoff: by comparing SubDGuide and PLAYGROUND with the same labels, the system makes clear why SubDGuide’s local-patch-plus-rollback keeps failing on missing components, while PLAYGROUND’s fixed early groups prevent recovery from early layout errors — different harness choices, different limits.

007From 350 papers~8 min

What 350 Papers Reveal

350 papers is not a reading list — it's an avalanche. The survey analyzed 350 papers from 2024 to September 2026, and counted 304 that use observation as feedback. With that many people inventing agents at once, the authors found the same trick described under five different names — so they needed a shared vocabulary before anyone could spot real trends.

Trend 1 is about eyes. Visual feedback is everywhere: 77.0% of those 304 feedback-using works rely on rendered images or video to check their work. That makes sense — vision-language models can look at a picture without a custom judge for every task. But one view is rarely enough: 58.2% combine multiple observation types, adding geometric measurements or physics tests that a picture alone can't show. Imagine judging a chair by a photo — you see the wobble, but you need a tape measure or a gravity test to know if it will actually stand.

The CAD vs scene split: Scene generation dominates visual and structural observations (“is the lamp on the table?”), while CAD generation dominates runtime observations — compile errors, invalid solids. A living room is judged by looking; a CAD part is judged by whether it builds at all.

Trend 2 is about fixing. CAD uses full regeneration — remake the whole thing — more often. Scene generation uses local patch — fix just one part — more often. Why? In a scene, objects are mostly independent: you can move one sofa without breaking the lamp. In CAD, operations depend on each other: change an early sketch and a later cut or join can collapse. That dependency makes tiny edits risky, so starting over is often safer.

And the field is learning to patch smarter: local patching rose from 50.0% to 83.0% across the analyzed period. Think “search-and-replace” beating “retype the whole essay.” A parallel trend explains how: documentation and rules reached 85.3% of records in the latest period — as agents get more specialized Blender, FreeCAD, and other APIs, they need the manual. For resources, scenes reuse asset libraries most (pull a ready-made chair from Objaverse), while CAD leans on documentation most (pick the right modeling operation).

Beyond the final picture: The survey notes benchmarks are shifting too (Fig. 5 in the paper). Instead of only scoring the last render, new tests like BlenderGym, VIGA, and CAD-World grade multi-step editing and the whole interaction trajectory — did the agent keep improvements, recover from mistakes, and follow constraints?

Numbers alone don't tell you why — play with the filters in the lab to make the four trends click. Switch between visual vs runtime feedback, CAD vs scene, and drag time forward to watch patching and docs climb, just like the paper's Figure 4.

008Making & what's missing~7 min

What Agents Can Make Today — And What Still Can't Make Reliably Yet

So what can these agents actually build today? The survey's application sections are like a showroom. And Fig. 12 shows one of its stars: SceneSmith.

SceneSmith doesn't place everything at once. It builds hierarchically: first the room walls, then big furniture, then tiny supported things like a lamp on a nightstand. For each stage, three roles take turns: a Designer proposes edits with structured tools, a Critic checks rendered views and object positions, and an Orchestrator decides: keep it, ask for a fix, or rollback to a checkpoint when the critic score drops. That rollback is the trick — without it, one bad placement poisons everything after.

Other systems show the same lesson: how you plan and fix must match how you touch graphics. VIGA does reconstruction from a photo with a code→render→inspect loop, but it strictly separates read-only inspection (move the camera, query object pose) from persistent edits. That lets it gather evidence before risking a change. FirePlace handles vague language like "put the vase on the shelf" by grounding words in real 3D surfaces — it colors surfaces, lets a VLM pick which ones you meant, then a solver computes poses that actually fit without collision. Articraft and Artisan build articulated objects (doors, drawers) with code that defines parts and joint axes, then test with geometric checks and even MuJoCo physics for collision and gravity — but Artisan adds an independent reviewer to make sure a fix that stops collisions doesn't also ruin the intended motion, like blocking a door from opening fully.

The common trick: co-design harness and interface. The representation you edit (code, geometry, layout, dynamic state) determines what you can fix, and the tools you give to observe and verify determine what you will notice.

Yet the survey ends with a clear warning: none of this is reliably solved yet. In Sec. 9 it lists open problems that show up across all tasks:

  • Multi-agent collaboration — how should specialists share knowledge when tools use incompatible representations?
  • Action orchestration — when should an agent write code vs call a tool vs click a GUI vs call a solver? Adaptive switching is still manual.
  • Agent-oriented languages — today's DSLs were made for humans. Agents might need clearer, solver-aided languages, but those may be unreadable to designers.
  • Long-horizon memory & planning — tracking decisions and dependencies over dozens of edits without letting early mistakes compound.
  • Transparency — exposing plans and edit history so users can see why something changed.
  • Human intent alignment — vague requests like "make it cleaner" or "move the stars lower" have many valid answers. Agents must know when to infer, when to show assumptions, and when to ask.
  • Reliable evaluation — VLM critics often miss subtle or physical errors, runs vary randomly, proprietary models hide whether the harness or the base model improved, and judging graphics still needs expert time.
  • Creativity & attribution — who authored what when outputs mix user material, retrieved references, and multi-tool assets?

The paper's final takeaway is hopeful but practical: its 4-dimension taxonomy is adaptive — the high-level structure can stay while categories grow as new tools appear. Evaluation must grow too: from "does the final image look good?" to "does the trajectory of edits generalize and stay editable?" And to help, the authors state they will release their agentic survey system publicly so the community can keep the map up to date.

In the lab, try being the future architect: you'll get a vague brief and must choose which open problem to tackle first. Watch how each choice helps — and what new trade-off it creates.

ABCWord bank

Word bank.

LLM / VLM

A big AI model trained on text and code that can write new code, explain ideas, and decide what to do next. When it can also look at images, we call it a vision-language model or VLM.

Agentic system

A system where an LLM doesn't just answer once, but acts in a loop: it does something in a graphics program, looks at what happened, and then decides how to fix it.

Harness

The helper software around the AI that runs its code, shows it the results, keeps its memory, and decides when to ask it to try again.

Verifier

A checker that looks at what the agent made and judges it. It can be the agent itself (self-check), a second AI (critic), a program that tests geometry, the physics simulator itself, or a human.

Taxonomy

A sorting system that gives every paper the same labels so we can compare them, even if the original authors used different words.

Design space

The four big choices every graphics agent needs: what it is asked to make (specification), which AI brain it uses (base model), how it plans and fixes mistakes (harness), and which graphics programs and tools it can touch (graphics interface).

Action type

How the agent tells the graphics program what to do: by writing code, filling in a structured form like JSON, calling a pre-made tool, or clicking buttons like a human would.

Representation

How the inside of a 3D thing is stored for editing. Examples: the code that built it, its shape (geometry), where objects sit (layout), what it looks like in a photo (pixels), or how it moves in a simulation (dynamic state).

CAD

Computer-Aided Design. A way of building precise 3D parts using operations like extrude, cut, and join, where every dimension can be changed later.

Benchmark

A test or dataset that checks if an AI made the right thing. For graphics it also checks the steps the agent took, not just the final image.

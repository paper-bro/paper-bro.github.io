001Lesson 1~6 min

Even a smart AI needs good instructions

Imagine you hire the smartest intern in the world — but you give them messy instructions, the wrong file passwords, and a shared inbox with no labels. They'll still fail. Flip it: clear instructions, tidy tools, and a helpful checklist can make even an average helper succeed.

That's exactly how today's AI agents work. The paper calls it:

$$\text{Agent} = \text{Model} + \text{Harness}$$

Model ($\mathcal{M}$) is the frozen brain — the big language model whose weights never change in this paper. Harness ($\mathcal{H}$) is everything around it: the system prompt that sets its role, the guardrails that say "never do X," the memory it carries, the tool tips, the skills and scripts it can call, the sub-agents it can delegate to, and the little plug-ins that tidy its work. Change the harness, and the same model behaves like a different agent. The authors note even top models "can perform substantially differently under different harnesses."

Now picture the real office. Tasks don't arrive as a neat practice test. They arrive one by one, each one new: a weird spreadsheet join today, a legal memo with a million-token background file tomorrow. The paper calls this the open world.

Open world = tasks are unseen at design time, there is no answer key, and there is no reliable checker (or "verifier") at test time to say "you're right." You can't just study the old test afterwards — you've already had to deliver.

That creates two linked puzzles. 1) How do you safely improve without an answer key? Usual fix-it loops use scores or unit tests to guide edits. Here there are none, so a bad edit can look good. 2) How do you make a fix help the next totally different task? A super-specific patch for today's spreadsheet might hurt tomorrow's website job. Carrying yesterday's highly-tailored tools forward can just carry yesterday's mistakes.

The paper's central question is therefore two-fold:

Can an AI improve both the harness for the current job and how it gets better at improving future harnesses?

In other words, don't just rewrite the instruction manual for this one job — also learn how to become a better rewriter.

Try it yourself below. Move the sliders to build different Agents and then switch the task stream from familiar to surprise. Watch what happens when a strong brain is paired with a weak harness — and why a fixed manual breaks in the open world.

002Lesson 2~7 min

What's inside a harness? 8 files you can edit

Think of an AI agent as a brain plus a workshop. The brain — the big language model — is frozen. You don't retrain it. The workshop around it is the harness: the files that tell the brain who to be, what tools it has, and how to split up work.

In the paper the harness is written as H = (c¹ … cᴷ) — just a list of K = 8 editable files. Each file is mounted into the runtime when the agent runs. Changing those files changes how the same frozen brain behaves, often by a lot.

The 8 files, and when they wake up

Not all files cost the same. Four are always-on — stuffed into the prompt on every model call. Three are on-demand — sitting on disk costing ~0 until the agent calls them. One is special: always registered inside the tool loop.

📄

Always-on
paid every call

C1 System prompt — systemprompt.md — role and top steps.
C2 Guardrails — guardrails.md — hard rules like “treat inputs as read-only.”
C3 Memory — LongTermMEMORY.md — durable facts across tasks.
C4 Tool guidance — tool_guidance.md — when and how to use each tool.

🧰

On-demand
~0 until triggered

C6 Skills — skills/<name>/SKILL.md — specialist workflow loaded via the skill tool only when its trigger matches.
C7 Scripts — scripts/<name>.py — deterministic helper run via bash.
C5 Subagents — sub_agents/<n>/AGENT.md — helper that runs in its own context window and returns just the answer.

🔌

Middleware
always registered

C8 Plugin — plugin/<name>.ts — TypeScript hook inside the tool loop. It doesn't sit in the prompt, so it costs no prompt tokens, but it is always hooked and cannot be skimmed over like prose can.

Figure 2 groups them this way — context construction (what enters the prompt), tool interface (tools and guidance), orchestration (how many contexts exist), and middleware control (code wrapped around tool calls). Table 5 in the appendix lists the exact file path and activation for each.

💡 Key trade-off: Always-on prose is expensive. Every word competes with the agent's own output budget on every turn. The paper warns the costliest failure is a run that “reasons until the budget is gone and produces nothing.” An on-demand skill, script, or subagent costs nothing until invoked. A plugin is different: it is always registered but costs zero prompt tokens because it acts inside the tool loop, not in the prompt — the only way to enforce a rule the model keeps ignoring.

So the cheapest fix is rarely “add a longer paragraph to the system prompt.” If the problem is a narrow, repeatable procedure — say checking that a spreadsheet still opens offline, or collecting all source files before writing — the right lever is usually a skill or script (on-demand, reusable). If the model keeps skipping a check, the right lever is a plugin (always registered, enforces behavior). You save always-on budget and get a part the next task can copy.

Try it in the lab: build a harness from the 8 levers — watch which group each belongs to, see which ones charge every call vs only when used vs inside the loop, and find the combination that raises reliability without blowing your token budget.

003Lesson 3~8 min

The trick: try it, watch what changes, then choose

A strong model can still ship a broken spreadsheet if it joins on the wrong column or never reopens the file it just wrote. The paper calls that a harness problem — and in the open world you have to fix the harness without anyone handing you the answer key.

So how do you edit safely with no labels and no verifier? Harness2 does not try to guess the correct answer. It tries a version, watches what changes compared to before, and only keeps edits that visibly help.

$$ (\mathcal{H}', e', \xi) = \Phi(q_t, \mathcal{H}, \mathcal{E}; \mathcal{R}_t) $$

This is one contrastive step. In plain words: start with the current job qt and current harness H (the 8 files from last lesson) plus any history E. Guided by a fixed “how-to-improve” guide Rt, the step Φ returns three things: a successor harness H', its execution record e' (trajectory + deliverable), and a step record ξ that logs what you tried and why you kept it.

What those symbols mean: e = (τ, y) is the trace τ and final deliverable y. ~ means “sample a run” — the same task can play out differently each time. No hidden score ever enters the context.

Propose → Probe → Compose

  1. Propose — make two scoped guesses. First run a reference e0 ~ A(q; M, H) to see how H behaves right now. Then edit files to make two candidates: an invariant one fixing general process (planning, tool use, verification) and a domain-specific one fixing job knowledge (which columns join, what sections matter). You may copy a skill or script from the library, but you must re-check its facts against this task’s evidence.
  2. Probe — run under matched conditions. Run each candidate on the same task with the same model and files. Compare trajectories and deliverables to the reference. This “behavioral contrast” does not say “correct” — it says “this edit made the agent list the 8 unmatched rows, and that one made it reopen the file.” One run is weak evidence, because luck and shared model biases can fool you.
  3. Compose — keep only what you saw. Read the reference, the file diffs, and all the probe evidence. Selectively merge supported changes, fix conflicts, adopt one candidate, or keep the base if nothing helped. Write every decision with its concrete moment into ξ, then actually execute H' to get e'.
Hard rule: no rubric, grading criteria, or answer key is ever in the editor’s context. Decisions must cite an observed divergence — “failed in all base runs” or “this probe reopened the file and flagged 8 rows” — not a presumed score bump.

The whole trick is replacing “is this right?” with “did this change behavior in a way the reference shows was broken?” Try it below: you are the Composer. Propose two fixes, probe them side-by-side, and practice keeping only edits with visible support — checkboxes update the preview live.

004Lesson 4~7 min

Do it wider or do it again — scaling with budget k

Imagine your task is to fix a broken recipe. You have two ways to spend your effort. You could try five different tweaks all at once and then pick the tastiest — that's wider. Or you could taste, tweak, taste again, and tweak again for five rounds — that's deeper. Harness² does both, and calls the amount of effort its budget k.

Remember the single contrastive step from last lesson: Propose two candidates, Probe them, Compose a successor. At k=1 you do that once and you're done. No final choice is needed. When you set k to 2, 3, 4, or 5, Harness² scales that step in two organized ways.

Parallel: many fixers at once

In parallel recursion the current harness stays fixed while you explore widely. You first collect k reference runs, called B. Then you independently propose k invariant candidates and k domain candidates — that's a pool P of candidates each with its own matched execution.

Then k independent Composers each see the whole pool and each build one successor:

$$\mathcal{H}'_{j}=\text{Compose}_{j}(q_{t},\mathcal{H},\mathcal{B},\mathcal{P};\mathcal{R}_{t}),\qquad j=1,\dots,k$$

In words: for this task qt, starting from harness H, using references B and pool P, and guided by the fixed improvement harness Rt, Composer j builds harness H'j. This is width, not depth — you do one population update but k controls how broad it is. Because the Composers don't depend on each other, they can run at the same time if you have the computers.

Sequential: learn from each revision

In sequential recursion you chain the step. You start at H(0) = H0 and apply the contrastive step Φ again and again, carrying forward all the evidence:

$$(\mathcal{H}^{(r)},e^{(r)},\xi^{(r)})=\Phi(q_{t},\mathcal{H}^{(r-1)},\mathcal{E}^{(r-1)};\mathcal{R}_{t}),\qquad r=1,\dots,k$$

Here H(r) is the harness after round r, e(r) its execution, ξ(r) the record of what was decided, and E(r-1) is all the evidence so far. Later rounds can keep a good edit, revise it, or correct a mistake — because they see both the current and the previous evidence.

Budget k is your exploration dial. Bigger k means more candidate harnesses and more executions to learn from. For k > 1 both forms end with the same last step: an agentic selector compares the anonymized deliverables — just the finished documents, with no clue which harness made which — against the request and source files, and returns one existing output. It never invents a new answer and it never sees scores or a rubric.

The paper tested k = 1 → 5 on WorkBuddy-Bench Code and Office. Both parallel and sequential improved steadily as k grew — for example parallel went roughly 76.5 → 80.8 on Code. Baselines that just ran more times without better harnessing were flat or even got worse for a step. Strikingly, Harness² at k=2 already beat every baseline at k=5. More compute alone didn't guarantee a win; smarter refinement did.

005Lesson 5~7 min

Saving the lesson, not just the fix

So far you have made a better harness for one job. Lesson 4 showed you can try harder on that job by spending budget k. But what about the next job? If you just carry over the whole harness you just built, you often drag along details that were perfect for the last task and wrong for this one.

Harness² does something narrower: it saves the lesson about how you improved, not just the fix itself. That is harnessing-level recursion — the second level of "squared."

Two levels, two objects: Task-level recursion improves the execution harness for this task. Harnessing-level recursion improves the improvement harness that will guide the next task.

After each task the system runs reflection. It has the full improvement record Dt: the reference runs, every candidate harness and its probe run, the Composer's decisions, and which deliverable was finally picked.

From Dt it creates an update:

$$\mathcal{R}_{t+1}=\text{Update}(\mathcal{R}_t, \mathcal{H}^{\star}_t, \mathcal{D}_t)$$

Rt is the improvement harness before this task — basically its library. H*t is the harness that was finally adopted for this task (the star means "picked," not "proven best"). Dt is that full record. The result Rt+1 is the improved library for tomorrow.

What goes in the library? Each entry is an executable harness plus an EXPERIENCE.md file with three things: the situation where it applied, the lesson as a checkable rule naming which component to change, and the evidence — the behavioral contrast that showed it helped. The next task still starts from the common starting harness H0. Its Proposer can copy a skill or script from the library, but only after re-checking the facts against this new task.

Here is the crucial rule the paper insists on: selection alone is not evidence. The final selector picks the best-looking deliverable without seeing any harness. Picking one output does not prove the edits inside its harness caused the win. A lesson is saved only if a probe showed a concrete change in behavior — "this candidate stopped making pseudo tool calls and actually ran the tool, while the reference did not." If the record is confounded or a single noisy run is all you have, reflection writes NO_ENTRY instead of guessing. A made-up lesson would poison every future task.

Why not just keep the last harness? The authors show that directly refining the base harness with no library hurts: on WorkBuddy-Bench, Code falls from 73.4 to 63.2 and Web from 69.9 to 65.0. A larger library built at k=5 flips that to gains of +0.9, +4.4 and +5.1 points on Code, Web and Office. A library built on JobBench even helps WorkBuddy by +0.6 / +0.5 / +2.9 without any extra probing. Selective reuse beats blind inheritance when task distributions shift.

006Lesson 6~8 min

Does it actually help? The numbers

So, does rewriting its own instruction manual actually make an agent better? The paper tests Harness2 exactly like it would run in the real world: tasks arrive one by one, there is no answer key, and the improvement library starts empty. They try it on three very different job suites — WorkBuddy-Bench (code, web and office documents), JobBench (long professional jobs) and LAB (legal work) — and with four starting setups: Gemini 3.5 Flash and GLM-5, each inside the off-the-shelf OpenCode and Codex harnesses.

With just one fix-try-observe-choose cycle — that is, k=1, one invariant candidate, one domain candidate, one probe each and a selective compose — the agent beats its own starting harness everywhere. Under OpenCode, the biggest one-step jumps are striking: up to +11.5 points on WorkBuddy-Bench average (GLM-5 goes from 64.2 to 75.7), +4.5 points on JobBench (Gemini 3.5 Flash 31.5 → 36.0) and +11.8 percentage points on LAB Partial (GLM-5 59.6% → 71.4%). No cherry-picking — in all four model×harness combos and all three benchmarks, one step helps.

A weaker brain can win with a better harness. After that single step, GLM-5 with OpenCode (75.7) already scores higher on WorkBuddy than Gemini 3.5 Flash did with its original harness (72.4). The harness matters as much as the model.

Giving the agent a bigger test-time budget k helps further. With parallel recursion at k=5 — trying k invariants and k domain ideas at once and letting k independent composers merge from the whole pool — the paper reports an extra +2.9 to +3.9 on WorkBuddy avg, +3.0 to +4.2 on JobBench, and +2.6 to +6.7pp on LAB on top of the k=1 score. Both parallel (wider) and sequential (step-by-step) improve steadily from 1→5, unlike the baselines, where more tries can wobble or even get worse.

Is it worth the extra computer time? The authors count every token — both doing the job and fixing the harness — and plot score versus total cost. Harness2 sits on the Pareto frontier: for the same cost it scores higher, and for the same score it costs less, than the two online baselines, retrieval-only ReasoningBank and per-task Harness Scaling. Those baselines give smaller or inconsistent gains, and can even drop below base on some coding splits.

🧩

Ablation: what matters?

At k=1, removing the library costs -3.1 WorkBuddy / -1.8 JobBench, removing scoped roles (invariant vs domain) costs -2.9 / -3.7, and removing selective composition costs -1.6 / -1.9. In simplified terms: all three help, and scoped proposals help the most on JobBench.

🔧

Not just fewer steps

Harness2 cuts tool-error rate on all three benchmarks — e.g. JobBench 14.4% → 9.1% — even though it sometimes makes more tool calls (JobBench 27.4 → 32.8, LAB 20.8 → 25.2). Better tool use, not just shorter runs.

The same harnesses also travel. With the same model as both fixer and doer at k=2, all five tested models improve. And a harness sharpened just for Gemini 3.5 Flash / OpenCode, pasted unchanged onto GLM-5, Gemini 3.7 Flash or Claude Opus 4.8, still helps — GLM-5 jumps +17.3 on WB-code. Against the best fixed production harness per domain (Claude Code leads on Code/Office, Codex on Web), Harness2 starting from OpenCode at k=5 wins by 4.6 / 5.8 / 4.9 points.

007Lesson 7~6 min

What it proves — and what it doesn't

Harness² can make an agent better at brand-new jobs without ever seeing an answer key. But better on average is not the same as always right. This last lesson is about where the wins come from, where they break, and what still costs you.

The win: one adaptive harness beats any single fixed one

No fixed production harness won everywhere. On WorkBuddy-Bench with Gemini 3.5 Flash, Claude Code was strongest on Code and Office, while Codex was strongest on Web. Each was tuned by a team of experts — and each had a blind spot.

Harness² started from the weakest of those fixed harnesses, OpenCode, and adapted it live with a budget of $k=5$ (meaning 5 parallel tries per task). Result: it beat the best fixed harness in every domain — by 4.6 points on Code, 5.8 on Web, and 4.9 on Office. Compared to its own starting point, that is 7.4 to 9.4 points higher. Think of one toolbox that reshapes itself for each job, instead of picking one pre-packed toolbox for all jobs.

But it still fails — in three familiar ways

The paper tracked nine regressions where the new harness scored lower than the old one:

  • 1. The chooser picks the prettier, less faithful output. The final selector only sees anonymous documents, not scores. In one case it picked a 55-point output over a 95-point one because the weaker one looked more polished. With no ground-truth grader in the room, “looks thorough” can beat “is correct.”
  • 2. A shared wrong idea infects every candidate. If both the invariant and domain-specific proposals assume the same wrong rule — like “match on name literally” when the task needs matching on ID — the composer has nothing correct to choose from. Agreement across candidates feels like proof, but with the same task and same model, it is not independent proof.
  • 3. Luck and missing checks muddle the signal. Model runs are a bit random. One lucky good run or one truncated output can make a bad edit look good, or a good edit look useless. When the judge cannot see a full verdict, attribution gets noisy.
Key insight: Harness² never claims a correctness guarantee. It replaces “is this right?” with “did this edit visibly change behavior in a supported way?” That is safer than guessing, but it can still be fooled by shared biases and a single rollout.

What it costs, and where it goes next

Each improvement costs tokens: a reference run, two candidate runs, and editor sessions to propose and compose. Parallel $k=5$ can run at once if you have concurrency, but it still burns more inference than doing nothing. The paper shows Harness² sits on the best trade-off curve — more gain per token than the alternatives — but there is no free lunch. And behavioral contrasts remain sensitive to randomness and to biases all candidates share.

Two open directions follow directly:

  • Tidy the library as it grows. Right now every adopted harness and its lesson is kept. Future work could merge overlapping skills, prune outdated lessons, and retrieve only the most relevant entries for the task at hand.
  • Choose effort adaptively. Instead of fixing $k=5$ and always running parallel, decide per task whether to go wide, go deep, or stop early — spend tokens where evidence says they help.

Together, that is the full picture: recursive harnessing turns one-task fixes into reusable know-how that lifts whole streams of unseen tasks — and its limits remind us why judging without an answer key will always need caution.

ABCWord bank

Word bank.

Agent (Model + Harness)

An AI built as Model + Harness. The model is the frozen brain. The harness is the workspace around it: instructions, tools, skills, and helpers that let it actually do work.

Harness

All the editable scaffolding around a frozen model: system prompt, guardrails, memory, tool guidance, skills, scripts, subagents, and plugins. Changing the harness changes how the same model behaves.

Recursive Self-Improvement (RSI)

Recursive Self-Improvement: an AI system that turns its own execution outcomes into lasting changes to itself, so future improvements get better too.

Open world

A task stream where every new task is unseen, unpredictable, and has no answer key or reliable checker at test time. You can't just study for a fixed test.

Execution harness

The harness that runs the current job. It is what Harness² tries to improve for this specific task.

Improvement harness

The harness that guides how to improve. It contains the library of past harnesses and lessons. It stays fixed while you improve one task, then gets updated after the task.

Execution record

Reference trajectory + final deliverable from running an agent on a task. Written as e = (τ, y).

Propose-Probe-Compose

Harness²'s core step: 1) Propose two new harnesses, 2) Probe them by running them, 3) Compose a final harness by picking only the edits supported by what you observed. No ground-truth score needed.

Invariant vs domain-specific candidate

The two proposal jobs: Invariant looks for general problems like bad planning or tool use. Domain-specific looks for job-specific knowledge like legal formatting or spreadsheet joins.

Behavioral contrast

Comparing what the original harness did vs what a candidate harness did on the same task, to see if an edit actually fixed something or broke it — without knowing the 'correct answer'.

Parallel / Sequential recursion

The budget k = 1 to 5. Parallel tries k different fixes at once and merges evidence. Sequential chains k steps, each building on the last harness and its evidence.

Harness improvement library

The memory that grows across tasks. Each entry saves an adopted harness plus an EXPERIENCE.md file: when it helped, why, and what evidence supported it.

Agentic selector

A blind chooser that picks the best final document by comparing anonymized outputs against the request and source files — never seeing which harness made which.

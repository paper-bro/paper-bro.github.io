001Lesson 1 — The problem~6 min

Why one super-expensive AI for a whole job hurts

Imagine you hire a brilliant but very expensive consultant to fix a messy codebase. They don't just answer once. They look at files, run a test, see it fail, edit code, run again — maybe 30 or 50 turns. You pay for every word they read and write along the way. The longer the job, the bigger the bill.

That's a long-horizon agentic task. An AI agent works in a loop: it thinks, calls a tool like a shell command, reads the output, and tries again. The workspace — all the files and folders it can change — stays and builds up. Good performance today usually comes from big, capable cloud models like GPT-5.6 Sol, Kimi K3, or Claude Opus 5. They are accurate, but you pay per token every turn, so a long task gets pricey fast.

Cheaper alternatives exist. The paper points to lower-tier cloud models and small open-weight models like Qwen3.8-27B that you can even run locally on hardware like an NVIDIA DGX Spark or Apple Mac Studio. In the paper's accounting, that local run costs $0 in API fees. The catch: used alone, the cheaper models succeed less often.

The old fix was query-level routing: look at the initial question and pick one model to do the whole task. That fails here because what the task needs changes as the workspace changes. Early you might need a strong planner; later you might just need careful fix-ups. You can't know that from the first sentence.

Instead the paper asks: can two different models collaborate inside one task? Let a capable model start, build something useful, then hand off the workspace to an efficient model to finish. The total billed cost is simply:

$$ \text{total cost} = \text{cost before handoff} + \text{cost after handoff} $$

If the first part is short and the second part is cheap, you save a lot. But only if the second model can actually finish without ruining the work. Does that work? When, and in which direction?

Use the relay-race simulator below. Drag task length longer to feel how a long horizon inflates the capable-only bill. Switch between Capable-only, Efficient-only, and Team baton. Watch how total cost is the sum of the two legs, and how success stays high only in one team direction. That tension is what the rest of the course will unpack.

002Lesson 2 — How an agent actually works~7 min

The agent's workshop: tools, tries, and traces

An AI agent in this paper isn't a chatbot that answers in one go. It's more like an intern with a terminal. It types a command, watches what happens, fixes something, and tries again.

The paper runs every model inside the same simple workshop: mini-SWE-agent v2.4.0. Think of it as a loop with two things that keep growing:

  1. The workspace — the actual files and folders. When the agent edits app.py or creates a new file, that change stays there. Whoever continues later inherits exactly that workspace.
  2. The trajectory (history) — a linear, numbered list of turns. One turn = the agent writes a little text + makes one or more tool calls, then the tool sends back its output.

What does a tool output contain? Three short pieces the paper tracks everywhere:

⌨️

Tool call

Usually a shell command like ls, cat app.py, edit, or pytest. Up to 16,000 new tokens allowed per turn.

📤

Tool output

return_code (0 = ok), stdout (normal output), stderr (error text). That feedback is how the agent learns.

This loop is used to test two very different homework sets. Terminal-Bench 2.1 is mixed terminal chores — coding, science computing, sysadmin. DeepSWE v1.1 is harder: real bug fixes in open-source repos, checked by programs that actually run the code, not by a human grade. Each task gets a 2-hour timeout.

💡 Cost rule to remember: API cost = (tokens used) × (provider price). In the paper's accounting, the small open-weight model Qwen3.8-27B can run on your own hardware like a DGX Spark or Mac Studio, so its cost is counted as $0. That's why handing work to it can make the bill collapse.

Everything the next model needs to continue lives in those two places — the files left behind, plus the history of what was tried and what the tools said back.

003Lesson 3 — The baton pass~6 min

Passing the baton without dropping the work

Imagine a relay race where the track itself changes as you run — you lay down tiles as you go. That's what a long coding task is like. The first runner builds files, edits code, and leaves test results behind. If you want a second runner to take over, you can't just shout "go!" — you have to hand them both the tiles and the notes about why they were placed.

In this paper that idea is called a one-time handoff: Model A works for N turns, then stops. Model B inherits the whole workspace — every file edit and artifact — and runs until the task ends. There's no switching back. The total bill is simple:

$$\text{total cost} = \text{cost}_{A,\,before} + \text{cost}_{B,\,after}$$

If A is pricey and B is cheap, you want A to do just enough of the hard early work and then get off the track, so B's cheaper steps dominate the sum.

The hand-over itself matters too. The paper compares two ways to tell B what happened. In-context transfer pastes the whole conversation into B's new prompt — keeping roles, assistant text, tool calls and their outputs (return code, stdout, stderr) — converting formats if needed and just omitting any missing reasoning_content when a model hides its chain-of-thought. Logfile transfer instead writes an ordered .jsonl file in the workspace, one JSON record per turn with turn_index, response, and actions including command and outputs. B starts a fresh session with the task, the logfile path, and a schema, and is told to inspect the final records first using tools like cat and grep.

Why two methods? Pasting everything guarantees B sees it, but makes the starting prompt very long — that's extra prefill tokens you pay for, and B can get biased by A's earlier guesses. A logfile keeps the start short and lets B look selectively, but B has to remember to actually open it.

To study this cleanly, the researchers used a neat replay trick: they took a finished run, re-ran its recorded shell actions inside a fresh container to restore the workspace at exactly 30% or 75% of the way through, and then let the other model continue from that checkpoint. So "when" to hand off becomes a dial you can move.

Try that dial yourself below: drag the handoff point along a 20-step job and flip between pasting everything vs leaving a logfile. Watch how the inherited workspace grows, how the receiver's starting input balloons with in-context, and how total cost = before + after changes.

From AgentBaton (arXiv 2610.35959)

Based on the research paper — real results, simplified for learning.

Course length: 56 minutes — short enough to finish in one sitting.

Course overview: Solving long-horizon agentic tasks requires language agents to interact with their environments over multiple steps, and reliable performance often comes from the expensive capable models available through cloud providers. Meanwhile, alternative efficient models with inferior performance but a much lower cost are emerging, including lower-tier cloud models and smaller open-weights models deployable on local hardware. This raises a natural question that remains less explored than traditional query-level routing: can capable and efficient models collaborate within a single long-horizon agentic task to substantially reduce cost while preserving task accuracy? In this paper, we systematically investigate key design choices for such collaboration through model handoffs, where one model takes over from another, focusing on handoff direction and context transfer. We find that efficient-to-capable handoffs generally underperform capable-only execution with limited or even no cost reduction, whereas capable-to-efficient handoffs at suitable stages of task progress largely preserve or even improve accuracy while substantially reducing cost. These findings suggest that a one-time, simple, well-timed handoff strategy is good enough for cost-effective agent collaboration, motivating AgentBaton, a lightweight detector that learns when to hand off from recurring patterns in task progress. Across 11 model pairs and two representative benchmarks, AgentBaton reduces API costs by 65.9% on average while largely preserving task accuracy, with accuracy gains of up to 8.8 percentage points over capable-only execution. Experiments across various reasoning-effort settings further show that AgentBaton extends the empirical accuracy–cost Pareto frontier.

Written by Junlong Li, Jindong Jiang, Yonggan Fu, Jiarui Yao, Hanrong Ye, Wonmin Byeon, Peter Belcak, Hao Zhang, Pavlo Molchanov.

Quiz question: How is cost counted in a handoff run? Answer: Total cost = cost before handoff + cost after handoff. The paper measures total cost as source cost before handoff plus receiver cost after. That is how it reports the 65.9% average reduction.

Quiz question: Why does the paper say query-level routing falls short for agentic tasks? Answer: They decide from the initial query only and ignore how the workspace evolves. Query-level routers pick one model from the initial description only. In long tasks the needed skills change as files and errors change, so upfront picking fails.

Quiz question: What asymmetry did the paper find about handoff direction? Answer: Efficient → Capable generally underperforms capable-only; Capable → Efficient can preserve accuracy with big cost cuts. Figure 3 / Table 1: starting with the efficient model then handing to capable generally loses accuracy vs capable-only with little or no cost saving, while the reverse saves a lot.

Quiz question: When is logfile transfer preferred over in-context? Answer: Logfile tends better for Efficient→Capable; Capable→Efficient depends on source model (e.g., missing CoT hurts in-context). Table 1: logfile matches or beats in-context for Efficient→Capable, while for Capable→Efficient in-context is better for GLM/Kimi and mixed for GPT Sol (partly because GPT Sol hides chain-of-thought).

Quiz question: Which situation matches the paper's three signs of handoff readiness? Answer: An artifact exists, it received real test/execution feedback, and leftovers are localized fixes. Section 3.3: 1) substantive artifact exists, 2) it got real execution/test/inspection feedback (even a useful failure), 3) remaining work is localized repair/validation.

Quiz question: Why not just prompt the capable model to 'hand off when ready'? Answer: Prompting is unreliable: some models never hand off at all. Table 2: prompting the capable model to hand off itself is unreliable — Kimi K3 0/113 handoffs, GLM 6/113 — motivating a separate learned detector.

Quiz question: What is AgentBaton? Answer: A 2B model trained on Codex-annotated trajectories to predict READY/NOT_READY each turn and trigger handoff online. Section 4.2: trained from Qwen 3.5 2B, watches trajectory each turn, predicts HANDOFF_READY/NOT_READY JSON, triggers one-time handoff; input is task + actions + tool outputs.

Quiz question: What was the headline result? Answer: AgentBaton cuts ~65.9% cost on average and can even improve accuracy, extending the cost-accuracy Pareto frontier. Across 11 pairs × 2 benchmarks average -65.9% cost; specific wins like GLM max→Luna 72.6% at $0.80 vs 69.0% at $3.06, and Kimi→Luna 79.6% at $1.60 beating best single model 75.2% at $8.90.

Glossary — language agent: An AI program that works in steps: it thinks, runs a tool like a shell command, sees the result, and tries again until the task is done. — long-horizon task: A task that takes many turns of tool use and feedback, like fixing a bug in a real code repository. The paper uses Terminal-Bench 2.1 and DeepSWE v1.1. — workspace: All the files, code and folders the agent can change during a task. — tool call / trajectory: One turn of agent action + tool output, e.g. run `cat file.txt` and get the text back. A full run is a trajectory. — model handoff: Stopping one model and letting a different model continue from the same workspace. The paper studies a single one-time handoff per task. — capable vs efficient model: In the paper, capable = expensive, high-accuracy cloud models like GPT-5.6 Sol, Kimi K3, GLM-5.3, Claude Opus 5, Gemini 3.8 Flash. Efficient = cheaper models like Qwen3.8-27B (run locally for free in the paper's accounting) and GPT-5.6 Luna. — context transfer: How the new model learns what happened before the handoff. — in-context transfer: Paste all previous chat, tool calls and outputs directly into the new model's prompt. — logfile transfer: Write history to a .jsonl logfile in the workspace that the new model can read with commands like cat/grep when it wants to. Starts with a fresh session plus the logfile path. — reasoning effort: A setting (low, medium, high, xhigh, max) that controls how long a model is allowed to think. More effort usually costs more. — Pareto frontier: If no other setup can give you higher accuracy without higher cost, and lower cost without lower accuracy, you are on the Pareto frontier. The paper shows AgentBaton pushes this frontier outward. — detector: AgentBaton itself: a small model (Qwen 3.5 2B) that watches each turn and outputs {"judgement":"HANDOFF_READY"} or HANDOFF_NOT_READY.

004Lesson 4 — Which direction actually works?~8 min

Cheap first or expert first? Only one saves money

Imagine a relay race with two runners: a pricey star who almost always finishes, and a thrifty teammate who is fast but gets lost alone. Who should start?

You might think “let the cheap runner try first, and only call the star if needed.” The paper tested exactly that — and the opposite — by forcing a single clean handoff at a fixed point.

How it was tested: take a completed run of one model, rewind the workspace to, say, 30% or 75% through it, and let the other model take over from there. Total cost for that task is just simple addition:

$$\text{total cost} = \text{cost before handoff} + \text{cost after handoff}$$

The team tried both directions for three star models — GLM-5.3, Kimi K3, and GPT-5.6 Sol — handing to the efficient helper Qwen3.8-27B, and the reverse. They later swept six timings: 15%, 30%, 45%, 60%, 75% and 90% of the first model’s solo run. 0% on their charts means “helper alone.”

The asymmetry: helper first → star generally got lower accuracy than just using the star alone, sometimes even at higher cost. It saved little. Star first → helper at the right moment largely kept the star’s accuracy while slashing the bill.

In numbers on the hard coding benchmark DeepSWE v1.1:

  • Kimi K3 → Qwen at 45%: 72.6% accuracy vs 73.5% for Kimi alone — almost identical — with 61.5% lower cost.
  • GPT-5.6 Sol → Qwen at 60% (using a logfile, see next lesson): 67.3% vs 68.1% alone, with 47.9% lower cost.
  • GLM-5.3 → Qwen at 30%: 61.1%, exactly matching GLM alone, with 82.4% lower cost ($0.56 vs $3.16).

The other direction looked poor. Qwen → GPT Sol at 30% did beat GPT Sol alone 70.8% to 68.1%, but the bill barely moved — only about 6% cheaper. Qwen → GLM and Qwen → Kimi lost accuracy as you delayed the handoff, and stayed expensive.

Why? When the star goes first it leaves behind something useful: a real file, a test run that showed what is broken, a narrowed bug. The helper can then do the focused repair it is good at. When the helper goes first, it can wander, write a shaky start, and the star has to waste turns cleaning up. That is also why the paper warns against switching back-and-forth every turn — errors pile up and the star keeps paying to fix them.

The paper goes further in other sections on how to pass the notes and when to cut over — that is next. For now, try the lab to feel the asymmetry yourself.

In the lab: pick a direction and an expert, then drag the handoff slider from 0% to 90%. Watch the two traces: accuracy vs the flat expert-only dashed line, and cost vs its flat line. Find the sweet spot where expert-first keeps the green line high while the cost line dives — and see how helper-first fails to do the same.

005Lesson 5 — How to pass the notes~6 min

Two ways to tell the next model what happened

Imagine your expert teammate finishes their shift and leaves notes for the cheaper teammate who takes over. There are two very different ways to leave those notes — and the paper found the better way depends on who is handing to whom.

Method 1: In-context. You photocopy every chat message, every tool call like cat file.jsonl and every tool output (return code, stdout, stderr) and paste it straight into the next model's prompt. If the first model used a different chat format, you convert it. If its private reasoning text wasn't exposed, you just leave that part out — you don't make it up.

Method 2: Logfile. You write that same history to a file, like history.jsonl, inside the workspace. Each line is one turn with the model's text, the command it ran, and what came back. The next model starts a fresh session with the original task plus a note: "here's the logfile path, records are in time order, check the last ones first to see where things stand." It can then cat or grep the file only if it wants to.

The trade-off in one sentence: in-context guarantees the receiver sees everything but pays a longer prefill bill and may copy the previous model's bad assumptions; logfile keeps the prompt short and lets the receiver be selective, but the receiver has to actively look.

So which wins? The paper tested both at 30% and 75% through the source trajectory, for both directions (Table 1).

Efficient → Capable: logfile is the clear favorite. It matches or beats in-context accuracy in most cells while significantly cutting cost. For example, Qwen → Kimi on DeepSWE at 30%: logfile 62.0% at $4.45 vs in-context 47.8% at $7.77. Because of this, the paper uses logfile for all efficient-to-capable handoffs from then on.

Capable → Efficient: it's model-dependent. For GLM-5.3 → Qwen and Kimi K3 → Qwen, in-context is usually more accurate. But for GPT-5.6 Sol → Qwen it's mixed: logfile is better at 30% on both benchmarks and at 75% on DeepSWE, while in-context is better at 75% on Terminal-Bench. The paper's hypothesis: unlike GLM and Kimi, GPT-5.6 Sol does not expose its full chain-of-thought, so in-context has less useful reasoning to reuse.

There is no universal best envelope. The direction and whether reasoning traces are visible change the answer. Try it yourself below: flip between efficient-first and capable-first for the same timing and watch the accuracy and cost bars swap winners.

006Lesson 6 — Reading the room~7 min

The three clues that say 'now is a good time'

When should the pricey expert step aside? The paper didn't guess — it looked at moments where the cheap model Qwen 3.8 27B failed if handed the job early, but succeeded if handed it just a little later. What changed in between tells us what "ready" looks like. Two examples in the paper: fixing a bug with quoted file paths, and double-checking a coordinate math tool until its test output matched.

🧱

1. Something real exists

There is a runnable piece of work in the workspace — code, a prototype, a file. A plan or sketch that was never executed is not enough.

🧪

2. It got real feedback

That piece was actually run, tested, compiled, or inspected, and we saw the result. Even a failed test counts if it points to one spot. An environment crash that prevented running does not count.

🔍

3. What's left is small

The hard "what approach to use?" question is settled. What remains is localized: fix one function, patch the encoding, validate output, tidy up.

Key idea: "ready" means all three together. Artifact + feedback + small leftovers. A passed test isn't required — a useful failure that narrows the bug is often the exact signal the cheaper model needs to finish.

You might think we could just tell the capable model, "hand off when you see those three clues." The researchers tried that prompt. It didn't work reliably. In Table 2 on DeepSWE v1.1, Kimi K3 handed off in 0 out of 113 tasks, GLM-5.3 in only 6 out of 113, and GPT-5.6 Sol handed off every time but still cost $3.75 per task on average versus $5.32 doing it alone — not the best trade-off.

Why the difference? Models are trained to be helpful and finish, not to give up control. They don't judge their own progress the same way twice. That's why the paper builds a separate tiny judge — AgentBaton — that watches the trace from the outside and shouts "now" when it sees the three clues.

In the lab, you get to be that judge. Pick a case, slide through its turns, check which of the three clues are lit, and decide HANDOFF_READY or HANDOFF_NOT_READY. Watch for the trap: a file that was never run, or a crash that tells you nothing about the code.

007Lesson 7 — Building AgentBaton~8 min

A 2-billion-parameter referee that shouts 'hand off now!'

A prompt that says “hand off when ready” sounds simple, but the paper tried it and it flopped. Kimi K3 never handed off in 113 tasks. GLM-5.3 did it only 6 times. GPT-5.6 Sol handed off every time but still cost $3.75 per task — not cheap enough. Asking the expert to judge itself doesn't work.

AgentBaton fixes this with a tiny outside referee. It's not a giant coder. It's a 2-billion-parameter model — about a thousand times smaller than the big experts — fine-tuned from Qwen 3.5 2B to do one job: after every turn, look at the trail and output a tiny JSON verdict:

$$\{\text{"judgement":"HANDOFF\_READY"}\}\quad\text{or}\quad\{\text{"judgement":"HANDOFF\_NOT\_READY"}\}$$

The referee is fast because it's small. Over 360 real checks with inputs from 2,000 to 121,000 tokens, it answered in 338 ms median and 1.11 s at the 95th percentile on one NVIDIA H100 GPU. Quick enough to check every turn without slowing the agent.

What did the referee study? 2,000 tasks from SWE-rebench V2. For each task the authors ran two different capable models (picked from 5: GPT-6 Astra, GPT-5.6 Sol, Claude Opus 5, Kimi K3, GLM-5.3) — so 4,000 full trajectories. Then Codex, acting as a teacher, looked back through each trajectory and marked the earliest turn that met all three readiness clues from Lesson 6. If it never happened, it labeled the run no_clear_handoff. Codex only saw the task description plus tool calls and outputs — no private reasoning, no final test score.

How is that turned into training? Say the teacher said “READY at turn h.” Then every turn before h is labeled HANDOFF_NOT_READY and turn h itself is HANDOFF_READY. To teach the model not to freeze if it misses the perfect moment, the authors also add extra positive examples after h — same idea: “even if you missed it, say READY now.” Earlier wrong decisions are hidden from the loss so they don't punish the model twice. Training ran for 2 epochs, max 32K tokens per example, packed to save compute, on 16 H100s with AdamW at learning rate $10^{-5}$.

At run time the capable model starts alone. After each turn AgentBaton reads the updated history and votes. If the history gets longer than 32K tokens, the oldest half is dropped — but the system instruction and original task are always kept. The first HANDOFF_READY triggers the one-time handoff; the efficient model inherits the workspace and finishes the job using the transfer method that works best for that pair (logfile for GPT models, in-context for the others).

008Lesson 8 — Results~8 min

65.9% cheaper, just as good — and sometimes better

Expensive AIs are good but they charge for every step they think. The paper asked the bottom-line question: if a pricey expert starts the job and a cheap helper finishes it, do we lose accuracy to save money — or can we save money and keep the score?

Across 11 different pairs of models and two hard benchmarks, the answer is striking. On average AgentBaton cut the API bill by 65.9% while largely keeping the same accuracy. In a simplified way, that means a task that cost about 5 dollars with the expert alone drops to about 1.70 dollars with the handoff.

And sometimes the team does better than the expert alone. Take two real examples from DeepSWE v1.1 in Table 3:

  • Kimi K3 → Qwen 3.8 27B: 72.6% accuracy vs 73.5% with Kimi alone — only 1.2% lower — but cost fell 72.9%, from 4.73 dollars to 1.28 dollars per task.
  • Claude Opus 5 → GPT-5.6 Luna: 76.1% vs 67.3% alone — that is +8.8 percentage points, +13.1% relative — while cost fell 70.5%, from 9.91 dollars to 2.92 dollars.

In 12 out of 22 pair-and-benchmark settings, accuracy was either higher or within 5% of the capable-only result. Handoff happened early on software-building tasks (about 27–41% through the expert's run on DeepSWE) and later on mixed terminal tasks (about 56–69% on Terminal-Bench) — the detector learned when "enough is built" looks different per task type.

The point is not just one cheap trick. The paper also checked the alternatives and they lost: a query-level router trained to pick the cheap model from the initial question picked the cheap model on only 1 of 113 test tasks — no savings. A per-turn router called MTRouter that switches every turn cost 46.7% to 86.6% more than AgentBaton with the same or worse accuracy.

Reading the Pareto frontier

Think of every setup as a dot: left-right is cost (cheaper is left), bottom-top is accuracy (better is top). You want dots up and to the left. A dot is on the Pareto frontier if no other dot beats it on both cost and accuracy — you would have to pay more to get higher accuracy, or accept lower accuracy to pay less.

In Figure 1 the solid lines are single models tried at different reasoning efforts — low, medium, high, xhigh, max. More thinking usually helps a bit but costs a lot more. The diamonds (handoff to Qwen) and squares (handoff to Luna) are AgentBaton team-ups. The green dashed line connects the best team-ups — the new frontier. It sits above and to the left of every single-model line, which means it extends the frontier outward.

Three concrete frontier points on DeepSWE make it real:

  • Luna xhigh → Qwen matches Luna alone at 56.6% accuracy but at 0.06 dollars per task instead of 0.21 dollars.
  • GLM-5.3 max → Luna gets 72.6% at 0.80 dollars, beating GLM alone at 69.0% at 3.06 dollars — higher accuracy for about one quarter the price.
  • Kimi K3 high → Luna reaches 79.6% at 1.60 dollars, beating the best single-model dot in the whole sweep, Claude Opus 5 xhigh at 75.2% at 8.90 dollars.

In short, thinking harder and handing off smarter complement each other. You can pick a cheap, good-enough point or push to a new best score without paying the old best price. ABCWord bank

Word bank.

language agent

An AI program that works in steps: it thinks, runs a tool like a shell command, sees the result, and tries again until the task is done.

long-horizon task

A task that takes many turns of tool use and feedback, like fixing a bug in a real code repository. The paper uses Terminal-Bench 2.1 and DeepSWE v1.1.

workspace

All the files, code and folders the agent can change during a task.

tool call / trajectory

One turn of agent action + tool output, e.g. run `cat file.txt` and get the text back. A full run is a trajectory.

model handoff

Stopping one model and letting a different model continue from the same workspace. The paper studies a single one-time handoff per task.

capable vs efficient model

In the paper, capable = expensive, high-accuracy cloud models like GPT-5.6 Sol, Kimi K3, GLM-5.3, Claude Opus 5, Gemini 3.8 Flash. Efficient = cheaper models like Qwen3.8-27B (run locally for free in the paper's accounting) and GPT-5.6 Luna.

context transfer

How the new model learns what happened before the handoff.

in-context transfer

Paste all previous chat, tool calls and outputs directly into the new model's prompt.

logfile transfer

Write history to a .jsonl logfile in the workspace that the new model can read with commands like cat/grep when it wants to. Starts with a fresh session plus the logfile path.

reasoning effort

A setting (low, medium, high, xhigh, max) that controls how long a model is allowed to think. More effort usually costs more.

Pareto frontier

If no other setup can give you higher accuracy without higher cost, and lower cost without lower accuracy, you are on the Pareto frontier. The paper shows AgentBaton pushes this frontier outward.

detector

AgentBaton itself: a small model (Qwen 3.5 2B) that watches each turn and outputs {"judgement":"HANDOFF_READY"} or HANDOFF_NOT_READY.

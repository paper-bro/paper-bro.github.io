AI chips sit mostly idle. Teach them to share.

Expensive AI chips often leave around 90% of their math units idle while answering live chat requests because each step waits on memory. This course unpacks why GPUs waste so much hardware today and how a GPU operating system—plus new compiler and chip designs—can pack useful background work into the gaps without making replies noticeably slower.

001The core problem~5 min

Why expensive AI chips sit mostly idle.

Imagine hiring a master chef who can chop 280 carrots a second, inside a kitchen whose pantry door only lets one carrot through per second. No matter how fast the chef is, they spend almost their entire shift waiting for deliveries.

That is what happens inside an expensive AI chip when it answers messages live. A GPU is built from many small processor blocks called SMs (Streaming Multiprocessors)—188 of them on the NVIDIA RTX PRO 6000 Blackwell card measured in this paper. Inside each SM are matrix-math engines called tensor cores. Yet when OpenInfer served a 397-billion-parameter model (Qwen3.5-397B) across four of those GPUs under realistic live deadlines, the tensor cores were busy only about 7% of the time—and just 2.9% in a pool dedicated solely to generating replies. Another giant model, Kimi K2 (~1 trillion parameters), kept tensor cores busy only 6–11% of the time.

The culprit is how text generation works. After reading your prompt, an AI writes its reply one word-piece (token) at a time, a phase called decode. For every single token, the GPU must haul the model's learned numbers (weights) and the saved notes from earlier in the conversation (the KV cache) out of main memory. Because replies must arrive quickly, the chip only handles a small batch ($B$) of requests at once—so each byte read from memory sparks very little math before the tensor cores finish and wait again.

We can estimate this bottleneck using a chip's ridge: the ratio of peak math operations it can perform per second to the bytes it can read from memory per second. Standard AI chips fed by external memory (HBM or GDDR) have huge ridges—roughly 240 to 560 operations per byte (about 280 on the RTX PRO 6000 Blackwell, 250 on AMD's MI300X, 240 on Google's TPU v5e, and 560 on TPU v6e). By contrast, specialty chips built around huge on-chip SRAM memory read tens of times faster, dropping their ridge to 2–6.

$$\text{Math busy fraction} \approx \frac{\text{ops per byte}}{\text{ridge}} \approx \frac{B}{\text{ridge}}$$

In a simplified version ignoring KV-cache traffic, decode at batch size $B$ supplies roughly $B$ math operations per byte of 16-bit weights (or $2B$ for 8-bit weights). At batch $B = 2$ on a chip with ridge 280, math units are at most a few times $B \div \text{ridge}$ busy—around 1%. Grouping 256 requests into a big batch helps dense models, but modern Mixture-of-Experts (MoE) models slice that batch right back down. Instead of running the whole model for every token, an MoE routes each token to just a handful of specialized sub-networks (experts). Kimi K2 sends each token to only 8 of 384 experts, so even a batch of 256 gives each expert only about $256 \times 8 \div 384 \approx 5$ tokens.

The core insight: AI chips sit ~90% idle during live replies not because the math units are slow, but because small batches and MoE routing starve them behind a memory wall.

002The OS idea~5 min

Teaching the GPU to spend its slack.

A laptop runs your browser, music, and file backups at the same time because its operating system (OS) juggles them. If you click a link, the OS pauses background work in microseconds so the screen responds right away. GPUs have nothing like this. A GPU runs queued programs—called kernels—in order, and once a piece of work starts on the chip, nothing can ask it to leave until it finishes.

To fill the idle gaps from the last lesson without slowing down live chat replies, the authors propose an OS for the GPU. Its currency is slack: the extra speed margin by which urgent replies beat their deadline. They enforce a strict 6% slow-tail budget. If you measure the slowest 1% of urgent steps running alone (the 99th-percentile step time, written $p_{99}$), an urgent step sharing the chip is only on time if it finishes within $1.06\times$ that solo $p_{99}$ time.

$$\text{On-time limit} = 1.06 \times p_{99,\text{alone}}$$

Why not just mark background work as "low priority" using features GPUs already ship? Because today's stream priorities only pick what starts next—they never interrupt a kernel that is already running. In the team's tests, 1-millisecond low-priority pieces slowed urgent work by up to $10\times$. On an AMD MI300X GPU, an urgent task got stuck waiting $180\text{ ms}$ behind a $200\text{ ms}$ background job.

To avoid trapping urgent work in line, background jobs must be sliced into tiny pieces that finish quickly. That creates a sharp cliff, or knee, between $20$ and $50\text{ microseconds}$ ($\mu\text{s}$, millionths of a second): pieces of $2\text{--}20\,\mu\text{s}$ met $92\text{--}100\%$ of deadlines (adding $+5.6\%$ to $+9.5\%$ to step time), whereas $50\,\mu\text{s}$ pieces slowed urgent steps by $+47\%$ and missed every single deadline.

Even with tiny blocks, not all sharing costs the same. A GPU OS must treat the chip as separate resources, each with its own slowdown price:

🆓

Spare Memory

Holding $60\text{ GB}$ of idle memory for another job cost urgent work $0\%$ slowdown.

🐢

Paced Traffic

Microsecond-paced memory reads ($280\text{--}365\text{ GB/s}$) cost only $+2\text{--}7\%$, and paced host copies ($\le 13\text{ GB/s}$) cost roughly $0\%$.

🚨

Unpaced Bursts

Bursting host copies at $90\text{ GB/s}$ cost $+21\%$, bursty memory traffic ($400\text{ GB/s}$) cost $+38\%$, and on-chip cache traffic cost $+36\%$.

Six layers from milliseconds to microseconds

The proposed OS spans six layers: chip hooks (L0), short restartable kernels (L1), an on-GPU scheduler placing work every few microseconds (L2), a resource governor pacing memory and cache traffic (L3), plus an envisioned cost model (L4) and admission controller (L5) deciding every few milliseconds which jobs fit inside the slack.

003Kernels & compilers~5 min

Squeezing urgent work onto fewer processors.

Imagine loading delivery trucks through a single warehouse doorway. Adding 188 workers does not make trucks leave any faster once the doorway is full. If 24 workers can keep the loading ramp completely busy, the other 164 could be packing boxes in the next room.

A GPU can share its processors the same way. Giving urgent AI replies a smaller slice of the chip's SMs leaves the rest free for background jobs. That trick only works, however, if the urgent work stays fast when squeezed onto fewer SMs.

Why 24 processors can fill the memory pipe

Memory speed obeys a rule called Little's Law: the amount of data traveling from memory at any instant equals the delivery rate (bandwidth) multiplied by the round-trip wait time (latency).

$$\text{Bytes in flight} = \text{Bandwidth} \times \text{Latency}$$

On the RTX PRO 6000 Blackwell card measured in the paper, peak measured memory bandwidth is $1,538\text{ GB/s}$ across 188 SMs. At the card's memory latency, filling that pipe requires roughly $2.3\text{ MB}$ of read requests in flight at once. When a well-written streaming kernel keeps about $96\text{ KB}$ of reads in flight per SM, just 24 SMs reach $1,527\text{ GB/s}$—99.2% of peak bandwidth—leaving 164 SMs free.

Today's decode kernels fall far short of that mark. On the paper's Kimi K2 decode test, the model averaged only $769\text{ GB/s}$ (50% of peak) even when given all 188 SMs. Worse, squeezing its experts phase onto 60 SMs slowed that phase by 22% (from $14.4\text{ ms}$ to $17.6\text{ ms}$). Instead of saturating memory on a small partition, today's decode kernels lose speed as SMs are taken away.

⚙️

Compilers must split the work

Shareable kernels need short, tens-of-microsecond pieces that pause cleanly and declare how much memory they read per math operation. Compilers like Triton and libraries like CUTLASS must generate partition-sized versions automatically—telling NVIDIA's cuBLASLt library to target fewer SMs today actually made steps 1–2 points slower.

🧩

Models can help too

In an untested direction, models with balanced MoE routing or hybrid linear attention (such as Kimi Delta Attention) run steadier kernels whose cost does not grow with conversation length, giving a GPU OS predictable gaps to fill.

004Today's sharing limits~6 min

What co-running achieves today, and where it hits a wall.

In the last lesson, you saw that a well-written streaming kernel only needs 24 of the GPU's 188 processors (SMs) to saturate memory bandwidth. That raises an obvious question: if we use NVIDIA's shipped green contexts to fence off SMs for urgent replies and hand the rest to background jobs today, how much idle hardware can we put to work?

To find out, the authors built a single-GPU proxy for Kimi K2 decode: all 61 layers, batch 8, and a 32k-token context on an RTX PRO 6000 Blackwell. Running alone, each step took about 39 ms and kept tensor cores busy only 8.7% of the time. They measured extra output in GPUs' worth—the background job's speed divided by its best speed running alone on a full GPU.

With synthetic tiles designed to keep a small ~5.5 MB working set inside the on-chip L2 cache, handing 48 of 188 SMs to background work recovered 0.23 of a GPU and lifted tensor-core activity to roughly 30%. Median steps slowed by +5.1% and the 99th-percentile tail by +5.5%, just inside the 6% budget.

Real off-the-shelf work hit a wall much sooner. Running NVIDIA's 8-bit matrix-multiply library (FP8 GEMM) beside decode recovered only 0.09 of a GPU inside the budget (+4.7% median, 15.4% tensor-core activity). Pushing that real job to 0.13 of a GPU slowed urgent steps by +9.9%, blowing past the 6% limit. Even the matrix shape mattered: a 1536×1536×1536 job disturbed the urgent model's L2 cache less than a 2048×2048×2048 job because its working set was smaller (~9 MB vs. ~16 MB).

🧩

Urgent work's SM loss

On a 156-SM partition (32 SMs given away), today's decode kernels already lose +2.3% speed on their own because they are not tuned for smaller slices.

🚦

L2 & memory contention

Cache-friendly tiles add just +2.4 points on 156 SMs. Real FP8 GEMMs stream data through L2 and memory, adding +7.6 points of traffic-jam delay.

Two scaling traps make the real-world limit even tighter. First is the 64-GPU straggler problem: in a 64-GPU deployment, all 64 cards must finish each step before moving on, like relay runners waiting for the slowest teammate. Waiting for the slowest card pushes the 140-SM tile setup from +5.5% to a projected +6.6% tail slowdown—over budget—forcing the safe limit back to 156 SMs (0.15 of a GPU at +4.9% tail slowdown).

Second is a 1-layer cache trap. Switching partitions between phases of a step looked great on a 1-layer test (0.42 of a GPU at +2.1%) only because half of one layer's 264 MB of experts fit inside the 128 MB L2 cache. On the full 61-layer model, weights fall out of cache, the experts phase on 60 SMs slows by 22%, and switching streams adds 1.4 ms of gaps—spiking slowdown to +11.8% median and +16.8% at the tail.

005A working prototype~5 min

Putting a whole model inside one resident kernel.

Every time a normal AI server generates a single token, the CPU launches dozens of separate GPU kernels one after another, waits to check whether the reply is finished, and schedules the next step. Those tiny hand-offs add up—and they make sharing harder, because each short kernel assumes it owns the chip until it finishes.

OpenInfer built a working research engine that flips this design upside down. Instead of launching kernel after kernel, it packs the entire Llama-3.1-8B-Instruct model (using 8-bit FP8 weights) into one resident kernel that starts once and stays loaded on the GPU for the life of the process.

🔄

No CPU in the loop

The resident kernel places one worker block—called a CTA (a group of GPU threads)—on each of the card’s 188 SMs. It pulls new requests from a memory ring, updates the paged KV cache, samples the next token on the GPU, and writes finished tokens back out to a ring buffer for the CPU to read.

🚦

Clean phase-boundary pauses

Because one program owns the whole decode step, it can reserve 16 of its 188 CTAs for background math tiles. At the boundaries between model phases, those background CTAs check a shared yield flag and pause cleanly so urgent work stays on schedule.

Skipping the CPU launch loop pays off right away. On a single live request (256 output tokens on identical weights), the resident kernel decodes about 3% faster than vLLM 0.32’s best tuned setup: 6.80 ms per token instead of 6.99 ms.

Even bigger gains show up when sharing. Inside the resident kernel, those 16 background CTAs recover roughly a quarter of a GPU’s math capacity while barely nudging the urgent reply:

SetupGPU recoveredUrgent slowdown
Shipped green-context partition (Lesson 4)0.23 of a GPU+5.1%
Resident kernel, 1 request (16 BG CTAs)0.22 of a GPU+0.3%
Resident kernel, 16 requests (16 BG CTAs)0.24 of a GPU+1.6%

In both resident-kernel runs (210 TF/s at 1 request and 220 TF/s at 16 requests, compared against the card’s 934 TF/s register-fed FP8 ceiling), the generated output tokens were bit-identical with background work turned on or off.

Where this prototype stops: This is a hand-built engine for one model, and its vLLM speed comparison was measured at a single request. More importantly, the 16 background CTAs ran synthetic math tiles fed from fast on-chip registers and a tiny 64-byte L2 pad—with zero DRAM traffic. As you saw in Lesson 4, real background jobs stream large matrices through L2 and DRAM, which causes much heavier contention. Also, giving 32 CTAs to background tiles instead of 16 hit a register-file ceiling per SM and stayed flat at 210 TF/s.

006Hardware asks~5 min

Three features only new chips can fix.

Software workarounds can only push GPU sharing so far. Earlier lessons showed how green contexts and resident kernels recover idle math units—but once real background jobs run alongside live decode, three limits built into today's silicon block the way.

First, pausing a running job without hardware help is punishing. On an NVIDIA GPU, stopping and relaunching background work every 2 to 5 microseconds throws away 41% to 44% of its throughput. On an AMD MI300X, stream priorities fail to trigger hardware preemption at all, and relaunching 2 to 50 microsecond blocks slowed a short foreground test by 1.55$\times$ to 4.8$\times$.

Second, today's partition controls break down across a multi-step model. CUDA lets a program attach a green-context partition to a single step inside a pre-recorded CUDA graph, then quietly ignores it and runs that step on all 188 SMs anyway. Splitting phases across separate streams instead adds 1.4 milliseconds of empty switching gaps to every decode step.

To remove these walls, the authors ask chip makers for three core hardware features:

⏸️

S1: Fast pausing

Pause background work within 5 to 20 microseconds and resume right where it left off, removing the 41–44% relaunch penalty.

🚦

S2: Memory priority

Let urgent work go first in the L2 cache and main memory (DRAM) controllers at runtime. Today's static L2 set-aside had no meaningful effect against bandwidth contention—where real FP8 matrix jobs added +7.6 points on 156 SMs—and MIG requires a chip reset to resize.

🧩

S3: Graph partitions

Honour the SM partition assigned to each kernel inside a CUDA graph, eliminating the 1.4 ms stream-switching tax.

Supporting asks (S4–S7): The paper also requests instruction priority inside a shared SM (S4), fast chip-wide signals and queues (S5), readable performance counters (S6), and rate limits for data copies and power (S7)—since unpaced data copies from the host or another GPU slowed decode by +21% and +18%.

007The bigger picture~4 min

Climbing the headroom ladder together.

Across the earlier lessons, we saw separate fixes for idle AI chips: reserving SMs with green contexts, running cache-friendly tiles, keeping a model inside one resident kernel, and asking chip makers for new hardware hooks. To see how far all of these improvements go together, the authors organize them into a headroom ladder.

Each rung adds another layer of software or hardware and tracks two numbers: how much extra GPU capacity you win back, and how honest the evidence is. The paper carefully separates hard measurements from calculations and early bounds:

  1. Shipped partitions + real jobs (Measured: 0.06–0.09 GPU): Using today's green contexts on the full 61-layer Kimi K2 proxy at batch 8, real 8-bit matrix-multiply jobs (FP8 GEMM) recover 0.06 to 0.09 of a GPU at +4.4% to +4.7% slowdown. Pushing real GEMM to 0.13 slows decode by +9.9%, breaking the 6% slow-tail budget.
  2. Cache-friendly background work (Measured: 0.23 GPU): Swapping in synthetic tiles that reuse data inside the L2 cache avoids memory traffic jams, lifting recovery to 0.23 of a GPU at +5.1% slowdown.
  3. Roofline decode kernels (Derived: ~2× headroom): Today's decode kernels use only half of the card's measured memory bandwidth across all 188 SMs. Arithmetic on that bandwidth shows that kernels hitting the memory roofline on fewer SMs could unlock roughly twice the headroom—though nobody has built a full decode kernel like that yet.
  4. Silicon hooks S1–S3 (1-layer bound: 0.60 GPU): On a single-layer test using register-only math blocks to stand in for fast pausing and memory isolation, recoverable work reached 0.60 of a GPU at +7.7% slowdown. The full 61-layer step has not been measured.

The biggest gains arrive when every layer of the AI stack is designed for sharing together:

🧩

Models

Balanced MoEs or hybrid linear attention (like Kimi Delta Attention) create steadier gaps, and models can generate cache-friendly tasks of their own, such as adapter training or reward scoring.

⚙️

Compilers & OS

Compilers split kernels into pauseable pieces sized to any slice of SMs, while a GPU OS prices each resource and admits work inside the slack.

🔬

Chips

Hardware hooks S1–S3 give the OS fast 5–20 microsecond pausing, runtime priority in cache and memory, and per-kernel partitions that the chip actually obeys.

Where the paper's evidence stops

The authors spell out clear limits. Full-step co-runs tested a single-GPU proxy for Kimi K2 at batch 8 without real multi-GPU all-to-all network traffic, 64-GPU figures are straggler projections, and how recovery changes across batch sizes is unmeasured. Model co-design ideas are untested, and while pausing and partitioning lessons should carry over to datacenter GPUs and other accelerators, the exact interference numbers will differ.

ABCWord bank

Word bank.

SM (Streaming Multiprocessor)

One of the many small processor blocks on a GPU that run AI math and memory instructions in parallel. An NVIDIA RTX PRO 6000 Blackwell has 188 of them.

Tensor core

Specialized matrix-multiplication units inside each SM that do the heavy lifting for AI models.

Decode

Generating an AI reply one token (word piece) at a time after reading the user's prompt.

KV cache

Saved intermediate math from earlier words in a conversation so the model does not have to recompute them for every new token.

MoE

Mixture-of-Experts: a model design where each token is routed to only a small subset of specialized sub-networks (experts) instead of running the whole model.

Ridge

The ratio of math operations a chip can perform per second to the bytes of data it can read from memory per second. If a task does less math per byte than the ridge, the math units sit waiting.

Slack

The margin by which urgent live work finishes ahead of its response-time deadline, which an OS can spend on background tasks.

Green context

An NVIDIA hardware feature that reserves a fixed subset of SMs for one queue of work.

Kernel

A single program sent to run on the GPU.

Resident kernel

A single long-lived GPU program that stays loaded in memory and runs an entire AI model step after step without waiting on the CPU.

L2 cache

A fast on-chip memory shared across SMs that holds recently used data so the GPU does not have to fetch it from slower main memory.

Preemption

Pausing a running background task cleanly so urgent work can use the chip, then resuming it without starting over.

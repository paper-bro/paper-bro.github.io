001The problem~6 min

Smart choices need more than smart reading

Your AI assistant gets a lot of "choose now" jobs: pick the right tool to call, pick the best document for a question, or say how severe a problem is on a scale. Researchers call these System One jobs — quick decisions, not long essays.

For these jobs, the answer isn't free-form text. The paper builds on Jev (Almeida, 2026), which said: give the model a typed output. There are just three types:

👉

Choice

Pick one of $K$ candidates. Example: which team owns "I was charged twice" — Billing, Technical support, or Delivery?

⚖️

Noul

Yes / no as a probability. Example: $P(\text{true}) = q_{\text{yes}}$ for "Was the customer charged twice?"

🔢

Score

A number from a rubric. Example: $\text{score}=\sum_i q_i v_i$ where $v_i$ are 0,1,2 for Low, Medium, High.

All three are just different ways to read the same probabilities over the options. So far, so simple. The trouble is how most open models compute those probabilities.

Current open-source practice does this: glue the request plus all candidates into one long text — "Question: ... Option A: Billing Option B: Technical support ..." — and then read the answer from the logits for tokens like a/b/c, or from a fixed-size head that only knows, say, 4 symbols. In other words, the meaning of the question, the meaning of each option, and whether an answer even exists are all mixed together inside one joint prompt.

Why mixing hurts: If everything is one text, (1) changing the request or swapping in a new candidate means re-processing the whole thing, (2) the model can learn that "first listed = more likely" and flip its pick when you shuffle, (3) a head that only has symbols a–d can't handle a 5th or 2,048th option without redesign, and (4) a softmax over the supplied candidates must sum to 1, so it can never say "none fit" — it just picks the least-bad one.

Jeva's fix, in one line, is to stop mixing. A shared language encoder reads the request alone and each option alone, turning them into separate vectors — $z_0$ for the request, $u_i$ for each option. Then a tiny decision stack lets only the request vector adapt by looking at an unchanging option memory. The options don't get rewritten each time.

This separation is what makes the four promises in the next lesson possible. But first, get a feel for the shuffling bug it solves.

Try the lab: pick a scenario and shuffle the three options. In "Joint-text" mode the top pick jumps even though no words changed — position is leaking in. Switch to "Jeva" mode and shuffle as much as you want: the same content stays on top. Watch what happens to the probabilities when only order changes.

002What good looks like~6 min

The four promises a chooser must keep

Imagine a judge at a talent show. A good judge needs four promises: say “no one qualifies” when no one does, not change the winner just because you shuffled the lineup, handle 5 tryouts or 500 with the same rules, and not re-interview the same contestants from scratch every day.

Jeva makes those promises explicit. The paper names them as four structural requirements for any chooser that picks from a list:

🚫

(i) Null-aware

Distinguish “no good candidate” from “unsure among good candidates.” A normal softmax over the supplied options must split 100% among them — it can never reserve probability for “none of the above.”

🔀

(ii) Permutation-invariant

Reordering the same options should not change the decision. If your answer is “pick Billing,” it should stay Billing whether it was listed first or last.

📈

(iii) Option-scalable

Growing from 2 to 2,048 candidates should not require redefining the output. Fixed answer symbols like a/b/c/d run out; Jeva uses one shared scorer for any K.

💾

(iv) Cacheable

Request-independent work over recurring options should be reusable. A tool registry or document list may stay the same while the question changes — you should not have to re-read all option texts inside a giant joint prompt each time.

Today’s open-source habit — paste the request plus all candidates into one long text and read answer-token logits — breaks each promise for a different reason. Fixed symbol heads break (iii). Treating an unordered set as an ordered sequence lets position leak in and break (ii). Normalizing only over candidates breaks (i) — there is no way to say “acceptable candidate exists” vs “best of a bad lot.” And putting reusable candidate text inside request-specific joint context breaks (iv) — recombining candidates forces reprocessing.

The point is not training harder: it’s architecture. Jeva promises all four jointly by separating reusable encoding from set-dependent judgment, rather than adding four patches. What the paper saves for later is how it keeps those promises — separate encoders, a tiny decision mixer, symmetric scoring, a coverage gate, and storable option memory.

Figure 2 in the paper previews the payoff you will see tested: (a) an explicit null outcome, (b) no decision flips under any tested permutation, (c) support for thousands of candidates, and (d) reuse across newly assembled sets without changing decisions.

003Building blocks~8 min

Reading the question and the answers on different pages

Imagine you hand a friend a test. The lazy way is to copy the story and all four answers onto one giant page and say “read it all at once.” Most AI choosers do exactly that — they glue request + every candidate into one long prompt and then try to read the answer off the last word.

Jeva does the opposite. It gives the question its own page, and each answer choice its own page. No page knows what is on the other pages. That is what “independent encoding” means.

📄

Page for the request

Template Tx(t, ι, x) is just:
Decision type: {t}
Question: {question}
State: {x}
This becomes one vector z0 — the model’s starting idea of “what is being asked.”

🗂️

Page for each option

Template To(t, oi) is just:
Option for {t}: {oi}
Each becomes its own vector ui. It has no index number and no other option’s text inside.

How does text become a vector? Both pages go through the same shared language reader Eθ — a big pretrained transformer that understands English. The model takes the last word’s hidden state, then squeezes it with a small bias-free projection:

$$ z_0 = P_x E_{\theta}(T_x(t,\iota,x)) \qquad\text{and}\qquad u_i = \mathrm{nrm}\!\left(P_o E_{\theta}(T_o(t,o_i))\right) $$

Px and Po just change size, nrm stretches ui to length 1 so it is a direction, not a magnitude. In the real Jeva-4B, the reader outputs width 2560 and the projections shrink it to d = 768 numbers — that is the size of each dot you will see below.

Now stack all option vectors into a table U with rows u1 to uK. Here is the key rule: inside one decision, U never changes. Only the request vector zℓ is allowed to evolve. Think of U as an immutable memory of choices pinned to the wall, while your understanding of the question walks up and looks at them.

Two practical wins already: each text gets its own token budget (you are not cramming 2,048 tool descriptions into one window), and you can reuse an option’s vector later — “Delivery” means the same thing whether the story is about a double charge or a missing package.

Why not just score each option on its own? If you score independently and make probabilities with softmax, the relative chance of A vs B is
$$ \log\frac{q_i}{q_j}=\frac{g_i-g_j}{\tau} $$
The denominator with all other options cancels out. Adding or removing C cannot flip whether A beats B — it can only nudge the absolute numbers. Jeva needs its request state to be conditioned on the whole set so the A-vs-B preference can actually reverse when the context changes. The next lesson shows how it does that without ever rewriting U.

004Core trick~10 min

How the question learns from the whole list

Looking at each option alone is not enough. Imagine you must pick the best helpdesk team for “I was charged twice.” If the list is Billing vs Technical Support, you pick Billing. But if the list is Billing vs Technical Support vs “Fraud — stolen card,” the presence of Fraud can change how you weigh Billing vs Technical Support, even though Billing and Technical Support themselves did not change. Jeva is built to let the whole list teach the question.

In Jeva only the request state moves. It starts as $z_0$ — the vector for your question and situation. The option vectors $U=[u_1;\dots;u_K]$ stay frozen as an immutable memory. Then one tiny decision block does this: it makes a question-query $q^h = \operatorname{nrm}(W^Q z_\ell)$, option-keys $k_{\ell i}^h = \operatorname{nrm}(W^K u_i)$ and option-values $v_{\ell i}^h = W^V u_i$. Compatibility is $c_i = q^\top k_i$ — high when an option is relevant to the current question-state.

Evidence is gathered with soft weights

$$a_{\ell i}^h = \frac{\exp(c_i/\tau_\ell)}{\sum_j \exp(c_j/\tau_\ell)}$$

which are the unique weights that maximize $a^\top c + \tau_\ell\mathcal{H}(a)$, a balance of “listen to the best match” and “keep some spread.” The block forms a message directly: $m_\ell = W^O\operatorname{Concat}_h(\sum_i a_{\ell i}^h v_{\ell i}^h)$, then nudges the state $\tilde z_\ell = z_\ell + \alpha_\ell m_\ell$ and $z_{\ell+1}=\tilde z_\ell + L^{-1/2}F_\ell(\operatorname{RMSNorm}(\tilde z_\ell))$, where $\alpha_\ell = \tau_\ell\sigma(\gamma_\ell)/\sqrt{L}$ so $0<\alpha_\ell/\tau_\ell < 1/\sqrt{L}$. No $K\times K$ table is ever stored — the mixer never materializes pairwise interactions.

The key difference: an independent scorer sets $\log(q_i/q_j) = (g(x,\iota,o_i)-g(x,\iota,o_j))/\tau$. The denominator cancels, so adding or removing other options cannot reverse A vs B. Jeva’s $z_1$ depends on the whole set, so it can.

Proposition 1 proves this with one block and fixed vectors. Take $z_0=(1,0)$, $A=(4,3)/5$, $B=(4,-3)/5$, $C_{\pm}=(3,\pm 4)/5$, with $\tau=3/20$ and $\alpha=1/20$. Let $w=(1+2e^{4/3})^{-1}$ be the weight on $C$. Then Jeva’s final scores $s_i = z_1^\top u_i$ satisfy

$$s_A - s_B = \pm 24\alpha w/25$$

— plus with $C_+$ and minus with $C_-$. The same A and B flip winners when you swap the third option. No independent scorer (Eq. 2) with a fixed tie-break can do both. In words: reusable features do not mean independent decisions. The geometry behind it is $\Delta s_i = \alpha_\ell\sum_{h,j} a_{\ell j}^h G_{\ell,ij}^h$ with $G_{\ell,ij}^h = u_i^\top W^O S_h W^{V,h} u_j$ — how much option $j$ contributes to option $i$ is learned, weighted by attention to the current state, without ever updating $u_j$ itself.

Try it below. Keep A and B exactly where they are, swap only $C_+$ for $C_-$ and watch the refined arrow $z_0\to z_1$ tilt up or down. In Jeva mode the A–B margin crosses zero; in independent mode it stays flat. Play with $\tau$ (how sharply to focus) and $\alpha$ (how strongly to nudge) to see when the flip appears.

005Competition vs coverage~8 min

How Jeva says 'none of the above' honestly

Imagine a teacher hands you three answer choices. There are two different worries: "which choice is best?" and "is any choice actually correct?" Most AI today mixes those worries into one. It turns scores into probabilities with a single softmax over whatever you gave it — so if none fit, it still has to pick one. Jeva separates them.

After Jeva has read your request and every option separately, it has a refined understanding zL and a score for each option:

$$ s_i = z_L^\top u_i $$

That is just how well the request matches option i — a bigger dot product means a better match. From those scores Jeva first asks the competition question: if a good answer exists, which option wins?

$$ q = \mathrm{softmax}(s / \tau_{\mathrm{dec}}) $$

q is the distribution over the candidates only. A lower temperature τdec makes the winner take more; a higher one spreads it out. But notice: if you add the same number to every si, q does not change at all — softmax is translation-invariant. Relative preference alone cannot tell you whether any option is acceptable.

Jeva's honest "none" comes from a second, separate knob: coverage.

Coverage asks: does any candidate clear the bar? Jeva looks only at the best score:

$$ \rho = \sigma\!\left(\frac{\max_i s_i - b_{\mathrm{cov}}}{\tau_{\mathrm{cov}}}\right),\quad p_{\bot}=1-\rho,\quad p_i = \rho\, q_i $$

ρ (rho) is the probability that at least one good answer is present. σ is the sigmoid squish to 0–1, bcov is a learned threshold — "how high must the best score be to count?" — and τcov controls how sharp that decision is. This is a factorization the paper writes as P(Y=i)=P(Y≠⊥)P(Y=i|Y≠⊥): coverage times competition. For a closed-set question you use q; for an open-set question you use the full p which includes the explicit null ⊥. The three temperatures τℓ (evidence gathering), τdec (competition), and τcov (coverage) are learned separately.

Why not just add a "None" candidate and softmax over K+1 things? That is what many baselines do, and it creates a hidden link to K. The paper proves (Proposition 2) that with K equal scores s and a fixed null score b₀:

$$ p^{\mathrm{flat}}_{\bot}= \sigma\!\left(\frac{b_0 - s}{\tau} - \log K\right) $$

Even if every score stays the same, adding more weak options forces log K to drag null probability down — as if the number of bad decoys proved a good answer exists. Jeva's ρ depends only on max si, so adding options below the current best leaves ρ unchanged. Probability still redistributes among pi=ρ qi because q renormalizes, but your "is there an answer?" judgment stays steady.

Figure 4 in the paper shows exactly this with τdec=0.20, τcov=0.15, bcov=0.50: (a) shifting every score up by the same amount preserves q (softmax is translation-invariant) but raises the max so ρ changes; (b) adding a weak sC=0.4 below the current max at fixed other scores preserves ρ while p=ρq spreads thinner. The joint winner among null plus candidates can still flip when you add candidates, but that comes through q, not through an automatic log K penalty on null.

In the lab, drag the three scores and the thresholds. Watch q vs p side-by-side and compare to the flat-softmax null. Then press "Add +0.5 to all" — q should stay identical while ρ rises and Jeva's null p⊥ falls. Press "Add weak option" — Jeva's null should stay put while the flat null drops.

006Symmetry & speed~8 min

Cache the answers, not the decisions

Shuffle a multiple-choice sheet and the right answer shouldn't move. That sounds obvious, but most AI readers break it: they read “question + all options as one long sentence,” so “Billing” at the top feels different from “Billing” at the bottom. Jeva fixes this by caching the answers, not the decisions.

Remember the split from earlier lessons: each option text like Option for choice: Billing is encoded on its own into a vector ui, and the question+state into z0. The stack never rewrites the options — it only rewrites the question state zℓ by looking at them. Concretely, each block makes queries from zℓ, keys and values from the frozen ui, mixes with weights

$$a_{\ell i}^{h}=\frac{\exp((q_{\ell}^{h})^{\top}k_{\ell i}^{h}/\tau_{\ell})}{\sum_j\exp((q_{\ell}^{h})^{\top}k_{\ell j}^{h}/\tau_{\ell})}$$

then message mℓ = WO concat( Σi aℓih vℓih) and updates z. The sum Σi a v is just a weighted average — addition doesn't care about order.

Permutation invariance, proved as Proposition 3: in exact math, permuting the candidates and their metadata together only permutes the final candidate probabilities pi = ρ qi. The refined state zL, the null probability p⊥=1-ρ, and typed outputs Noul and Score stay bit-for-bit the same. If one option was the unique winner, it stays the winner as a meaning — just in a different slot. No shuffling-augmentation loss needed. The proof is one line: reordering keys and values only reindexes the sum, so induction keeps z identical and shared scoring permutes.

Ties and computer rounding are the only caveats — with a true tie, “first max” depends on scan order, and different batching can wiggle the last decimal (the paper notes max prob change 0.00736 across cache modes). Otherwise zero flips: on 600 Choice sets Jeva had 0.00% flips, vs 17% to 45% for baselines.

The same trick gives reuse. Because ui and its layer projections kℓih, vℓih depend only on the option text and type, the paper bundles them as atomic memory

$$\mathcal{M}_{t}(o_i)=\left(u_i,\{k_{\ell i}^{h},v_{\ell i}^{h}\}_{\ell,h}\right)$$

and caches that. Two levels: set-cache remembers a whole ordered tuple — hit only if you ask the exact same list in the same order again. Hybrid-cache also remembers individual options, so a new combination like (C,A,D) after (A,B,C) reuses A and C for free. The paper's Figure 5 example makes it concrete: (A,B,C) then (C,A,D) from an empty bank → 0/3, then 2/3, then 3/3 hits without eviction — every whole-set lookup would have missed, but individual hits save work. Caching never reuses the answer: the new question is always re-encoded and z fully refined.

Scaling follows: with prepared memory the decision head costs O(L(d² + K·d + d·f)) — linear in K — at Jeva-4B's d=768, L=1, H=8, f=3072. No K×K matrix is ever built. Storing a bank of M options costs O(M(L+1)d). You pay to write K probabilities, so linear is the best you can hope for.

007Proof it works~6 min

Results that held up at 2,048 choices

We've seen how Jeva is built to keep four promises — honest "none fits," shuffle-proof, any number of choices, and remember what it already read. Did that actually hold up when the list got huge?

To test it, the authors started from a Qwen3.5-4B language model and added just one tiny decision block. Only 13.37 million new numbers were trained (using LoRA rank 64 — a small add-on, not retraining the whole brain). Training ran in stages from simple typed decisions to long texts and large candidate pools, with a direct loss that taught both coverage and competition at once:

$$\ell = \text{BCEWithLogits}(g,c_y) - \sum_i y_i \log q_i$$

In plain words: $g$ is the coverage logit — how strongly the model thinks "at least one candidate fits" — and $c_y$ is the true answer (1 if something fits, 0 if none fits). The first part teaches the honest "none fits" signal $\rho=\sigma(g)$. The second part teaches the competition $q$ among candidates. Together they train the full distribution $p$ over null plus candidates.

🎯

Strong typed decisions

Jeva-4B led 7 of 8 columns in Table 1 — over 90% on BANKING77 and MASSIVE at both 8 and 16 candidates, and 79.99% / 62.25% / 66.23% on Mind2Web (16 candidates). On Typed Decisions it scored 78.30%, essentially tied with InternDecision-4B at 78.70%.

🔀

Zero wobble on shuffles

On 600 Choice tests tried in original order, reversed and three random shuffles: 0.00% flips and mean total-variation 3.17×10-8 — effectively zero. Baselines flipped 17–45%. Jeva's all-order accuracy (correct in every ordering) stayed 76.67%, same as its original accuracy.

🚫

Knows when to say none

On BANKING77 K=16 with 3,080 requests (588 where no candidate actually fit), null-detection AUROC 98.66% — near perfect. Next best: KEV 93.61%, InternDecision-4B 84.27%, JevK5 79.44%. At a 5% false-alarm rate it caught 93.88% of the true "none fits" cases.

Score errors were tiny too: Noul Brier 0.0184 and MAE 0.0939 (how close probabilities were to truth), Score MAE 0.2315 and RMSE 0.3222.

The hardest stress test was scale. On ToolRet — 500 different queries split into cohorts from 32 to 2,048 candidates — the paper reports only aggregated numbers: Jeva kept 100% coverage (all 500 answered) with 78.40% aggregate accuracy, including 86.90% at K=32 and 69.88% at K=2,048. The recursive baseline JevK5 fell to 64.00% overall and 67.47% at K=2,048. Some baselines using fixed answer symbols handled only 65 of 84 ≈77% at K=32 and none beyond. Because Jeva scores the whole set in one pass, median latency with smart batching was 7.519s at K=1,024 (down from 31.730s) and 12.04s at K=2,048 (down from 94.459s) — a 7.85× batching win and over 2× faster than JevK5's ~28s at 2,048, while also more accurate.

Why this matters: Jeva needs no new output heads for more choices. One shared scorer reads each option vector, so going from 32 to 2,048 is just linear work — no new symbols, no K×K matrix.

Caching sealed the deal. Reusing just option vectors and layer projections — not final answers — left decisions identical (largest probability change 0.00736). On MLDR long documents, hybrid reuse gave 1.95× at ~50% reuse and 27.98× at 100% reuse: 2,102 ms → 75.1 ms (median paired 27.86×). At 0% reuse there is no saving — a novel set misses the whole-set cache. Whole-set caching alone stayed near 2.1s on novel orderings. Even on short Typed Decisions, a shared bank saved 93.1 ms → 46.6 ms and avoided 99.2% of re-encoding.

ABCWord bank

Word bank.

System One model

"Decide now, don't explain." A fast AI brain that picks an answer from a list instead of writing out its thinking first. Jev started this idea, Jeva improves it.

Choice / Noul / Score

Three ways to answer: Choice = pick one option (which tool?), Noul = how likely is 'true' vs 'false' (yes/no), Score = weighted average over numbers (how severe, 0-2). All come from the same probabilities.

Null-aware (answer absence)

Knowing when to say "none of these fit" instead of guessing. Jeva does this with a separate coverage gate that is different from being unsure among options.

Permutation-invariant

If you shuffle the order of options, the best answer shouldn't change. Jeva guarantees this by design.

Option-scalable

Handling 2 options or 2,048 options with the same model weights, without adding new output heads. Jeva scores each option with the same shared scorer.

Cacheable / option memory

Saving work when the same options appear again in a new request, like reusing a tool registry or document list instead of re-reading it.

Encoder & embedding vector

The shared language reader E_θ that turns any text into a list of numbers capturing its meaning. Jeva pools the last token and projects to vectors z₀ (request) and uᵢ (each option).

Softmax & temperature τ

Formula that turns scores into probabilities: softmax(s/τ). Lower temperature τ makes the winner take more; higher τ spreads probability.

Attention weights

Jeva's soft voting that gathers evidence from options: a_{ℓi}=exp(qᵀk/τ_ℓ)/sum exp(...) . High compatibility cᵢ=qᵀk means that option gets more attention, but entropy regularization keeps the spread controllable.

Brier / MAE / RMSE

For Score/Noul: how close predicted probabilities are to true targets. Brier = average squared error for probabilities, MAE = average absolute error, RMSE = square-root of squared error in original units. Lower is better.

Null-detection AUROC

How well a model separates "answer present" vs "answer absent" cases. 98.66% AUROC means nearly perfect ranking; 93.88% detection at 5% false alarm means it catches most nulls while rarely crying wolf.

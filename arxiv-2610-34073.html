001The problem~5 min

Your AI Remembers Everything — Or Does It?

Imagine an AI assistant that's chatted with you for months — birthdays, food allergies, cancelled trips, little preference updates. If you ask "When is Maya's birthday party?" you'd hope it remembers. Intuition says: let the AI turn that messy history into a neat scrapbook — a summary, a list of facts, a little profile — and answers will get better.

This paper asks a simple, uncomfortable question: what is the net value of that scrapbook compared to just searching the raw chats directly?

To call it a "net" value, the authors use a straightforward rival called naive RAG. Think of it as a photo box, not a scrapbook. It keeps the raw history as short chunks (turn by turn), and when a question comes, it just searches for the chunks that look most similar to the question and puts them in the prompt. No clever rewriting.

The setting: each person is one long corpus. In the main benchmarks that corpus is huge — a median of about 115,000 tokens over roughly 50 sessions on LongMemEval-s (about 123,000 on PersonaMem-v2 and about 139,000 on MINT-Eval). That's like a small novel of past chats. Tasks range from direct recall ("When was...?") to combining clues scattered across sessions and handling updates and cancellations.

If we only measure the scrapbook on its own, we can't tell whether it helped because of its clever organizing, or just because any search for past chats would have helped. Without the plain photo-box baseline, the two effects stay tangled.

That's why the authors fix one reference for the whole study: history as $H = \{h_1, ..., h_T\}$ — all your past turns — and the question of whether turning $H$ into a memory really beats searching $H$ directly. The paper goes much further than we will here, testing 11 different memory systems in detail. We start with the core comparison: raw search versus built memory.

002Background you need~7 min

Scrapbook vs Photo Box: RAG vs Memory

Think of two ways to keep a year of chats. The photo box just tosses every picture in as-is, maybe trimmed to fit the box. The scrapbook rewrites them into neat notes: “Mum’s birthday = 14 March,” “loves spicy.” Which helps you answer a question later?

The paper writes this as a tiny pipeline. Start with your history:

$$\mathcal{H}=\{h_1, h_2, \dots, h_T\}$$

Each $h_t$ is one turn — a message, observation, or step. Memory builds a store:

$$\mathcal{M}= I(\mathcal{H})$$

$I$ is the ingestion step. For the scrapbook, $I$ extracts facts, merges sessions, or makes a graph. For plain search (RAG), $I$ does almost nothing — it just chops raw turns into chunks. The paper calls that “$I$ is close to identity.”

At question time both use the same next steps:

$$\mathcal{C}= R(q,\mathcal{M}) \quad\text{and}\quad \hat{y}= G(q,\mathcal{C})$$

$R$ = retrieval: pick the best units for question $q$. $G$ = generation: the LLM writes the answer from question $q$ plus retrieved context $\mathcal{C}$. So RAG and memory are the same formula — they just built $\mathcal{M}$ differently.

The paper’s RAG is intentionally boring, to be a fair baseline: chunk by turns (merge short turns into ~1024-character buffers, never across sessions), search twice in parallel with BM25 word-match plus dense embeddings (Qwen3-Embedding-0.6B), dedup, then rerank (Qwen3-Reranker-0.6B) and take the top-$k$ chunks. RAG-2rd adds one more step: the LLM checks “do I have enough?” and if not, issues a second query. Answers are scored by another LLM judge (Qwen3-6-27B, checked to agree with humans 95–100%). Cost is tracked four ways: token cost (Build + maintenance + Infer), time, number of LLM calls, and total store size in tokens.

Why “same top-$k$” is unfair — Retrieval Scope. $\text{RS} = \frac{\text{tokens the LLM actually sees from retrieval through answering}}{\text{total tokens in that system’s store}}$. A scrapbook that compressed 120k tokens to 15k and a photo box that kept 120k have wildly different denominators. Top-5 could be 2% of one and 10% of the other. The paper therefore tunes top-$k$ for each system so its RS is at least as big as RAG 1-round (about 1.9% on LongMemEval-s), keeping exposure roughly comparable. Otherwise you’d confuse “saw less” with “memory is worse.”

In short: if you want to know whether the clever rewriting actually helps, you must compare against just searching the raw box — with the same amount of looking.

003The shock~8 min

The Surprise: Fancy Memories Often Lose to Plain Search

You would expect a fancy memory to beat a plain search. You take months of chats, you pull out the key facts, you link ideas together, you build a neat notebook — that should help, right? This paper tested that expectation at huge scale: 11 different memory systems, 3 benchmarks, 3 different AI models. And the surprise was how often the plain search won.

Plain search here is called naive RAG. The history is $\mathcal{H}=\{h_1,\dots,h_T\}$ — about 50 chat sessions and 100,000+ tokens per person. RAG does almost nothing fancy: it chops the history into chunks, finds chunks most like your question with keyword + embedding search, re-ranks them, and pastes the best ones into the prompt. No summarising, no graph-building.

Every memory system does more: it builds a store $\mathcal{M}=I(\mathcal{H})$, retrieves $\mathcal{C}=R(q,\mathcal{M})$, then answers $\hat{y}=G(q,\mathcal{C})$. The paper measures accuracy — judged by another AI that agrees with humans 95 to 100% of the time — and cost: token cost (building + answering), time, number of AI calls, and how big the store got.

The shock in numbers: On LongMemEval-s with Qwen3.6-27B, RAG-1rd scores 77.6% and RAG-2rd scores 81.4%. A-Mem gets 79.4% (that's −2.0 vs RAG-2rd), LightMem 78.8% (−2.6), MemoryOS 73.4% (−8.0), OpenViking 58.8% (−22.6). On PersonaMem-v2 with the same model RAG-1rd is 46.8%, most memories sit below it — MemOS is one rare exception at 50.2% (+1.5). On MINT-Eval with Qwen3.5-4B, RAG-1rd is 25.8%, MemOS drops to 18.0% (−8.1). Negative net value means $\text{accuracy}_{memory} - \text{accuracy}_{RAG} < 0$ on that setup.

Cost makes it sting more. Many memories spend far more tokens to build and to answer, make many more AI calls, and keep a much larger store — for the same or lower accuracy. In the paper's Pareto plot (accuracy up, token-cost left, bubble size = store size), RAG sits near the frontier: hard to beat on both accuracy and cheapness at once.

Is RAG just luckily tuned? The authors checked. Swapping chunk sizes, retrieval methods, and embeddings barely moves RAG — it stays strong. And looking back, only 3 of the 11 memory papers had even reported a RAG baseline at all. So the gap isn't a trick of settings; it was previously hidden because the simplest baseline was often missing.

Not every memory loses on every task — we'll see next how the same memory can both help and hurt — but overall, in these settings, a lot of extra engineering bought less, not more.

004A new lens~6 min

The Double-Edged Scissors: Benefit and Tax

Imagine you tidy a messy bedroom by cutting out every useful note and pasting it into a scrapbook. The room looks cleaner, and often you find things faster. But scissors are double-edged: the same cut that makes one fact easy to grab can slice another fact in half or hide it under glitter.

That's how the paper thinks about AI memory. Every memory system starts from the same raw history H — about 50 chats, 100,000+ tokens in these tests — and changes it a little: split a long turn into fact cards, link names across sessions, spell out a preference the user only hinted at, or rewrite "last Tuesday" as "12 March 2024". The authors call any such change a deviation from raw history.

Deviations are on purpose. They are meant to help. The trick is to see them against a simple reference: naive RAG, which just chops raw history into ~1024-character chunks and searches them with BM25 + embeddings + reranker, no clever building.

For each question, compare who is correct:

  • Memory benefit: RAG gets it wrong, memory gets it right. The deviation helped.
  • Memory tax: RAG gets it right, memory gets it wrong. The deviation hurt.

Overall score = starting RAG score + benefit − tax. So net value = benefit − tax. In the paper's Venn diagrams, the blue-only petal is benefit, the red-only petal is tax, the overlap is both right. Several systems have a small blue petal and a bigger red one — that's why the total can fall below plain search, even though memory isn't "always worse."

The key insight: The same mechanism produces both sides. Focused atomic extraction fits scattered gold facts into the top-k for one question (benefit), then fragments a single turn across two cards and only one is retrieved for the next question (tax). Multi-hop linking, preference exposure, temporal anchoring, forgetting old facts, verbalizing code — all show this pair in Appendix D.

The authors focus the rest of the analysis on tax, because benefit is the intended, expected part. Tax is the overlooked cost. And remember: tax is reference-dependent — in this whole study, it means "lost relative to naive RAG (1-round)" on the same raw history, not an absolute failure.

005System side 1~7 min

Vanishing Ink: When Building Memory Erases Clues

Think of an AI's memory like notes you rewrite from a messy chat. Rewriting can make things tidier — but every time you rewrite, you risk leaving something out. Once it's gone from the notes, no amount of clever searching will bring it back.

That is faithfulness: did the evidence survive the building step at all? The paper separates it from a later problem — getting evidence back out. To do that, they run an "oracle" test that removes search completely.

On each question, the researchers know which raw chat turns actually contain the answer — call them gold raw turns. They also track what happened to those turns when notes were built — the matching gold memory units (or nothing, if it was lost). Then they answer using only those perfect pieces.

If accuracy with gold raw turns is high but with gold memory units drops, the gap is construction loss. Search wasn't involved, so the only explanation is vanishing ink.

How common is vanishing ink? Humans checked 500 random facts and labeled how well each fact survived into memory (Table 2 in the paper). The labels are simple:

  • NL — no loss, fully preserved
  • PL — partial loss, some detail gone
  • ML — major loss, core meaning gone
  • NU — no unit at all, nothing was created

Results vary hugely by system. In a simplified reading: MemoryOS kept 98.4% with no loss and 1.6% with no unit; MAGMA kept 93.6% with no loss; SimpleMem kept only 65.6% with no loss, with 27.6% partial loss and 4.6% with no unit; OpenViking kept just 39.4% with no loss and a striking 38.0% with no unit. Some systems are neat copyists; others are heavy editors.

Here's the twist that makes faithfulness different from just "bad system = always worse." For some systems, the oracle accuracy with gold memory units is close to oracle accuracy with gold raw turns, but both are far above their normal accuracy with real retrieval. Translation: the ink didn't vanish — the note is still there, just buried. That's not a faithfulness tax; it's an accessibility tax, which we tackle next lesson.

006System side 2~7 min

Buried Treasure: Why Kept Clues Stay Hidden

Last time we saw memories can delete a clue before you even search. But this lesson is stranger: the clue is still in the memory — and you still lose.

Think of buried treasure. The map is safe in your drawer. You just can't find the drawer because you reorganized the whole house into tiny labeled boxes, stuffed the map into a thick scrapbook, and rewrote the labels in different words.

The paper calls this accessibility: how easily can kept evidence be recalled? To test it, the authors did a replay. For each question they know the gold evidence — the raw chat turns that prove the answer. They also know the matching gold memory units in each memory store. Then they simulate searching again and again, removing what they found each round, and count how many rounds it takes to get all the gold pieces. Pieces that never existed (the NU cases from last lesson) are marked not retrievable and excluded.

Key result: on LongMemEval-s and PersonaMem-v2, memories recover fewer queries in round 1 than naive RAG over raw chunks. The same evidence is there, but buried deeper.

Looking at real examples, three patterns kept appearing:

🧩

1. Fragmenting

One chat turn is split into several memory units. You need every piece to answer, but the pieces rank far apart, so some only show up in round 2 or 3.

💧

2. Diluting

The evidence is wrapped in extra text — a long user profile or elaborate note. The extra words water down the match with your question.

📝

3. Rephrasing

The evidence is rewritten. The meaning may be close, but the embedding — the numbers that measure similarity — moves away from the query, so it ranks lower than the original wording.

You can see this shift in numbers. For each fact the authors compare $sim(q, g_{raw})$ — how close the query is to the original turn — with $sim(q, g_{mem})$ — how close it is to the memory version. If there are several memory units for one turn, they use the median similarity. Absolute numbers can't be compared across systems directly, because each system searches its own store. What matters is the within-system drift: does the memory version slide left to lower similarity than the raw version it came from? For some systems it does, clearly.

A subtle point the paper stresses: a low $sim(q, g_{mem})$ does not by itself prove deletion. In accessibility analysis the evidence is confirmed preserved — the drop is purely about being harder to surface. That's why even a loss-free system like MAGMA (93.6% no-loss) can still pay memory tax.

So faithfulness is "did we keep it?" Accessibility is "can we find it fast?" Both create tax, but only the first involves loss.

007System × evaluation~7 min

Shaky Hands and Easy Tests

Imagine you build a scrapbook with one pair of hands, but later you have to read it with different hands. If the scrapbook adds extra steps — like the AI summarizing, rewording, or linking pages — those steps can shake when the hands change. Plain search over the original photos has fewer moving parts, so it shakes less.

This is what the paper calls robustness as a form of memory tax. The team built each memory with three different backbones — the small Qwen3.5-4B, medium Qwen3.6-27B, and large GPT-5.6 Luna (low) — and then answered questions with a different backbone. Two things happened. First, changing who built the memory changed the result, which makes sense because the building uses that model. More telling: holding the build fixed and only swapping the answering model caused a bigger accuracy drop for many memory systems than for naive RAG. In Figure 6/15 the grey bar is RAG's drop; the memory's segment sticks out further in red when it is worse. The tax here is not just “a harder test,” it is extra wobble introduced by the memory itself.

The other half of the story is not about shaky hands at all, but about easy tests. The paper checked a wider pool of long-memory benchmarks and found simple retrieval already scores high. One ultra-simple baseline that just picks the rarest words in the question (IDF-keyword) gets above 50% on several benchmarks. The paper's hybrid RAG gets about 82.7% on EverMemBench-MCQ, 79.9% on HaluMem-Medium, 77.6% on LongMemEval-s, and 75.3% on LoCoMo (Table 15, ordered by RAG-Hybrid score). Those numbers leave little headroom — not much space between “plain search does” and “perfect 100%.”

When headroom is small, even a small tax becomes visible. Suppose memory could add 6 good fixes but also breaks 10 questions RAG got right. On a hard test where RAG gets 30%, those 6 fixes count fully and net value is 6 − 10 = −4, still negative but close. On an easy test where RAG already gets 80%, only 20 points of improvement are even possible before you hit 100%. Then the same memory can only contribute at most 6 of those 20, so net stays 6 − 10 = −4 or worse — and every loss is magnified because you compare to an already-strong baseline. Lightweight systems that hardly change the raw history inherit RAG's strength and pay almost no tax, so they look especially good on retrieval-friendly benchmarks.

Key idea: tax is not only a point-loss. It shows up as brittleness across models and as visibility on easy benchmarks. Both mean we should always report RAG alongside memory, keep headroom in mind, and build harder complementary tests.

008Generalization~6 min

Same Story Elsewhere: From Robot Skills to Video Worlds

So far we saw the trade-off in chat: a tidy summary can make a fact easier to find, or it can erase it. The paper argues this is not just about chat at all.

Any time an AI does something clever to past information — rewrite it, compress it, turn it into a workflow or a set of numbers — it deviates from the raw history. That deviation is double-edged by definition: meant to help, but it can also hide what you need. The authors call the visible wins memory benefit and the losses memory tax, both measured against the simplest alternative: just search the raw past.

First, agent experience. Here memory means "remember how I solved earlier tasks." The test uses 6 benchmarks with Qwen3.5-4B, where the agent trains on one split and is tested on another with memory frozen. The naive baseline is very plain: for each new task, pull the 2 past tasks whose descriptions are most similar and paste their whole trajectories into the prompt.

Results flip by domain. On web tasks like WebShop and Mind2Web, turning long traces into short workflows can beat naive — for example Memp gets 44.5 on WebShop vs 38.4 for naive RAG, and 47.9 vs 45.3 on Mind2Web. But on tool-use tasks the same idea often loses: on AppWorld naive RAG gets TGC 22.6 while Memp gets 14.3 and ReasoningBank 14.3, well below naive. On τ²-Bench naive gets 69.0 pass^1, while several memory methods score lower. In Figure 8 the paper colors bars green when above naive and red when below, with dashed boxes below zero showing the tax — the score naive got where memory failed.

Same pattern in video worlds. To keep a generated video consistent over time, a world model must remember past views. Naive memory just re-injects past frames (I3DM). Fancier memories keep compressed versions: raw KV caches, learned KV, visual latents, or a handful of memory tokens. On Context-as-Memory evaluation naive frames get SSIM 0.560 and 1-LPIPS 0.704; the best fancy latent (MagicWorld) gets 0.388 and 0.341 there. On MemoBench naive gets 0.430 / 0.476 vs 0.379 / 0.420 for raw KV (WorldKV) and lower for others. The raw past is strong again.

In short: across chat, skills, and video — across stores that look like text, workflows, latents, KV caches, and tokens — plain retrieval over the raw history is a tough baseline to beat. That is the paper's generalizability claim. It does go further into tables and costs for each setting (see Appendix C.6), but the lens stays the same: ask what benefit the deviation added and what tax it charged.

009Fixes & takeaways~6 min

Paying Less Tax — And Why It Matters

We’ve seen the bad news: a clever memory can lose to dumb search because it changes the raw history — and some changes hurt. The good news from this study is you don’t need a brand-new memory to pay less tax. Small, cheap patches help a lot.

Think of history H as your photo box of past chats. A memory system builds M = I(H) — summaries, facts, graphs — then at question time fetches C = R(q,M) and answers with y-hat = G(q,C). Every tweak in I is a deviation from the raw box. The paper’s lens is simple: benefit = questions memory fixes that RAG missed; tax = questions memory breaks that RAG got right. Net value = benefit − tax, always relative to naive RAG.

Three low-cost fixes the paper actually tried — no new architecture. 1) Keep a lightweight path back to the source: also retrieve raw chunks alongside memory and rerank together. 2) Remember how you remembered: save past queries plus the evidence that finally worked, so deep-search wins become easy next time. 3) Model future demand: use past interests to decide where to spend build effort (ahead-of-time vs just-in-time).

Fix 1 makes deviations recoverable. If a summary erased a date or buried it in a long profile, the raw-chunk rerank can rescue it. In the paper’s proof-of-concept, adding this joint retrieval consistently cut tax across several systems — one extra rerank is far cheaper than rebuilding a graph.

Fix 2 is recursive. Access experience itself becomes memory. When evidence only appeared in round 3 last time, storing that path means a similar next query gets it in round 1. Fix 3 treats memory like a recommender: predict which past facts future you will actually ask about, so you don’t waste tokens over-processing everything now, and you don’t pay latency to build everything just-in-time later.

Why bother? Because naive search is shockingly strong. On 15 benchmarks the simple RAG-Hybrid already hits ~70-83% (e.g., EverMemBench-MCQ 82.7%, HaluMem 79.9%, LongMemEval-s 77.6%). When there’s little headroom left, even a tiny tax dominates. Reporting RAG and controlling Retrieval Scope (RS = tokens seen / total tokens in store) shows how much room is really left — and whether your memory tax is worth paying.

Go deeper: The net lens travels. In tool-use agents and in video world models (naive frames SSIM 0.560 vs latent/KV memories <0.39 on C-as-M), simple raw retrieval again beats fancier memory — same trade-off, different modality. The authors’ message is not “memory is useless,” but: always measure benefit vs tax vs RAG, track RS, and test across backbones.

ABCWord bank

Word bank.

Agent with long-term memory

A long-horizon AI assistant that keeps information across many chats or tasks and re-uses it later.

RAG (naive chunk-based)

Retrieval-Augmented Generation: keep the raw history (chopped into chunks), search for chunks most similar to a question, put them in the prompt. No smart summarising.

Memory ingestion I(H)

How the history is turned into memory: M = I(H). Example: I = extract facts, make a summary, build a graph.

Retrieval R(q,M) and Generation G(q,C)

Fetch from memory: C = R(q, M). Generate answer: y-hat = G(q, C). R picks, G writes.

Retrieval Scope (RS)

Fraction of stored tokens the model actually sees from retrieval to answering. In the paper: exposure tokens / total retrievable-store tokens, averaged over questions. Used to fairly set top-k when systems have very different memory unit sizes.

Memory Benefit

Per question where memory succeeds while RAG(1-round) fails. The intended upside of memory deviations.

Memory Tax

Per question where RAG(1-round) succeeds but memory fails. Losses from harmful deviations; when tax > benefit, net value is negative.

Double-edged deviation from raw history

Deviation view: any nontrivial memory step changes structure/wording/access of raw history. Designed to help, but can also hide or lose evidence.

Embedding and Reranker

Numbers that turn text into vectors so similarity = closeness. Paper uses Qwen3-Embedding-0.6B for all systems, plus Qwen3-Reranker-0.6B reranking.

Cost metrics

Token cost (ingestion+QA), wall-clock time (single-concurrency normalized), LLM calls, and memory store size in tokens.

Faithfulness vs Accessibility

First check: is evidence still in memory at all? (construction loss). Second check: is kept evidence easy to surface in top ranks?

Benchmark headroom

How much headroom a benchmark leaves above simple retrieval. If naive RAG already scores ~70%, even small memory losses become visible.

Experiential and World-model memory

Re-using past task traces (e.g., ALFWorld embodied tasks, WebShop) or past video frames as memory. Paper shows same benefit/tax pattern there.
